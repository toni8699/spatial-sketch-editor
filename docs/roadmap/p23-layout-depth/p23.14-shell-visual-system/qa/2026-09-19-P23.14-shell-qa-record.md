## Findings

- **F1 — Scene workspaces could mount the Camera node editor** (resolved in the review pass).
  With a camera node retained from the Camera domain, Scene · 3D rendered
  `EditorCameraInspector` (position/target/FOV — framing authoring) while the Status Rail read
  `No selection / 0 selected`. Contract: `design-shell-specs.md` §15 (“Scene workspaces may show
  Camera entries … without exposing sequence/timeline/framing authoring”) and §20. Root cause:
  the panel followed the *selection's* domain while the workspace was Scene, and the header
  walked an independent precedence over the raw selection slots. Now **the workspace owns
  exposure** (`app/inspector-target.ts`): a Scene workspace never mounts the Camera editor and a
  Camera workspace never mounts a Scene/Asset editor, the retained selection is still remembered
  (nothing is cleared — S3 continuity is intact), and header and body resolve from the same
  value. Verified live: Scene · 3D with a selected asset shows header `Paris Salon Grand Piano /
  ASSET` over an `Asset details` body; carrying that selection into Camera · 3D leaves header and
  body on the workspace's own (empty) target. Pinned by
  `tests/lib/editor/app/p23-14-inspector-target.test.ts`.
- **F2 — Inspector header and body could describe different selections** (resolved, same fix).
  With the Assets panel focused, the section header still read the remembered camera node
  identity while the body rendered the asset-details panel: two selection models reaching one
  panel. The header is now scoped to the resolved domain and reads the same exposed slots the
  body branches on, so it cannot name an entity whose editor is not mounted.
- **F3 — locality badges asserted the legacy format (fixed in this pass).**
  `CameraPlanInspector` hard-coded `Camera node · room-local` and printed an unguarded
  `Room` slot; `EditorCameraInspector` and `EditorTransformInspector` likewise. All now
  derive from the selection (`roomId ? 'Room-local' : 'World-local'`), matching P23.0b
  world-local being the canonical Scene format.
- **F4 — numeric fields report `:invalid` while holding legal values.** `min="0.001"` with
  `step="0.01"/"0.05"` puts the browser's step base off-grid (`0.1`, `3.75` both fail), so
  the a11y tree announces valid values as invalid. No stylesheet paints `:invalid`, so this
  is an AT-truth defect, not a visual one. **Not patched, and explicitly deferred — not
  accepted.** The fix (align `min` to `step`, or `step="any"`) changes arrow-key increments,
  which is Inspector entry design rather than shell polish, so it is now tracked as **TD-2**
  in [`docs/operations/tech-debt/README.md`](../../../../operations/tech-debt/README.md) with
  its own repro and owed acceptance tests (17 `min="0.001"` rows plus the `min="0.05" step="0.05"`
  rows in `EditorInspector.svelte`).
- **F5 — `POV / Observer` appeared twice in Camera 3D** (resolved in the review pass). The View
  Bar painted a second copy of the switch the Camera Drawer transport already owns. The drawer
  is the single owner — it carries the switch in *both* camera views and in both drawer states
  (the collapsed mini-player always; the expanded panel while a preview is live) — so the bar's
  copy is retired.
- **F10 — five facts had more than one writable home** (resolved in the review pass; the class
  behind F5). Mounting `EditorViewportToolbar` in both hosts meant the Tool Tray rendered the
  View menu as well as the View Bar, and the View Bar's utilities were echoed inside that menu:
  Panel visibility, the Scene grid toggle (`WorkspaceRibbon` mounts `EditorViewportGridControls`)
  and the camera Path/Frame toggles each had two writers, and Camera 3D painted the View menu
  twice. Now ownership is decided **by host** (the tray paints tool groups only; the bar owns
  the menus and utilities) and exposure **by workspace**. Pinned per fact by
  `tests/lib/editor/app/p23-14-control-ownership.test.ts`, and by
  `tests/lib/editor/app/contracts.test.ts` at the composition level. The durable rule this
  produced is recorded in the contract §10/§11 and §2.12.
- **F6 — progressive-density threshold was too high (fixed in this pass).** The container
  measured is the Navigator scroll track (232 px inside the reference 268 px column), so a
  `16rem` (256 px) threshold hid row metadata at the *reference* width. Now `216px`: fires
  only when the column is squeezed below ~252 px, i.e. between the reference and the 240 px
  minimum.

- **F7 — the Tool Tray's engraved tier had drifted above what the rail can paint (fixed in
  this pass).** Review F3 read `design-specs.md` §22's "10 px engraved group labels" as a
  floor and moved both the group label and the tool label from 8 px to 10 px. §11 also fixes
  the rail at 44 px, and the two cannot both hold: measured in the running app, at 10 px/600
  the group names need 46.6–63.8 px and single tool words up to 48.6 px inside the text box
  the rail can offer, so every label broke *inside the word* — `SELEC / T`, `OPENI / NGS`,
  `OBJEC / TS`, `Windo / w`, `Colum / n`, `Platfor / m`. Camera 3D's `Add camera` was worse
  than a bad break: `EditorViewportToolbar`'s own `white-space: nowrap` (a View Bar contract)
  is inherited into the tray, so the label painted 46 px wide in a 39 px box and overran the
  rail into the Paper. **Patched** — see the judgment call below; §22 of
  `design-system/design-specs.md` is reconciled to the landed tier and
  `p23-14-contrast-floor.test.ts` re-pins it.

- **F8 — the rest of the shell's type and button chrome had drifted from the Atlas (fixed in
  this pass).** The owner compared the whole shell, not just the rail: the Atlas's fonts,
  font sizes and button sizing/styling did not match what shipped. Measured cause: §7's flat
  ramp was **mostly dead** (nothing consumed `title`, `panel-title`, `toolbar`, `tree-row` or
  `status`), so components carried their own `rem` values instead — seventeen distinct sizes
  between 9.6 px and 13.6 px, no two surfaces agreeing, which is exactly why an Atlas
  comparison can never converge. Deltas found and closed:

  | surface | Atlas | shipped before |
  | --- | --- | --- |
  | View Bar controls | plain 24 px buttons, 10 px utility / 11 px MODE labels, pressed = edge border + inset bottom rule | 28 px enclosed troughs, 12 px labels, accent-soft fill |
  | Head (Project Row) | 26 px controls, 14 px identity | 12 px controls, 13 px identity |
  | Domain Spine station | 74 px, 11 px label in the domain's casing, 24 px icon | 72 px, 10 px uppercase tracked label |
  | Navigator rows | 29 px rows, 12 px label, 10 px mono meta | 2 rem (`32 px`) rows, 0.74 rem label, 0.62 rem meta |
  | Inspector section headers | 10 px/600/+0.04em | 11 px/600/+0.05em |
  | Timeline ruler | 9 px **mono** | 11 px sans |
  | Status Rail | 10 px, 12 px padding, 20 px gaps | 11 px, 8 px padding, 0.9 rem gaps |
  | Tool Tray | roles + fitted geometry | loose px in rules |

  **Fixed structurally, not value by value (owner ratification R3):** the shell no longer
  holds pinned sizes. The seven-step ladder (9/10/11/12/13/15/20 px) and every role
  (`--editor-type-*`, `--editor-control-*`, icon + fitted-geometry roles) are multiples of two
  knobs — `--editor-type-scale` for type, `--editor-control-scale` for button/group geometry —
  so the next Atlas pass retunes one file instead of fifty components. The pre-R3 generic
  control names survive as **aliases** onto the roles, so a component written against either
  vocabulary moves with the same knob. Verified live: the whole shell scales together
  (status 10 → 11.5 px, stations 11 → 12.65 px, rows 12 → 13.8 px, identity 14 → 16.1 px, rail
  44 → 51 px at 115 %), and the control knob moves only the chrome (station 74 → 89 px, rail
  tools 42 → 50 px). The sweep is pinned against regression by
  `tests/lib/editor/app/p23-14-type-roles.test.ts`, which fails if a swept surface
  reintroduces a pinned `font:`/`font-size:` value — a guard, because the failure mode is
  per-surface and invisible to any single component's tests.

  **Two things found while sweeping, worth naming:** the `font:` **shorthand** was the drift
  the greps missed (three pinned values in `EditorViewportToolbar`'s popover only showed up
  once the guard scanned declarations rather than a `font-size` string), and a **nested CSS
  comment** in a token-file note silently dropped the whole ladder from the cascade — real in
  the browser, invisible to a text scan. Both are now scanned for.

- **F8 residual (deliberately not half-migrated):** the **Inspector family**
  (`EditorInspector.svelte` + the eight panel inspectors) still carries pinned 12 px / 12.5 px
  tiers, because P21.5 Slice 4 pins them across all nine components. The band-by-band mapping
  is recorded in `tokens.css` so the batch stays mechanical.

- **F9 — the View Bar's `MODE` caption was painted inside a control capsule (fixed in this pass,
  owner-reported).** The owner read `MODE` as a third segment sharing the box with
  `Layout | Arrange`. The cause is the leak class §2.2 already records: `LayoutDraftToolbar`'s
  own `.segmented` rule (`padding: 1px; border: 1px; border-radius: 6px;
  background: var(--editor-bg-control)`) keeps applying inside the shell, and the shell scope had
  only cleared the properties it happened to name. Measured live before → after: wrapper
  `#E8E5DD` fill / 1 px border / 6 px radius / 1 px padding → transparent / 0 / 0 / 0; `MODE`
  10 px/600 muted with an 8 px gap (Atlas `.mode small`); the pair on the 11 px MODE tier at
  24 px (Atlas `.mode button`).

  **Three more instances of the same leak were found in the same audit and are fixed:** the
  tool-group divider (`padding-right: 0.32rem` + `border-right`) the Atlas does not have;
  `LayoutDraftToolbar`'s `button { height: 28px }`, which was sizing the View Bar's 24 px tiers
  from the component instead of from the role; and the component's pressed fill (a translucent
  accent wash). Pressed now takes the Atlas's recessive surface step (`--editor-bg-recess`) plus
  the edge border and inset rule, so hover lifts / pressed sinks — the pair the armed tray tool
  already uses (R2) — and the state does not rest on hue. Pinned by
  `contracts.test.ts` § "paints MODE as a muted caption beside two plain buttons".

### Judgment call — the tray's engraved tier (§7 vs §11)

Scope: the P23.14 tray's own type only. No other shell typography moved.

1. **Spec first, as asked.** §7's approximate scale lists `10 px: engraved/group labels`;
   §11 mandates the `44 px` rail. The tray was set to 10 px and does not fit it.
2. **Measured in the app**, canvas-metric at weight 600 against the widest text box the rail
   can give a label (`44 − 2 gutter − 1 rail border − 2 control border = 39 px`):

   | size | group labels that overflow 39 px | tool words that overflow 39 px |
   | --- | --- | --- |
   | 10 px | SELECT, OPENINGS, OBJECTS, TRANSFORM, CAMERA (46.6–63.8 px) | Window, Platform, Sculpture, Connect, Sequence (39.5–48.6 px) |
   | 9 px | OPENINGS, OBJECTS, TRANSFORM, CAMERA (39.1–57.4 px) | Sculpture, Sequence (42–43.7 px) |
   | 8 px | OPENINGS, TRANSFORM (41.7 / 51 px) | Sequence (38.8 px) |
   | 7 px | TRANSFORM only (44.7 px) | none |

   So 10 px is not a stylistic preference the rail can be talked into — it is arithmetically
   impossible above ~8 px for the group vocabulary.
3. **Deliberate call: paint the reference, not the tier.** §7 calls its own hierarchy
   *approximate*; §11 asks only for "small persistent group labels and compact icon-led
   tools"; and both the PLATE reference PNGs and the Atlas rail paint 7 px group / 8 px tool
   labels. The tray now paints those two values through two new tokens
   (`--editor-font-size-tray-group` / `-tool`), so the deviation is named, testable and
   reversible in one place instead of hiding as loose pixels in a rule. §7's 10 px tier still
   owns every other engraved label in the shell.
4. **The geometry was borrowed, not invented.** The rail stays `44 px` (`--editor-tray-width`)
   and buttons stay `42 px` tall; the gutter tightened `3 px → 1 px` and the control now
   stretches to the rail instead of a hard `38 px`, which is what turns 36 px of text box into
   39 px. That 3 px is the difference between `Sequence` fitting and breaking, and it is
   inside the rail's own padding — no §5 composition track moved. `white-space: normal` is
   added in the shell scope only, so the frozen relic's floating toolbars keep their View Bar
   contract.
5. **Result, measured live:** tray `scrollWidth == clientWidth` (43 px) in all four reachable
   tray vocabularies — Scene Plan, Scene 3D, Camera 3D, Camera Plan — with every label on one
   line except the two-word labels, which now wrap at their word boundary (`Rect Room`,
   `Poly Room`, `Add Camera`, `Add camera`).
6. **The one word that cannot fit at 7 px is resolved, not accepted (owner ratification R1):**
   the group label `TRANSFORM` (44.7 px at 7 px — wider than a 44 px rail can ever carry)
   now steps down to a 6 px compact floor via an opt-in `data-group-compact` on that group,
   so it paints on one line instead of breaking. The word is kept, because `TRANSFORM` is the
   group name the spec itself uses and renaming it to fit would have contradicted the spec
   being promoted. Nothing else in the tray touches the `overflow-wrap` guard.

## Review pass — ownership by host, exposure by workspace (2026-09-19)

A code review of this PR at head `f7a31e2` (diff + promoted contract + this record + the tests)
requested changes: the shell direction and the R1–R3 ratifications were accepted as coherent,
but three seams had to close before the promoted baseline could be trusted. All three are now
fixed, and the class they belong to has a durable rule in the contract.

**1 — Control ownership (the F10 class).** Mounting `EditorViewportToolbar` in two hosts meant
any inherited rule about *what the toolbar paints* applied to both, so the Tool Tray rendered the
View menu and the View Bar's own utilities were echoed inside that menu. Four facts had two
writable homes — Panel visibility, the Scene grid toggle, the camera Path/Frame helper toggles,
and `POV / Observer` (F5) — and Camera · 3D painted the View menu twice. The fix is by host, not
by button: the tray host paints tool groups only and the View Bar owns the menus and utilities,
and the drawer keeps `POV / Observer` because it carries the switch in both camera views and in
both drawer states. `tests/lib/editor/app/p23-14-control-ownership.test.ts` asserts unique
writable ownership per fact; `contracts.test.ts` asserts it at the composition level. What the fix
removed, so a reviewer can weigh reversibility: the bar's `Observer`/`POV` pair (a one-line revert
if the bar pair is preferred over the drawer's); the menu's `Panels` section (`Left sidebar`,
`Right inspector`, `Focus 3D` — all three are painted in the bar's utilities group); the menu's
`Grid` toggle (the grid controls own visibility and opacity); and the menu's `Node handles` /
`Framing & FOV` rows wherever a View Bar exists, because the bar paints Path and Frame directly.
The frozen relic's floating mount — which has no bar — keeps the full menu.

**2 — Inspector exposure (F1/F2).** The body routed by the *selection's* domain while the header
walked a separate precedence over the raw selection slots, so Scene · 3D could mount the Camera
framing editor and the header could name an entity whose editor was not mounted. Exposure is now
resolved once, by workspace, in `app/inspector-target.ts`: `resolveInspectorDomain()` returns the
single domain the panel is allowed to present, `resolveInspectorExposure()` gates the raw
selection slots the header and the panel bodies read, and both header and body consume the same
result. No selection is cleared — the retained selection stays remembered for workspace
round-trips (verified live: an asset selected in Scene · 3D presents its identity header over the
asset-details body, and the same selection carried to Camera · 3D leaves header and body on that
workspace's own empty target). `tests/lib/editor/app/p23-14-inspector-target.test.ts` pins the three acceptance
cases; `contracts.test.ts` and `p21.6-slice-c.test.ts` were re-pinned from the duplicated shape
to the constraint.

**3 — Coarse pointer.** The 44 px rule covered `button`, `[role]`, `select`, `input` and
`summary` but not `a[href]`, so the Project rows' Projects / Spatial / Publish links stayed at
the regular ~26 px control height while the guard test — named for the invariant — only checked
that the selector string was present. `a[href]` is now included, and
`p23-14-a11y-motion.test.ts` asserts the known interactive shell species instead of the string,
so another link cannot bypass the guard later.

**F4 is deferred, not accepted** — tracked as TD-2 in the tech-debt ledger so it cannot read as
ratified behaviour.
