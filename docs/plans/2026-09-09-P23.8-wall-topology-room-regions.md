# P23.8 — Straight-wall topology + persistent Room regions

**Parent:** [P23 — Layout Depth umbrella](2026-09-07-P23-layout-depth-minimum-build.md)  
**Status:** `implementation-ready` — Foundation Gate F0 middle; consumes P23.0a and blocks P23.0b writer cutover.  
**Evidence:** H3 topology harvest + H5 identity/migration harvest complete; owner reconciliation ratified 2026-09-09.  
**Current behavior note:** current Layout is still Room-owned until F0 ships.

## Outcome

Museum has a small explicit straight-wall topology layer that can node Walls, derive enclosed candidate faces, diagnose invalid topology, and reconcile those faces to persistent `LayoutRoom` identities deterministically.

This is not a general GIS/CAD kernel. It is the minimum topology needed for wall-first authoring.

## Hard ownership boundary

> **Geometry/topology derives candidate faces. Museum product logic owns persistent Room identity.**

H3 owns:

- robust straight-segment orientation/classification;
- explicit noding;
- directed-edge ordering;
- boundary-Wall face extraction;
- topology diagnostics/tolerance policy.

H5 owns:

- Room correspondence;
- Wall/Junction/Room lineage;
- ID allocation;
- metadata retention;
- semantic reference remapping;
- exact replay behavior.

Do not mix these responsibilities into a face extractor that creates Rooms directly.

## Canonical topology records

P23.8 consumes P23.0a's globally stable `LayoutJunction` / `LayoutWall` / `LayoutOpening` identities.

Connectivity rule:

```text
same Junction ID
→ connected

near coordinates only
→ not connected
```

Snap/proximity may propose a join, but the committed authoring operation must explicitly reuse/create the Junction ID.

## Straight-Wall classifier

Create one renderer-neutral typed classifier backed by the H3 robust orientation adapter.

Required result vocabulary includes at least:

```ts
type WallIntersectionKind =
  | 'none'
  | 'shared-explicit-junction'
  | 'endpoint-on-interior'
  | 'proper-crossing'
  | 'collinear-endpoint-touch'
  | 'collinear-overlap'
  | 'invalid';
```

Exact names may differ. What matters is that normal topology logic never collapses these into one tolerant boolean.

Use one Museum X/Z wrapper around `robust-predicates` orientation; callers must not import upstream predicates directly throughout editor/render code.

## Authoring noding rules

### Endpoint to endpoint

If an operation commits an endpoint to an existing Junction, reuse that Junction ID. No duplicate coincident Junction is created for the accepted connection.

### Endpoint on Wall interior — T

Committing a Wall endpoint onto the interior of another Wall invokes canonical Wall subdivision:

- create/reuse one Junction at the intersection;
- split hosting Wall through the subdivision contract below;
- connect the incoming Wall endpoint to the explicit Junction;
- recompute candidate faces/reconciliation;
- commit once or reject once.

### Proper X crossing

A Wall insertion that legitimately crosses an existing Wall may node both affected Walls at one explicit Junction only through a complete planned operation. Do not leave visually crossing but topologically un-noded new data.

If the proposed crossing produces an unsupported correspondence component, overlapping geometry, invalid opening split or other rejected topology, reject the whole command.

### Collinear overlap

Normal new wall-first authoring rejects collinear overlap. Do not auto-merge, trim, choose the longer Wall or infer shared ownership.

Legacy compatibility is handled by P23.0 and may preserve old overlapping physical records read-only.

## Wall subdivision identity

For Wall `W(A → B)` split at distance `d` from canonical start `A`:

```text
A────────────B
A────X───────B
```

Rules:

1. `X` is allocated/reused once;
2. `A → X` retains Wall ID `W`;
3. `X → B` receives one deterministic new Wall ID;
4. canonical orientation remains authored — do not reverse fragments for convenience;
5. split at existing endpoint is no-op/reject, not a zero-length child;
6. every Room boundary referencing `W` is rewritten atomically.

Forward Room boundary:

```text
[W forward]
→ [W forward, W2 forward]
```

Reverse Room boundary:

```text
[W reverse]
→ [W2 reverse, W reverse]
```

### Opening rebasing

Given opening interval `[o, o + width]`:

- `o + width <= d` → stay on retained Wall, same Opening ID/offset;
- `o >= d` → move to new Wall, same Opening ID, `offset' = o - d`;
- `o < d < o + width` → reject;
- split exactly at opening start → move to new Wall at offset `0`;
- split exactly at opening end → remain on retained Wall.

Equality/classification follows H3's canonical geometry policy; P23.8 adds no new epsilon.

## Boundary versus Partition

`LayoutWall.role` is semantic authoring truth:

- `boundary` → participates in Room face extraction;
- `partition` → physical Wall/Openings/render/query behavior but excluded from semantic Room face extraction.

Changing role is a topology-changing operation and must run the same candidate-face/Room-reconciliation gate before commit.

A Partition may divide physical floor space visually without creating a second Room.

## Candidate-face extraction

Build directed edges from **boundary Walls only** after explicit noding/validation.

Required properties:

- outgoing directed-edge ordering is deterministic and robust;
- traversal orientation is normalized once;
- candidate face stores oriented Wall references / deterministic derived key;
- candidate face does not allocate persistent Room ID;
- dangles/cut edges/invalid rings/non-noded inputs surface as diagnostics rather than being silently deleted from authored data.

Do not import a JTS/Flatten project model. Reimplement the narrow pattern in Museum terms.

## Holes / nested loops

Initial P23 does not promise general hole/island/nested-region authoring.

If candidate topology requires shell/hole interpretation beyond a separately proven simple case, reject with a specific unsupported nested/hole diagnostic rather than inventing Room semantics.

Legacy compatibility may still render recognized old documents through P23.0 preparation without granting new-authoring support.

## Room correspondence model

Use explicit lineage first:

```text
1. authoring-operation Wall/Junction lineage
2. candidate-face boundary lineage
3. overlap area
4. temporary predecessor interior witness
5. canonical face key
```

Never use:

- equal old/new Room count alone;
- face traversal order;
- Room array order;
- timestamps;
- random IDs;
- geometry-only global nearest matching.

## Canonical face key

Derive a deterministic **temporary** key from the already-derived oriented boundary cycle, e.g. stable Wall ID + direction tokens canonicalized by rotation and existing tuple-safe serialization.

The face key:

- is not a Room ID;
- is not persisted as product identity;
- is used for deterministic sorting/tie-breaking inside reconciliation/ID allocation.

## Affected correspondence components

Classify topology changes per connected affected predecessor/candidate component.

Safe automatic components for initial P23:

```text
0 old Rooms → new independent candidate faces
1 old Room → 1 candidate
1 old Room → 2 candidates
2 old Rooms → 1 candidate
```

Wall subdivision that preserves face count is a special `1→1` lineage case.

Unsupported initial components include:

- `2 → 3`;
- `3+ → 1`;
- simultaneous split+merge inside the same correspondence component;
- multiple plausible predecessor assignments after explicit lineage;
- global geometry-only rematching after Walls are rebuilt without lineage.

One user Wall-chain operation may produce several independent safe components. Reconcile all; commit only if **every** affected component is valid. Any unsupported/ambiguous component rejects the entire user command before state installation.

## Initial Room creation — foundation responsibility

Zero-predecessor faces are handled here in F0, for every topology operation, including closing a Wall chain and changing a closed Partition chain to boundary Walls. P23.9 only calls this operation.

- Prove each new face has no predecessor in its affected correspondence component; a failed match is not permission to create a replacement Room.
- Sort zero-predecessor faces by canonical face key, then allocate collision-free deterministic Room IDs and names against the complete candidate document.
- New Rooms use `floorThickness = 0.1 m` and `ceilingThickness = 0.1 m`, preserving current creation defaults. Split descendants use the split inheritance policy instead.
- Allocate during the authoring transaction only; compilation and rendering never create Rooms.
- Validate all new regions and commit once. Undo/Redo restores exact IDs, names and surface values.

## 1 → 1 preservation

Preserve Room ID when Wall/Junction lineage maps the predecessor boundary unambiguously to exactly one candidate face and no competing predecessor maps to it.

This remains true even if geometric overlap is tiny/zero after a legitimate large rigid deformation. Overlap is secondary evidence, not required for lineage-preserving deformation.

Equal Room count without lineage is insufficient.

## Simple 1 → 2 split

1. prove one predecessor produces exactly two candidate faces in the affected component;
2. prove both are descendants through explicit Wall/Junction lineage;
3. compute predecessor overlap area with each candidate;
4. greatest-overlap child keeps old Room ID;
5. exact tie: use old derived interior witness if it lies strictly inside exactly one candidate;
6. otherwise smallest canonical `faceKey` survives;
7. other child receives deterministic new Room ID allocated after sorting by face key.

### Split metadata

Current target policy:

- survivor retains old Room name;
- new Room receives deterministic default name;
- `floorThickness` duplicates to both;
- `ceilingThickness` duplicates to both;
- Wall thickness belongs to Walls, not Room metadata;
- openings follow hosted Walls and are not copied as Room metadata.

Any future Room metadata must explicitly define a split policy rather than inherit by generic object spread.

## Simple 2 → 1 merge

1. prove exactly two predecessors contribute to one candidate in the affected component;
2. compare predecessor overlap/contribution area;
3. greatest contributor retains Room ID;
4. exact tie uses stable existing Room ID ordering;
5. retired Room ID disappears from the committed new document;
6. field-level metadata policy decides automatic merge versus rejection.

Current fields:

- `name` → survivor name;
- `floorThickness` equal → keep; conflict → reject;
- `ceilingThickness` equal → keep; conflict → reject.

Do not silently choose/average conflicting physical Room surface metadata.

## Room disappearance / open enclosure

Retire Room ID only after candidate-face extraction confirms no enclosed descendant remains.

After P23.0 world-space migration, Scene/Camera content remains physically valid where it was even if no Room contains it.

Before commit, resolve every hard semantic Room reference. Unresolvable reference → reject.

No persistent Room tombstone is required in initial P23 because history snapshots already retain the previous metadata for Undo.

## Layout-object semantic references

`LayoutObject.roomId?` remains an optional explicit semantic association, never containment or transform ownership. Migration preserves valid associations and world transforms. On 1→1 edits/subdivision retain it; on split retain the predecessor ID (the surviving Room), without choosing by object position; on merge remap retired IDs to the surviving Room; on disappearance clear the association. These Layout-only changes are part of the same candidate/history snapshot. Never move or delete an object because its associated Room changes. Unassociated objects stay unassociated; do not infer associations from containment. Validate every remaining reference before commit.

## Portal semantic remapping

For new-schema doors, physical adjacency is derived from the hosting boundary Wall; `connectsRoomIds` is optional explicit semantic inter-Room intent.

P23.8 owns topology-edit remapping:

### Split

If relation contains predecessor Room A and A splits, map that side to the descendant physically adjacent to the opening's Wall side. Do **not** merely pick the child retaining A's ID.

If wall-side lineage gives no unique descendant → reject the topology edit.

### Merge

If a relation endpoint maps into a merged Room and two distinct adjacent semantic endpoints remain, remap.

If both tuple members collapse into the same Room, clear the relation as a planned semantic collapse while preserving the physical door.

### Disappearance

Clear/remap only when explicit topology lineage makes the semantic result unambiguous. Otherwise reject.

Legacy nonadjacent relations are P23.0 compatibility cases and must not be forced through these stricter new-schema rules on read.

## Diagnostics contract

Diagnostics should identify source Wall/Junction/Room IDs where available and be deterministic.

Minimum diagnostic classes:

- zero/tiny Wall;
- non-finite geometry;
- un-noded endpoint-on-interior/proper crossing in installed new data;
- collinear overlap;
- dangle/cut edge preventing intended enclosure;
- invalid/self-intersecting ring;
- unsupported nested/hole topology;
- ambiguous Room correspondence;
- unsupported many↔many component;
- opening-invalidating subdivision;
- metadata merge conflict;
- unresolved portal remap.

Diagnostics are not permission to auto-repair authored topology.

## Transaction/history

Every topology-changing intent follows:

```text
explicit intent
→ plan all Junction/Wall splits
→ construct full candidate graph
→ extract candidate faces
→ reconcile Rooms/metadata/references
→ canonical validation/compile
→ commit once
```

Invalid/cancel/no-op → no history.

Committed snapshot contains exact new Junction/Wall/Opening/Room IDs. Undo/Redo restores snapshots and never reruns matching.

## Selection/query consequences

Wall-first selection targets must key physical architecture by canonical authored identity:

- Junction → `junctionId`;
- Wall → `wallId`;
- Opening → `openingId`;
- Room region → persistent `roomId`.

Subdivision preserves selection on the original-start Wall fragment because the old Wall ID survives there. Newly created IDs enter query/render output after compile.

No stale `(roomId, segmentId)` physical identity may remain after full cutover.

## Tests / fixtures

At minimum:

### classifier / topology

- endpoint touch;
- explicit shared Junction;
- endpoint-on-interior T;
- proper X crossing;
- collinear endpoint touch;
- collinear overlap reject;
- tiny positive gap does not auto-join;
- near-collinear large-coordinate crossing deterministic;
- zero/tiny Wall reject;
- dangle/cut-edge diagnostic;
- self-intersecting/invalid ring diagnostic;
- unsupported nested/hole diagnostic.

### subdivision

- forward and reverse Room boundary rewrite;
- opening before split;
- opening after split;
- split at opening start/end;
- split through opening interior rejects;
- exact Undo/Redo fragment IDs.

### Room identity

- first closed boundary creates a Room with deterministic ID/name and 0.1 m floor/ceiling defaults;
- closed Partition chain changed to boundary creates its first Room through the same foundation operation;
- several independent new faces allocate in canonical order; failed predecessor matching never masquerades as birth;
- object associations retain survivor on split, remap on merge, clear on disappearance, and never change transforms;
- unassociated objects stay unassociated; Undo/Redo restores exact associations and birth metadata;

- large deformation with zero old/new overlap but clear Wall lineage keeps ID;
- equal Room count but swapped/ambiguous lineage rejects;
- asymmetric split;
- exact 50/50 split deterministic;
- valid tiny candidate follows H3 validity, no H5 epsilon;
- unequal merge;
- equal-area merge;
- conflicting floor thickness reject;
- conflicting ceiling thickness reject;
- Room disappearance;
- many↔many component rejects;
- one user operation containing several independent simple components succeeds atomically;
- one valid + one unsupported component rejects whole command.

### portal

- split remaps relation to physically adjacent child;
- merge retains distinct relation when valid;
- merge collapsing both relation endpoints clears relation explicitly;
- ambiguous remap rejects;
- disappearance unambiguous clear/remap;
- legacy nonadjacent relation is not processed as a new-schema topology edit fixture.

## Non-goals

- general polygon Boolean kernel;
- general GIS conflation assignment solver;
- persistent B-rep naming framework;
- proximity auto-merge/repair;
- arbitrary nested islands/holes;
- curved-wall intersection topology beyond legacy compatibility;
- multi-floor topology;
- persistent constraints;
- renderer-owned topology.
