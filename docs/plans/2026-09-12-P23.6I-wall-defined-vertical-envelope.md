# P23.6I — Wall-defined vertical envelope

**Parent:** [P23 Layout Depth — minimum useful Build set](2026-09-07-P23-layout-depth-minimum-build.md).

**Placement:** after the P23.6H implementation work and **before PR #25 merges as
the canonical format-5 cutover**, and before P23.6a / P23.6b. P23.6I is a
**forward amendment to P23.6H**, not a new schema generation: H and I together
are the single vertical-model cutover that reaches `main` as format 5.

**Status:** `implementation-ready`.

**Depends on:** P23.6 canonical Wall selection + Inspector; **P23.6H**
(authoritative `LayoutWall.height`, host-Wall Opening fit, mesh parity, exact
Height planner + history); P23.0/P23.8 wall-first schema, compiler and Room
reconciliation; P23.9 segment-first continuous Wall/Partition authoring.

**Blocks:** P23.6a (Room Unit Move); P23.6b (architecture hierarchy + Inspector
reconciliation); P23.7 (integration closeout).

**Supersedes:** the earlier P23.6I proposal memo (deleted; git history preserves
it) and, before merge, the specific P23.6H decisions listed in
§Relationship to P23.6H.

**Not implemented yet.** This plan authorises the work; no code, schema, fixture
or renderer change is part of the planning pass that produced it.

---

## Why this slice exists

P23.6H correctly made `LayoutWall.height` the authoritative physical height of a
Wall, and moved Wall extent, Opening fit, mesh parity and Height editing onto the
canonical path. It deliberately retained `floor.height` as four things at once:

1. a hard upper bound on `LayoutWall.height` (`0 < height <= floor.height`);
2. the Wall birth default;
3. the source of the Room ceiling elevation (`floor.elevation + floor.height`);
4. the compiled Floor/storey extent (`CompiledFloor.height`).

Reviewing the result surfaced two problems.

**First, the bound is effectively immutable.** Wall-first documents have no
Floor-height editor anywhere: the only `Floor height (m)` inputs in the app sit
on the **legacy Room-owned** Inspector panels (`EditorInspector.svelte`,
`selectedLayoutFloor`, derived through `project.layout.floors`), and their handler
ends in `updateLayoutRoomFields()` → `floors[…].height`. A wall-first document has
no `floors` array, so that input never renders and `floor.height` can only arrive
from the new-project boot, legacy migration or import. A creator therefore cannot
author a Wall taller than the storey, and cannot raise the storey either.

**Second, retaining it keeps a storey-first vertical authority inside the
canonical model.** That is exactly the Room-first residue P23 has spent ten
slices retiring: the enclosure should be defined by its Walls, not by a
document-wide number.

P23.6I completes the cutover:

```text
legacy storey height
    ↓ migration only (one conversion, then it is gone)
per-Wall height
    ↓
canonical physical Walls
    ↓
derived flat Room ceiling
```

Because PR #25 is unmerged, format 5 has **not** become a released canonical
contract. P23.6I therefore does not invent format 6 or 7 and does not preserve
H's Floor-capped semantics as a persisted generation; it replaces those semantics
before the format-5 contract reaches `main`.

## Product outcome

A creator can author, in one canonical model:

- a 1.2 m display Wall;
- an ordinary ~3 m boundary Wall;
- a 4 m or taller Wall;
- adjacent Rooms whose derived ceilings differ;
- a freestanding Wall taller than the Rooms near it.

No global storey height blocks any of it, and no Floor-height control is needed or
added. Plan stays X/Z authoring: Height is exact Inspector authoring that appears
in 3D, never a Plan Y gesture.

## Approved semantic decisions

### D1 — `LayoutWall.height` is the sole Wall vertical authority

```text
finite
strictly > 0
no global upper bound

bottomY = floor.elevation
topY    = floor.elevation + wall.height
```

`WALL_HEIGHT_EPSILON` remains, used only for equality/derivation comparisons and
the Opening-fit boundary — never as a cap tolerance. Opening fit stays host-Wall
based:

```text
opening.sillHeight + opening.height
  <= hostingWall.height + epsilon
```

No clamping anywhere: a violating value rejects.

### D2 — the canonical Floor carries elevation, not height

```ts
type LayoutWallFirstFloor = {
  id: string;
  name: string;
  elevation: number;
};
```

`floor.elevation` stays authoritative for Wall bottoms and the Room floor plane.
`floor.height` is absent from the current canonical schema, and **no replacement
Floor-level vertical scalar is introduced** (see D8).

### D3 — one format cutover: 4 → 5, no intermediate generations

```text
version 4:
    pre-H wall-first
    stored wall.height is NOT authoritative
    source floor.height present

decode 4 (the only v4 → v5 boundary):
    validate under the historical rule set
    every wall.height := source floor.height
    drop floor.height
    formatVersion := 5

version 5:
    final current format
    Wall height finite and unbounded
    floor.height key forbidden (unknown_key)
    Room ceiling is Wall-derived
```

`LAYOUT_WALL_FIRST_FORMAT_VERSION = 5` (unchanged) and
`KNOWN_LAYOUT_FORMAT_VERSIONS = [4, 5]` (unchanged). **There is no canonical
format 6 or 7**, no `[4, 5, 6, 7]` ladder, and no compatibility burden for
branch-only H-format fixtures.

Why one cutover is correct: a format-5 document produced *before* I — e.g.
`floor.height = 3` with boundary Wall heights `[1.2, 1.2, 1.2, 1.2]`, whose H
ceiling was 3 — would silently change meaning (ceiling 1.2) if a later decoder
advanced it to Wall-derived semantics without rewriting it. A version bump on the
new writer cannot preserve the meaning of an already-persisted payload. Since no
such payload exists on `main`, the burden is avoided entirely rather than managed.

The v4 normalization above preserves the previously visible vertical result
exactly, because pre-H rendering already used `floor.height` as the Wall top. It
is a **deliberate field rewrite at the compatible read boundary** (the one place
H already sanctioned normalization), and it replaces H's "rewrite nothing" choice
for v4 because the field it relied on no longer exists.

### D4 — legacy Room-owned migration

Legacy documents keep their own `floors[].height` semantics on their
compatibility path; nothing about the legacy read/write shape changes.

Lossless legacy → wall-first migration:

```text
legacy floor.height    → each produced canonical Wall.height
legacy floor.elevation → canonical floor.elevation
canonical floor        → { id, name, elevation }   // no height key
```

The legacy storey value has completed its conversion job and does not survive as
canonical wall-first truth. All existing migration behaviour is otherwise
unchanged: multi-floor rejection, curve/arc handling, portal/adjacency rules,
conflict rejection and deterministic IDs.

### D5 — Wall creation: one named default plus explicit run state

One canonical creation constant:

```ts
export const WALL_AUTHORING_DEFAULT_HEIGHT = 3;
```

It is a **creation default only** — not an architectural envelope, not a
validation cap, not a Room height, not a Floor height, and nothing but the initial
value of a newly authored Wall. It is the only Wall-birth literal allowed
anywhere.

**No inference from arbitrary Junction topology.** A Junction can carry several
incident Walls with different heights, so a generic "incident Wall" rule would
make creation depend on topology order. The rule is explicit, deterministic and
run-scoped:

```text
explicit requested height
    → requested height

continuing the current Wall/Partition draw run
    → wallChainRunHeight

first segment of a new run, starting on an existing Junction:
    exactly one unique height among the incident Walls at that Junction
        → inherit it
    zero incident Walls
        → WALL_AUTHORING_DEFAULT_HEIGHT
    more than one distinct incident height
        → WALL_AUTHORING_DEFAULT_HEIGHT

isolated new start (no existing Junction)
    → WALL_AUTHORING_DEFAULT_HEIGHT
```

After the first segment of a run commits successfully:

```text
wallChainRunHeight = the committed authored Wall height
```

Every later segment of that run inherits it, including turns, so one continuous
perimeter draw stays vertically coherent. `Escape`, closure, tool switch, cancel,
document reset, Undo/Redo-driven replacement and the other existing run-reset
paths must clear `wallChainRunHeight` together with the rest of the Wall-run
state. Continuation is never inferred from selection or from coordinates alone,
and a mixed-height Junction never silently resolves to the lower or higher Wall.

**Layering (explicit, so editor policy is not hidden in geometry code):**

```text
core planner (`planWallChain` / `planWallSegment`):
    keeps accepting an explicit `height`; resolves
    `options.height ?? WALL_AUTHORING_DEFAULT_HEIGHT`
    — it must NOT inspect mutable UI/session state

editor continuous-run adapter (`layout-interaction.ts` → viewport → `commitWallSegment`):
    owns `wallChainRunHeight`, resolves run inheritance / start-Junction seed /
    default, and passes the resolved height into the planner explicitly
```

**Bounded compound tools.** Rectangle and Polygon remain bounded compound
commands: for the generated chain they use an explicit height override **or**
`WALL_AUTHORING_DEFAULT_HEIGHT`, uniformly for the whole command. No per-leg
inheritance inside one Rectangle/Polygon gesture.

**Unchanged inheritance:** Wall split (`planWallSplitAtPoint`) and isolated-Room
duplicate (`planDuplicateIsolatedRoom`) keep copying the source Wall height
exactly.

### D6 — derived flat Room ceiling

For every canonical Room whose boundary Walls resolve:

```ts
roomHeight      = max(room.boundary.map(ref => wallById(ref.wallId).height))
ceilingElevation = floor.elevation + roomHeight
```

Computed once in the wall-first compiler adapter and fed into the existing shared
Room compile path. No `floor.height` fallback. No document-wide Wall max for a
normal Room.

### D7 — degenerate Rooms reject; they never acquire an invented ceiling

An empty or unresolved Room boundary is invalid canonical state, not an
architectural case:

- prevent it where it can be prevented — the codec must reject a wall-first Room
  whose `boundary` declares no Wall reference (add a named codec rule only if the
  current codec permits it; record the verified behaviour in the implementation
  note);
- if an internal candidate can still present a Room whose boundary Walls do not
  resolve, the compiler emits an explicit blocking issue (proposed code
  `room_ceiling_undefined`) — it must **not** manufacture a ceiling from
  `document max Wall height` or `WALL_AUTHORING_DEFAULT_HEIGHT`.

Creation defaults belong to authoring. They are never geometry recovery.

### D8 — no Floor-level envelope authority

`CompiledFloor.height` is removed. `CompiledFloor` keeps its identity
(`id`/`cacheKey`), `floorId`, `elevation`, `roomIds` and `bounds3`.

**Do not** replace it with `Floor envelope = max(Room envelopes)`. Wall-first
permits physical Walls without Rooms, so a room-only maximum would under-report
real architecture. Aggregate spatial extent stays where it already is: compiled
physical Wall bounds, Room floor/ceiling bounds (`roomBounds3`), LayoutObject
bounds and the existing aggregate `CompiledFloor.bounds3` /
`CompiledLayoutGeometry.bounds` (which already expand over canonical physical
Walls so roomless Walls are included).

Every consumer of the removed scalar must be migrated to the datum it actually
needs:

```text
needs a Wall top            → CompiledPhysicalWall.height / bounds3
needs a Room ceiling        → CompiledRoom.ceilingElevation
needs the Floor base        → CompiledFloor.elevation
needs aggregate extent      → bounds3 / CompiledLayoutGeometry.bounds
```

### D9 — topology purity

Wall height remains outside face extraction. A height change must not create,
retire, split or merge Rooms, must not alter Junction connectivity or Wall
`role`, and must not change Wall, Junction, Opening or Room identity. P23.6a later
moves Rooms while preserving Wall heights exactly.

### D10 — compatibility and publication isolation

Stored format-4 publications remain immutable bytes; the visitor cold runtime
continues through compatible project/Layout decode before any canonical compile;
there is no visitor-specific normalization branch. A canonical Save after a
compatible load writes format 5. Canonical writers keep failing closed on a raw
pre-H payload — the writer rules H shipped (`serializeWallFirstLayoutDocument`,
`validateWallFirstProject`, `wallFirstCanonicalProjectFormatIssue` in
`serializeProject`, and the editor session handoff) stay in force, with the
current-format value unchanged at 5.

### D11 — a flat ceiling is not watertight-volume semantics

```text
boundary Wall heights = [4, 2, 2, 2]
→ Room ceiling plane at 4
→ the three 2 m Walls stay physically 2 m
→ the vertical band above them is intentional under this minimum model
```

Name the semantics accurately everywhere: a **derived flat Room ceiling plane**.
This slice does not infer wall-top infill, stepped ceilings, sloped ceilings,
per-edge ceiling profiles, watertight 3D volumes or multi-storey Walls.

## Authority boundaries

- `LayoutDocument` owns canonical architecture; `SceneDocument` is untouched.
- `floor.elevation` and `wall.height` are the only Layout vertical authorities.
- One `compileLayoutGeometry()` path feeds Plan, editor 3D, museum and visitor.
- One Room reconciliation path; no second geometry truth.
- No hit-testing, selection, gizmo or Camera changes.
- One Layout history system (`layoutMutationRunnerFor` + guarded transactions).
- Editor and visitor consume compiled output; no renderer derives a Room ceiling
  or Wall top from source document fields, and no `{ elevation: 0, height: 3 }`
  compatibility fallback survives in a canonical renderer path.
- Plan remains X/Z authoring: no Y gesture is added.

## Implementation stages

One plan, one format bump (none — the version stays 5), ordered internal stages.

### I1 — schema + compatibility contract

- `LayoutWallFirstFloor` loses `height`; `FLOOR_KEYS` becomes version-aware:
  `height` is accepted for declaring version 4 and **forbidden** for version 5.
- `parseFloor` for v4 keeps reading the historical `height`; the v4 decode path
  normalizes `wall.height := floor.height` and drops `floor.height`
  (`normalizePreHWallFirstLayout` becomes the v4 → v5 shape conversion),
  returning a v5 document (keeping the additive `migratedFromVersion: 4`).
- The v5 branch performs no normalization and rejects a present `floor.height`
  as `unknown_key`.
- `createEmptyWallFirstLayoutDocument()` emits the final v5 Floor.
- Canonical writers keep their current gates (current-format value unchanged);
  migration emits final v5 directly.

**Acceptance:** v4 with `floor.height = 4` and historical Wall `height = 3`
decodes as v5 with every Wall `height = 4` and no `floor.height`; a v5 payload
containing `floor.height` rejects with `unknown_key`; a raw v4 payload still
rejects at every canonical writer; v4 compatible decode → canonical write
succeeds at v5; legacy migration preserves the previously visible extent.

### I2 — unbounded Wall validation

- Rule becomes `0 < wall.height` (finite, strictly positive).
- Remove `wall_height_exceeds_floor`, the Floor-envelope messages, the
  `planExactWallHeight` cap check, `canonicalWallBirthHeight(floor)` and the
  `invalid_floor_height` Wall-birth rejection; `WALL_CHAIN_DEFAULTS` keeps only
  thickness.
- Keep finite/positive validation and the shared epsilon.

**Acceptance:** a 6 m Wall validates; zero/negative/NaN/infinity reject; a 6 m
Wall with a fitting Opening compiles; lowering a Wall below a hosted Opening's
top still rejects atomically.

### I3 — creation semantics

- Add `WALL_AUTHORING_DEFAULT_HEIGHT` (the only Wall-birth literal).
- Add `wallChainRunHeight` to the existing continuous Wall/Partition state in
  `layout-interaction.ts`, with the D5 lifecycle: seed from a unique start-Junction
  incident height or the default, persist across turns within a run, clear on every
  existing run-end/cancel/reset path.
- Thread the resolved height explicitly from the viewport/patch layer into
  `commitWallSegment` / `commitWallChain` and from there into the core planner;
  the planner keeps accepting `options.height ?? WALL_AUTHORING_DEFAULT_HEIGHT`.
- Rectangle/Polygon (`commitWallChain` with `close: true`) stay uniform.

**Acceptance (tests named in the test plan):** isolated run → default; start on a
single 4 m incident Wall → 4 m; start on `[4, 4]` → 4 m; start on mixed `[4, 2]` →
default; later segments inherit through turns; Escape/new run does not leak the
previous height; closure clears it; Undo/Redo never depends on stale tool state;
Rectangle/Polygon uniform; split/duplicate preserve the source height.

### I4 — compiler Room ceiling

- The wall-first adapter derives each Room's `max(boundary Wall heights)` once and
  passes it as an explicit per-room derived ceiling into the shared Room compile
  path (the existing optional-`CompilerRoomSource` pattern, so the legacy source —
  which passes nothing — stays byte-identical).
- `compileRoom` uses the derived value for `ceilingElevation`, Room wall
  `bounds3` and room bounds; physical Walls keep compiling independently and
  exactly once.
- Degenerate Room boundaries produce a blocking issue per D7.

**Acceptance:** all-3 m boundary → ceiling 3; all-1.2 m → ceiling 1.2;
`[4, 2, 2, 2]` → ceiling 4 with the 2 m Walls' bounds still 2; adjacent Rooms
derive different ceilings; a shared Wall participates in each Room's max; a pure
height edit re-derives the ceiling with no topology or identity change.

### I5 — remove compiled Floor height and migrate its consumers

- Remove `CompiledFloor.height`; the Floor record's `cacheKey` drops it and keys
  on the values that remain (id, elevation, roomIds, bounds3).
- Migrate every consumer per D8 (shells' floor frames, `buildWallMeshesByRoom`,
  benches, tests).
- Delete any `{ elevation: 0, height: 3 }`-style Floor fallback from canonical
  renderer paths; the only sanctioned 3 m literal is
  `WALL_AUTHORING_DEFAULT_HEIGHT` on the authoring path.
- Both museum shells and the visitor shell must consume the same compiled result
  (`CompiledRoom.ceilingElevation`, `CompiledPhysicalWall`), with no independent
  re-derivation.

**Acceptance:** `CompiledFloor` has no `height`; floors still appear with correct
`elevation`/`roomIds`/`bounds3`; roomless physical Walls still contribute to
aggregate bounds; editor and visitor render identical vertical geometry for the
same document.

### I6 — Inspector / exact editing

- Keep P23.6H's canonical `Height (m)` control and `updateWallFirstWallHeight`.
- Remove only the Floor-envelope constraint; the planner's rejection message for a
  value that breaks a hosted Opening still surfaces through the existing status
  path.
- Add no Floor-height input for wall-first; the legacy Inspector controls stay
  legacy-only and unchanged.

**Acceptance:** 6 m accepted through the Inspector with one history entry; a value
that breaks a hosted Opening rejects atomically with the input restored; no
wall-first Floor-height control exists.

### I7 — tests, parity and migration proof

- Reconcile the P23.6H tests that intentionally pinned Floor-derived Room
  envelopes: **replace, do not delete** — each becomes an explicit supersession
  test asserting the new semantics (notably `p23-6h-wall-height.test.ts` →
  "does not lower the Room ceiling, the Floor envelope or the Room bounds" and its
  suite-header claim).
- Keep H's topology-purity, Opening-fit, history, mesh-parity and writer
  fail-closed coverage.
- Add the new suites listed below and keep the legacy golden/parity output
  byte-identical.

## Migration acceptance matrix

| Input | Read result | Vertical preservation | Canonical write |
|---|---|---|---|
| legacy Room-owned Layout | legacy-compatible or migrated by the existing project policy | legacy path unchanged; migration births Walls from legacy `floor.height` | migrated wall-first writes v5 |
| wall-first v4 | normalize once at the compatible boundary | every Wall gets the old visible `floor.height` | v5 |
| wall-first v5 (final) | direct | Wall height authoritative; Room ceiling derived | v5 |
| unknown format version | reject by name | none | none |
| raw v4 sent to a canonical writer | reject by name | none | none |

## Mutation / history behavior

- One successful Height edit → exactly one Layout history entry through the
  existing guarded transaction; Undo/Redo restore the exact previous height and
  the recompiled ceiling/geometry.
- Rejected edits (unknown Wall, non-finite, non-positive, Opening-invalidating),
  blank input and no-ops write zero entries.
- Wall creation commits stay one entry per segment/chain as today; the run-height
  state is editor state and never enters history.

## Failure / rejection behavior

| Condition | Result |
|---|---|
| Wall not found | reject `unknown_wall`, message names the ID |
| non-finite / ≤ 0 / blank | reject (planner for non-finite, presentation for blank) |
| hosted Opening no longer fits | reject atomically; Wall, Opening and history unchanged |
| candidate fails codec/topology/compile | reject; no mutation, no history |
| Room boundary empty / unresolved | reject at the codec, or compiler blocking issue `room_ceiling_undefined` — never a manufactured ceiling |
| raw pre-H payload at a canonical writer | reject `unsupported_format_version` |
| v5 payload declaring `floor.height` | reject `unknown_key` |

## Compatibility / migration consequences

- **Format:** unchanged at 5. v4 stays compatible-read only. No v6/v7 symbol,
  fixture, doc or comment may exist.
- **Mutable projects:** a v4 project becomes a v5 document in memory; the next
  Save writes v5 with `wall.height = floor.height` on Walls that differed and no
  `floor.height` key.
- **Immutable publications:** stored bytes are never rewritten; the visitor cold
  path normalizes in memory before canonical compile, and `decodeKind` stays
  `wall-first`.
- **Migration:** legacy output is v5 directly, with migrated Wall heights equal to
  the legacy storey height and no canonical Floor height.
- **Writers:** the fail-closed current-format rules H shipped stay in force; the
  gate's expected value is still 5.
- **API publication:** the publish/compile path remains P23.7's; this slice does
  not change `apps/api`.

## Deterministic identity requirements

- Wall/Junction/Opening/Room IDs are never affected by a height edit, by the v4
  normalization, or by the derived ceiling.
- No allocation occurs during a height edit or during a compatible decode.
- The v4 → v5 conversion is a pure, order-preserving field rewrite (no ID or
  ordering change), so Save diffs and history baselines stay comparable.
- Room ceiling derivation is a deterministic `max` over the resolved boundary
  cycle, independent of boundary traversal order or Wall document order.

## Acceptance gate

P23.6I is complete only when all are true:

1. the current wall-first Floor type has no `height`;
2. the only canonical current format is 5;
3. format 4 remains compatible-read only;
4. no v6/v7 symbol, fixture, comment or doc exists;
5. no Wall-height cap exists anywhere;
6. `WALL_AUTHORING_DEFAULT_HEIGHT` is the only authoring 3 m Wall default;
7. continuous runs inherit deterministically with no arbitrary incident-Wall choice;
8. Opening fit is host-Wall based and unchanged;
9. a Room ceiling equals `floor.elevation + max(boundary Wall heights)`;
10. a mixed-height Room renders a flat ceiling at the max with the shorter Walls unchanged;
11. no compiler fallback manufactures a ceiling for malformed Room topology;
12. `CompiledFloor.height` is removed;
13. canonical Floor/document aggregate bounds still include roomless physical Walls;
14. pure height edits preserve topology, Room identity and geometry identity;
15. legacy compilation and golden output are unchanged;
16. a v4 document's visible vertical result is preserved through normalization;
17. editor and visitor render the same compiled vertical geometry;
18. Undo/Redo is deterministic and independent of tool state;
19. `SceneDocument` is untouched;
20. Plan gains no Y authoring affordance;
21. the full existing verification set stays green (editor suite, both apps'
    `svelte-check`, `layout-core`/`project-model` typechecks, API tests, museum
    visitor-bundle verification).
