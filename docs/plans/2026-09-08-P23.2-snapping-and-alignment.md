**Status:** implemented on `p23.2` — Foundation Gate F0 closed 2026-09-10; foundations (snap resolver, alignment planner, grid-step centralization) plus editor wiring (Plan drag/draft paths with moving-target exclusion incl. opening drag, session-only guides, Inspector one-object→one-reference align actions) are complete with the full gate green, pending owner review. Review round 1 applied (committed `323af7f`): typed-owner snap exclusion, negative-slope-safe wall-span merge, collision-safe `kind:id` align reference keys, offset-space opening-drag resolver. Review round 2 applied (committed `53a5e5b`): compiled `wallKey` wall identity (legacy room-qualified), curved-wall nearest-point semantics without chord/midpoint invention, and intersection self-exclusion via pre-classification filtering. Review round 3 applied (uncommitted): collision-safe wall identity via `geometryId` length-prefixed tuples (delimiter joining collides — `:` is legal inside ids), typed `snapOwnerKey({kind, id})` ownership on every candidate family incl. junction points (object/wall/opening ids can never suppress each other, and moving one legacy room's `wall-1` never suppresses another room's `wall-1`), and a genuinely relative straightness tolerance (1e-6 × wall length).  
**Evidence:** P23-H2 complete; wall-first reconciliation ratified 2026-09-09.

## Outcome

Plan snapping becomes predictable, zoom-stable and semantically clear for wall-first architecture without becoming topology authority or a persistent constraint system.

## Canonical source

Snap candidates derive from:

- `CompiledLayoutGeometry.queries` / evolved canonical compiled query records;
- transient gesture/draft context such as active anchor, projected extension or orthogonal guide.

Plan/SVG code must not independently reconstruct authored geometry for snap truth.

## Grid step

Centralize one effective Layout Plan grid step.

- current default remains 0.25 m unless implementation evidence changes it;
- finite positive values only;
- route the selected step through affected Layout placement/translation/drafting callers;
- grid drawing and grid snap use the same configured step where semantically appropriate;
- Camera Plan behavior does not change merely because helpers are shared.

## Reference acquisition

Use a fixed CSS-pixel acquisition radius converted by Plan scale.

H2 recommends **8 CSS px** as the initial centralized/testable default.

```text
worldRadius = snapRadiusCssPx / pixelsPerWorldUnit
```

Pointer acquisition tolerance is not geometry/topology tolerance. H3 remains authority for robust authored-geometry classification.

## Wall-first candidate vocabulary

Supported candidate families may include:

- Junction / Wall endpoint;
- straight-Wall midpoint;
- valid Wall intersection;
- nearest point on Wall/reference span;
- Opening edge;
- rotation-aware Layout object bounds edge/center;
- Room-region/reference bounds where a tool explicitly needs them;
- orthogonal guide relative to active anchor;
- bounded extension relation;
- parallel/perpendicular or angle aids where explicitly scoped;
- grid fallback.

Do not add persistent snap points to `LayoutDocument`.

## Deterministic winner order

Keep the accepted H2 order:

```text
tool/context validity
→ semantic feature priority
→ screen distance
→ stable ID/key
```

A valid acquired semantic reference beats grid. Never use source-array/render order as a hidden tie-break.

The exact semantic-rank table must be centralized/tested per tool context rather than implied by call order.

## Snap is not topology

This is a hard wall-first rule.

```text
pointer is near Junction
→ snap candidate only

user commits endpoint on that Junction
→ authoring operation explicitly reuses Junction ID
```

Likewise:

```text
endpoint snaps to Wall interior
→ committed operation invokes P23.8 Wall subdivision
→ explicit Junction ID is written
```

A snap marker never itself creates connectivity, splits a Wall, changes Room identity or writes history.

## Moving-target exclusion

Exclude the active moving target and any geometry that would create self-snapping loops.

Examples:

- moving Junction does not snap to its own current query point;
- moving Wall/chain excludes its own draft/owned spans where necessary;
- moving Layout object excludes its own footprint bounds;
- opening drag excludes the opening's own edges as external reference candidates.

Tool-specific exclusion is explicit and deterministic.

## Transient guides / markers

Snap feedback is session state only.

Clear on:

- Snap off;
- Escape/cancel;
- pointer cancel/loss;
- tool change;
- Layout↔Arrange authority change;
- Plan↔3D switch;
- commit;
- invalidated/deleted reference.

No history/document JSON changes arise from showing/clearing guides.

P23.6 owns polished visual treatment; P23.2 owns the semantic result data.

## Orthogonal / extension aids

Treat relation guides separately from target geometry.

An orthogonal/extension candidate may depend on the active draft anchor and a referenced Wall/Junction, but the final snap result remains one deterministic coordinate + stable source IDs.

No persistent horizontal/vertical/parallel/perpendicular constraint survives after commit.

## Alignment

Keep alignment narrower than general CAD tools:

> one selected supported Layout object → one explicit reference.

References may include:

- another supported Layout object's canonical world/compiled bounds;
- a Room-region compiled bounds reference where useful;
- a selected straight Wall.

Actions:

- X/Z min/center/max alignment for bounds references;
- bounded **Center on Wall** action using canonical compiled Wall/query geometry.

Preserve selected object's Y, rotation, dimensions and document-level ownership. No-op adds no history.

Reference picking must not change canonical selection merely to use a reference.

## Interaction authority

Snapping does not create a second selection resolver.

- selection stays on existing canonical Layout/Arrange authority adapted by F0;
- snap source emphasis/hover is transient;
- Inspector reference picking preserves active selection;
- P23.9 draft state consumes snap results but does not own a separate hit-test geometry model.

## Tests

- non-default grid step reaches every affected Layout caller;
- reference radius is zoom-stable at 50%/100%/200%;
- equal-distance ties resolve by semantic rank/stable key, not iteration order;
- Junction/end/midpoint/intersection/nearest-span/opening-edge fixtures resolve deterministically;
- endpoint-on-Wall snap does not mutate until commit, then invokes one P23.8 subdivision;
- merely hovering/snapping never creates Junction connectivity;
- moving targets excluded;
- guides clear on every cancellation/authority transition;
- snap-off disables reference+grid snapping according to existing toggle semantics;
- rotated object bounds alignment reaches requested target;
- Center-on-Wall uses canonical Wall query geometry;
- no-op alignment produces no history;
- Camera Plan snapping remains unchanged unless separately planned.

## Implementation notes (2026-09-10)

- Foundations: `packages/layout-core/src/layout-snap.ts` (deterministic resolver, 0.25 m `LAYOUT_PLAN_GRID_STEP`, 8 CSS-px zoom-stable acquisition, per-family candidate builders over compiled query geometry) and `layout-align.ts` (pure `planLayoutObjectAlign`, `no_op` rejection means no history). Coverage: `apps/editor/tests/lib/layout/p23-2-snap.test.ts` (38) + `p23-2-align.test.ts` (18).
- Grid step: every former hardcoded 0.25 site routes through `LAYOUT_PLAN_GRID_STEP` — `snapToGrid`/`buildPlanGrid` defaults, the `* 4) / 4` form in `updateLayoutObjectDrag`, `snapLayoutPlanPoint`, `LAYOUT_OPENING_SNAP`, and the Inspector/StatusBar/LayoutDraftToolbar labels. Camera Plan keeps plain `snapToGrid` (step identity only).
- Editor wiring: `LayoutPlanViewport.svelte` resolves snaps via `applyLayoutSnap` over `preview.geometry` on draft/drag paths (object drag, wall-bend acquisition, opening click, vertex/room edit, polygon click) with explicit exclusions (dragged object/segment IDs, the moving vertex's own point) and renders session-only `snap-guide`/`snap-marker` primitives through `withLayoutSnapFeedback` (muted token for the grid fallback). Endpoint-on-wall commits continue through the existing `insertLayoutWallInteriorAnchor` P23.8 subdivision path.
- Moving-target exclusion keys on a typed `ownerId` (object/segment/opening ID), never on composite `sourceId`s like `obj#0:mid` or `wall#start` — a dragging object/wall cannot snap to its own bounds edges/endpoints. Opening drag resolves in offset space through `resolveOpeningDragSnap` (host-wall junctions, midpoint, other openings' edges on the same wall, grid fallback); the dragged opening's own spans are skipped so its own edges can never be external reference candidates, and the grid candidate snaps the opening center exactly like opening creation. Curved (auto-bezier) segments keep the legacy linear grid snap.
- Wall identity: the compiler stamps every wall/opening query span and every wall-bound query point with a `wallKey` — the document-global segment id for wall-first, `geometryId([floorId, roomId, segmentId])` (length-prefixed, collision-safe) for legacy since segment ids are only unique per room and `:` is legal inside ids. `dedupeWallSpans`, the align wall reference lookup, and the opening-drag same-wall filter all key on `wallKey`, so same-named segments of different legacy rooms can never collapse into one fake wall while shared wall-first walls still merge across rooms (compiler + consumer regression tests on both formats, incl. a naive-join collision fixture).
- Owner identity: every snap candidate carries a typed, collision-safe owner key — `snapOwnerKey({kind: 'object'|'wall'|'opening', id})` where wall owners use the qualified `wallKey`. The viewport sends the same encodings (`snapOwnerKey` for objects, `wallOwnerKey(geometry, roomId, segmentId)` for wall bend/anchor drags), so an object `foo`, wall `foo`, and opening `foo` never suppress each other and moving one legacy room's `wall-1` never suppresses another room's independent `wall-1` (cross-kind and cross-room exclusion tests).
- Wall span merging: `dedupeWallSpans` derives the **farthest true endpoint pair** of every compiled span (lexicographic tie-break), so negative-slope walls `(0,4) → (4,0)` never collapse to a bounding-box anti-diagonal and reversed shared-wall traversal across rooms merges to the authored extent. Straightness is detected geometrically — every sample endpoint within a **relative** perpendicular tolerance of 1e-6 × wall length from the chord line (path-length comparison would double-count shared-wall resampling; the cross product is compared against chord² × 1e-6, not chord × 1e-6). Curved (auto-bezier) walls keep their per-sample spans and snap via nearest-point only: no invented straight midpoint or chord semantics, and Center on Wall rejects curved references while bounds actions still resolve from the sample AABB. Covered by negative-slope + reversed-shared-wall + curved-wall tests in both snap and align suites.
- Intersection self-exclusion: intersection owners are composite (`a~b`) and can never exact-match a bare moving-target id, so walls owned by the moving target are removed **before** intersection classification.
- Align reference identity: Inspector options and lookups bind the collision-safe `kind:id` key (`alignReferenceKey`) — an object `foo` and a wall `foo` can legally coexist and resolve independently.
- Clear rules honored: snap off, Escape, pointer cancel/leave, tool change, Layout↔Arrange authority change, Plan↔3D switch, commit — all drop feedback without document or history changes.
- Inspector: one-object→one-reference Align fieldset (X/Z min/center/max + Center on Wall for wall references) through `planLayoutObjectAlign` + the existing one-transaction mutation runner; reference picking never changes canonical selection.

## Non-goals

- persistent constraints;
- multi-selection alignment/distribution;
- full LibreCAD snap family;
- tangency/normal/curve CAD constraints;
- snap-driven automatic topology repair;
- spatial index until measured project-size evidence requires one;
- a new Plan selection/hit system.
