# P23.3 — Wall-hosted openings that fit

**Parent:** [P23 — Layout Depth umbrella](2026-09-07-P23-layout-depth-minimum-build.md)  
**Status:** `implementation-ready` — main P23.3 implementation unblocked; P23.8 split-side portal-remap correction is a required prerequisite for the split-remap acceptance gate. Foundation Gate F0 closed (`32b2e8f`); P23.1 merged (`d5ec0df`, PR #9); P23.2 merged (`a369a15`, PR #13); **P23.9 merged (`5f20aaa`, PR #18)**. Reconciled against `main@5f20aaa` (2026-09-11) before coding; owner review amendments applied after reconciliation (drag snap/raw-validity, status/ordering, selection shape, validator ownership).
**Evidence:** P23-H1 + H5 complete; wall-first reconciliation ratified 2026-09-09; P23.9 segment-first amendment ratified 2026-09-11.

## Outcome

Doors and windows are edited as one physical Opening hosted by one canonical Wall. Direct manipulation, numeric editing and portal semantics all operate on the same authored record.

## Canonical authored model

```text
Opening
└─ wallId
```

Retain the strongest existing semantics:

- `offset` is physical meters from canonical Wall start;
- `width`, `height`, `sillHeight`, `kind`, `profile` remain explicit;
- overflow/overlap/vertical-fit errors reject rather than clamp;
- a completed gesture/Apply produces one Layout history result;
- invalid/cancelled/no-op produces none.

The old model `Opening → Room-owned segment` is legacy compatibility only after F0.

## Numeric helpers

Expose:

- Wall length;
- opening start offset;
- width;
- remaining clearances to both Wall ends;
- **Center on Wall**;
- distance-from-start / distance-from-end helpers that resolve back to canonical `offset`.

Do not migrate to normalized `[0,1]` offsets.

## Direct Plan manipulation

Straight Walls only for the minimum.

### Body drag

Dragging the opening body slides it along its hosting Wall.

Preserve unless directly edited:

- Opening ID;
- Wall host ID;
- width;
- height;
- sill;
- profile;
- semantic portal relation.

### Width handles

Left/right handles resize along canonical Wall direction while keeping the appropriate opposite edge fixed according to the interaction contract.

Transient preview uses the immutable gesture baseline. Pointer-up validates/commits once. Escape/pointer cancel restores baseline with no history.

## Fit validation

Validate the complete hosting-Wall opening set, not only the edited record in isolation.

At minimum:

- finite positive dimensions;
- `0 <= offset`;
- `offset + width <= wallLength`;
- valid sill/height relative to Wall/floor vertical semantics;
- no unsupported opening interval overlap on the same Wall;
- no invalid subdivision/host reference;
- compatible profile/kind fields.

No silent clamp or nearest-valid fallback.

## Shared Walls

A Wall between two Rooms hosts **one** physical Opening and produces one canonical compiler cut.

Do not duplicate the Opening per adjacent Room.

Room-side context needed for Plan/3D/portal behavior is derived from the hosting Wall's accepted topology.

## Physical adjacency versus semantic portal intent

These are separate:

```text
Wall-side topology
→ physical adjacent Room(s)

door.connectsRoomIds?
→ explicit semantic inter-Room portal intent
```

For new-schema `connectsRoomIds`:

1. only a `door` may define it;
2. tuple contains two distinct persistent Room IDs;
3. the two Rooms must be the two physical Rooms adjacent to the hosting **boundary Wall at the opening**;
4. the relation never creates adjacency by itself.

A door may omit the relation.

Exterior doors and doors on `partition` Walls normally do not have a two-Room relation.

## Portal editing UI

If P23.3 exposes a portal relation picker:

- candidate Rooms come from the actual accepted Wall-side topology;
- do not present arbitrary nonadjacent Room IDs as valid new-schema choices;
- relation removal is explicit;
- changing `door → window` clears/rejects the portal relation explicitly before commit;
- changing `window → door` does not invent a relation automatically.

## Topology-edit remapping

P23.8 owns split/merge/disappearance remapping. P23.3 must consume that result and never independently guess from Room IDs.

Important cases:

- Room split → relation side maps to the descendant physically adjacent to the opening side;
- Room merge where both relation IDs become one Room → relation is explicitly cleared while physical door survives;
- ambiguous remap → topology edit rejects.

## Legacy compatibility

Existing legacy `connectsRoomIds` may name Rooms that are not physically adjacent under the new topology contract.

P23.0 compatibility rules apply:

- keep old relation readable in legacy read-only/runtime mode;
- do not silently clear it on load;
- do not make an old publication fail solely for violating the new contract;
- block new-schema Save until the relation is explicitly resolved/removed.

Do not apply the stricter new-schema validator directly to raw legacy data before compatibility decoding.

## Wall subdivision interaction

P23.8's Wall split rules are authoritative:

- opening before split stays on retained Wall;
- opening after split moves to new Wall and rebases offset;
- split through opening interior rejects;
- Opening ID survives deterministic host rebasing.

P23.3 must not maintain a competing split-offset implementation.

## Snapping

Consume P23.2 snap infrastructure.

Opening-specific candidates may include:

- Wall end-clearance targets;
- Wall midpoint / centered placement;
- existing opening edges where useful;
- grid only where appropriate to meter-offset editing.

Acquisition/visual guides are transient; opening fit remains model-space validation.

Normative for body drag (reject-not-clamp): the pointer projection is a raw
candidate offset. A real snap win (endpoint-clearance, midpoint,
other-opening edge, grid-center) may suggest a valid snapped offset; mere
clamping to `[0, length - width]` never does. A raw candidate outside fit
bounds shows a transient invalid preview and rejects on pointer-up with no
history — it must not become an end-placed commit. See the P23.2 entry in
Post-P23.9 implementation delta and the Direct-manipulation state machine.

## Curves

Existing curved legacy openings remain compatibility-supported according to F0/H1/H3 fidelity rules.

New direct body/width manipulation is straight-Wall-only in the minimum. Do not resample curves into an approximate second placement model.

## Tests

- Center on Wall yields exact meter offset;
- distance-from-end converts correctly;
- body drag preserves non-edited fields and commits once;
- width handles preserve host/ID and commit once;
- endpoint overflow rejects rather than clamps;
- overlapping openings reject atomically;
- vertical-fit invalid candidate rejects;
- one shared Wall + one Door produces one authored Opening/compiler cut;
- valid new-schema portal relation requires actual two-sided Wall adjacency;
- nonadjacent new-schema relation rejects;
- exterior/Partition door may exist without relation;
- door→window handles relation explicitly;
- Room split remaps portal to adjacent descendant;
- merge collapsing relation endpoints clears relation explicitly;
- ambiguous remap rejects;
- legacy nonadjacent relation remains compatibility-readable but blocks new Save;
- Wall shrink from P23.1 cannot leave an invalid opening;
- Wall split rebase behavior matches P23.8 exactly;
- Undo/Redo restores exact Opening host/offset/portal state.

## Non-goals

- door leaf animation/open-close state;
- hinge/handedness/swing semantics unless separately authored;
- automatic Camera edges from doors;
- inferred portal relations from proximity;
- normalized offsets;
- curved-Wall/Bézier authoring, selection, direct manipulation, topology,
  snapping and Opening manipulation (post-P23; legacy `auto-bezier` boundaries
  stay fidelity-preserving compatibility geometry — readable/renderable, never
  silently flattened, and unsupported topology editing stays visibly
  unavailable);
- canonical Wall/Junction selection, hover and editing affordances — owned by
  P23.6 (extend the one selection authority) and accepted by P23.7;
- duplicate physical openings for adjacent Rooms.

### Canonical Opening state flow

```text
author (Plan click at wallId+offset | Inspector exact fields | Center-on-Wall)
→ resolve host Wall length (canonical start frame, wallId-keyed query spans)
→ snap (P23.2 offset-space; transient only)
→ pure candidate LayoutDocumentWallFirst (one Opening record, wallId host,
   meter offset, explicit width/height/sill/profile, door-only relation)
→ whole-hosting-Wall set validation (canonical opening-set validator + codec + portal gate)
→ P23.8 lineage where applicable (split/rebase/remap — not guessed here)
→ compileWallFirstLayoutGeometry() → geometry.walls (single cut) + queries
→ Plan render (physical-opening) / 3D standalone mesh / visitor shells
→ one Layout history entry (invalid/cancelled/no-op → none)
→ Undo/Redo restores exact host/offset/portal/IDs (never reruns reconciliation)
```

One physical Opening record per authored Opening; hosted by canonical Wall
ID; offset from canonical Wall start; shared Wall → one authored Opening,
one compiler cut, Room-side context derived from `wallFirstAdjacentRooms` +
Room `boundary` refs, never duplicated per Room.

### Direct-manipulation state machine

```text
idle (select tool, canonical opening hit available)
→ pointerdown on opening body
  → capture immutable gesture baseline (openingId, wallId, offset, width,
     height, sill, profile, relation) + snapshot for cancel
→ pointermove
  → project to host-wall spans → raw pointerOffset (canonical frame, unclamped)
  → P23.3 drag use-mode around resolveOpeningDragSnap: a real snap win
    (endpoint-clearance / midpoint / other-opening edge / grid-center)
    suggests a valid snapped offset; otherwise the raw candidate stands and
    validates on its own merits — clamping never converts invalid to valid
    (transient guides only)
  → transient preview: valid snapped/raw candidate previews on-wall;
    raw candidate outside fit bounds previews invalid (no document write)
→ pointerup → validate whole-wall set → commit once (one history entry) if
  valid; reject with no history if the raw candidate is outside fit bounds
  (a drag 2 m past the wall end never becomes an end-placed commit)
→ Escape / pointer-cancel / invalid → restore baseline, no history,
   selection unchanged

width handles (straight Walls only):
  left handle fixes right edge (offset+width const, offset varies);
  right handle fixes left edge (offset const, width varies);
  same transient → validate-once → commit-once → cancel-restores contract.
```

Exact edits (Inspector Apply / Center on Wall / distance-from-end) follow the
same validate-once → commit-once boundary; `door→window` clears/rejects the
relation explicitly before commit; `window→door` invents none.

### Transaction/history boundary

Every durable opening intent is one `runLayoutMutation` /
`commitLayoutTransaction` entry on the shared chronological stack carrying
the full candidate document (Junction/Wall/Opening/Room/portal effects where
P23.8 applies). Completed gesture/Apply → at most one logical history
result; invalid/cancelled/no-op → zero history (history-controller `matches`
no-op path). Undo/Redo uses snapshot capture/replace
(`layoutPreviewSnapshotMatchesLive` comparison); redo never reallocates IDs
or reruns Room correspondence. Rejected Wall-shrink / split-through-opening /
overlap / vertical-fit candidates commit nothing and leave prior Walls,
selection, and continuation state untouched.

### Compiler/query/render path

```text
LayoutDocumentWallFirst
→ compileWallFirstLayoutGeometry() (room adapter + canonical physical pass)
→ geometry.walls[i].openings (single cut per Wall, wall-start frame)
→ queries.spans (kind 'opening', wallKey = wallId, no roomId) + AABBs
→ Plan: plan-render-model physical-opening polylines (+ hit/selection once added)
→ 3D editor/visitor: buildStandaloneWallMesh cuts (sill/lintel/jamb/arch)
→ snap/align/hit: wallKey-grouped spans (never segmentId alone)
```

Wall-first `CompiledRoom.walls/openings` stay empty; Room floor/ceiling
polygons + identity persist for fills/containment/room hits. Legacy
documents keep the room-derived path untouched (byte-identical core,
`layout-geometry.ts:216-219,742-744`).

- Room correspondence: only `reconcileRooms` + `remapPortalRelations`

- Portal candidates: only `wallFirstAdjacentRooms` post-acceptance; Save gate

### Selection limitations

Live authority is legacy room-anchored (`layout-interaction.ts:121-127`;
`plan-hit.ts`; `plan-render-model.ts:367-371`; `layout-3d-picking.ts`);
the `(roomId,segmentId)` → `(wallId/junctionId/openingId)` cutover is
deferred (P23.8:370-381; P23.9 amendment). P23.3 therefore ships the
**minimal** canonical opening target only — enough for hit → select → drag /
handles / Inspector. Concrete shape constraint:

```text
P23.3 must extend the existing Layout selection authority with one
wall-first opening target keyed by:

  wallId
  openingId

It must not introduce a second selected-opening store/session slot.

Legacy opening selection remains:
  roomId + segmentId + openingId

Wall-first opening selection remains:
  wallId + openingId

Consumers discriminate through the existing LayoutSelection authority.
```

The implementer chooses the exact TypeScript discriminant after inspecting
all consumers. Do not make `roomId` optional on the existing legacy shape
just to squeeze both generations together — that spreads ambiguous checks
everywhere. P23.3 must not invent a parallel wall-selection system,
roomless-wall rich selection, or a second pick-index namespace (no
`selectedWallFirstOpening` side-channel or equivalent); anything beyond
opening hit/select/edit rides with P23.6/P23.7. Until the cutover,
roomless commits preserve selection (P23.9 rule) and continuous drawing
never depends on selection.

## Ratified behavior

- One physical Opening record per authored Opening; hosted by canonical Wall
  ID; offset in meters from canonical Wall start; no normalized offsets.
- No silent clamp: overflow/overlap/vertical-fit/invalid-host candidates
  reject. Pointer projection is a raw candidate; only a real snap win may
  suggest a committable snapped offset — clamping an invalid drag into
  endpoint validity is forbidden ("drag 2 m past the wall" rejects, it never
  becomes "place exactly at the end"). Creation-grid rounding still validates
  before commit.
- Complete hosting-Wall opening set validates atomically on every edit.
- Shared Wall → one authored Opening, one compiler cut, no per-Room
  duplicates; Room-side context derived from accepted topology, never stored
  as ownership.
- `connectsRoomIds` stays optional semantic intent on doors only; valid only
  for the exact two Rooms adjacent to the hosting boundary Wall; never
  creates adjacency; exterior/partition doors normally omit it.
- P23.8 owns every split/rebase/remap; P23.1 owns precision gates; P23.2 owns
  snap candidates; one compiler / one query output / one history stack;
  visitor/editor isolation intact.
