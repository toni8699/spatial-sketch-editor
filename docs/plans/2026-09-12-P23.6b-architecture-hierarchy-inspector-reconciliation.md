## Why this slice exists

P23.6 shipped canonical Wall/Junction selection and exact selected-Wall editing, but
deliberately left the left hierarchy **transitional** and the right Inspector
carrying a **competing edit target**.

Two concrete seams:

1. **Hierarchy.** `buildUnifiedProjectTreeModel` still returns a read-only
   `wallFirstRooms: UnifiedWallFirstRoom[]` bucket. Rooms render as inert rows
   with a `— edit in Architecture · exact` tooltip; document-global Walls, hosted
   Openings, Junctions and document-level LayoutObjects have **no** first-class
   resting rows. The legacy `Room → Architecture → Wall` shape cannot be restored
   because a physical Wall is document-global and may bound two Rooms
   (`apps/editor/src/lib/editor/unified-project-tree-model.ts`).
2. **Inspector authority.** `EditorInspector.svelte` keeps a private
   `precisionTarget = $state<PrecisionTarget>(null)` plus its derived
   `selectedPrecisionJunction/Wall/Room`. The `Architecture · exact` accordion
   navigates through `selectPrecisionTarget({kind,id})` (`EditorInspector.svelte`
   ≈ line 1222), which is a **second selected-entity authority** next to the
   canonical `LayoutSelection`. Hiding that inventory behind "Advanced" would
   preserve the competing target.

P23.6b retires both. It is a **projection + interaction authority**
reconciliation, not a new geometry/topology slice.

```text
canvas pick ↔ canonical selection (LayoutSelection / workspace / navigation)
           ↔ hierarchy projection
           → Inspector
```

## Product outcome

One project hierarchy that shows structure according to **true ownership**, and an
Inspector that edits exactly the one canonical thing selected.

- Every physical document-global Wall appears **exactly once**; a shared Wall never
  appears once per Room.
- Openings nest under their single host Wall.
- Rooms are semantic leaves; their boundary Walls are shown as relations, never as
  ownership.
- LayoutObjects are a separate document-level group; Scene content is a separate
  Scene-owned group in the same hierarchy.
- Selecting any canvas or tree row activates the existing canonical selection slot
  for its owner/domain; the Inspector follows the canonical selection and nothing
  else.

## Approved semantic decisions

### D1 — Hierarchy shows ownership, not containment

Groups are **Rooms**, **Architecture**, **Layout Objects**, **Scene Content**
(Camera Tour stays its own top-level root as today).

```text
Rooms
  Room A
  Room B
Architecture
  Walls
    Wall 1
      Door 1
    Wall 2
      Window 1
  Topology…  (⚠ n when relevant)
Layout Objects
  Column 1
  Platform 1
Scene Content
  Sculpture
Camera Tour
```

This is presentation IA. It creates **no** persisted project entity and no
tree-specific schema field.

### D2 — One Wall row per physical Wall

Walls are document-global. `wallFirstRooms[].wallIds` is **not** the Architecture
source; the source is the document's `layout.walls` (each `LayoutWall` once). A
Wall shared by two Rooms still yields one row. Boundary participation is shown as a
**relation** in the Wall Inspector, not duplicated rows.

### D3 — Openings nest under exactly one host Wall

`layout.openings[].wallId` is authoritative. An Opening row exists only under its
host Wall row. Selecting it routes through `selectLayoutWallOpening`.

### D4 — Junctions are canonical but not resting clutter

No always-expanded list of 50–100 Junctions. A `Topology…` disclosure exposes a
Junction browser + diagnostics; Junctions stay reachable through canvas,
selected-Wall endpoint relations, search, and the disclosed surface. This is the
existing `Architecture · exact` Junction inventory re-homed, not a second topology
model.

### D5 — LayoutObjects are a document-level group

`layout.objects` are document-level (`object.roomId` is an **optional explicit
association**, never inferred from coordinates). Rows live under **Layout Objects**;
an explicit `roomId` is shown as an "Associated Room" relation, not ownership. The
current Inspector's "Room ownership" label is renamed accordingly.

### D6 — Scene content keeps Scene ownership in the shared hierarchy

Scene `clusters`/`entities` render under **Scene Content** for continuity. One
hierarchy over two documents is **not** one document: Scene rows route to the Scene
selection slot, Layout rows to `LayoutSelection`. Mutation authority is unchanged.

### D7 — One canonical selection authority per owner/domain

`deriveActiveSelection` is the authority. The Inspector edits the canonical
selection (`active.domain` + `active.selection`) or nothing. Tree rows activate the
existing slots through the existing select helpers. There is no hierarchy-local or
Inspector-local selected-entity truth.

### D8 — Operation parameters are not selected entities

`precisionFixedEndpoint` (which Wall endpoint stays fixed during Length/Angle
edit), `precisionRectangleAnchor`, `precisionRectangleWidthWall` and accordion
disclosure are **ephemeral operation parameters**. They may derive from / reset when
the canonical selection changes, but they never select an entity and never edit a
document.

### D9 — Deterministic ordering and derived labels

Row order is deterministic document/compile order: Rooms in `layout.rooms` order;
Walls in `layout.walls` order; Openings grouped by host in `layout.openings` order;
LayoutObjects in `layout.objects` order; Scene rows in document order. Order never
changes because of selection, hover, viewport visibility or timestamps.

Walls/Junctions/Openings have **no authored human name** fields today. Use derived
labels (`Wall 17`, `Junction 4`, `Door · opening-3`) without adding schema. Canonical
IDs remain the internal row key and are visible/searchable in Advanced/debug.

### D10 — Numeric presentation

Exact numeric controls keep bounded presentation formatting (`formatMeters` /
`formatDegrees`), `step="any"` (or planner-owned validity) and the guarded Layout
mutation path. Duck-typed `step` arithmetic must never be the semantic authority.

### D11 — Rail collapse/focus is preserved, not redesigned

The existing contract in [`docs/components/shell.md`](../components/shell.md)
(independent left/right session booleans, CSS-only grid collapse, `inert` hidden
panels, focus restoration per panel, deferred collapse during a pointer gesture)
is **preserved**. B fixes only regressions the new hierarchy/Inspector introduce.

## Final hierarchy model

Target `UnifiedProjectTreeModel` shape (final names are implementation choice; the
**information** is the contract):

```ts
type UnifiedProjectTreeModel = {
  rooms: UnifiedTreeRoom[];              // legacy rooms (unchanged, format-gated)
  wallFirstRooms: UnifiedWallFirstRoom[]; // canonical Rooms (now truthful rows)
  architecture: {
    walls: UnifiedTreeWallRow[];         // canonical, one per layout.walls entry
    junctions: UnifiedTreeJunctionRow[]; // for the Topology disclosure, not resting
  };
  layoutObjects: UnifiedTreeObjectRow[]; // document-level
  sceneContent: { clusters; entities };  // scene-owned
  cameraTour: UnifiedTreeCameraTour;     // unchanged
};
```

```ts
type UnifiedTreeWallRow = {
  wallId: string;
  role: 'boundary' | 'partition';
  height: number;                        // P23.6H authoritative
  openings: { openingId; kind: 'door' | 'window' }[]; // host-nested
  boundedRoomIds: string[];              // relation only
};
```

### Format-gated legacy policy (decided — no duplicate rows)

The new document-level roots are populated **only for wall-first documents**.

```text
wall-first document:
  Rooms / Architecture (Walls + hosted Openings + Topology…) /
  Layout Objects / Scene Content / Camera Tour — populated

legacy compatibility document:
  existing legacy Room-nested projection retained
  (UnifiedTreeRoom.objects / .clusters / .entities stay exactly as today)
  new document-level Layout Objects / Scene Content roots
  — empty and not rendered
```

Why this is required rather than stylistic: the current legacy branch already
nests `layout.objects` (matched by explicit `object.roomId`) and Scene
`clusters`/`entities` (matched by explicit `roomId`) **inside `UnifiedTreeRoom`**
(`unified-project-tree-model.ts`). Populating the new top-level roots for legacy
documents as well would render the same object/entity twice. The wall-first branch
currently returns `{ rooms: [], wallFirstRooms, cameraTour }`, so for wall-first
documents nothing nests and nothing can collide.

Consequences to implement:

- `buildUnifiedProjectTreeModel` populates `architecture` / `layoutObjects` /
  `sceneContent` in the `'formatVersion' in layout` branch only; the legacy branch
  returns empty roots (and the component must not render empty groups).
- P23.6b does **not** migrate the legacy hierarchy; P23.7 retains the final
  compatibility/legacy-retirement decision and its end-to-end acceptance.
- Required tests (see §Test plan): `legacy Room-associated LayoutObject appears
  exactly once`, `legacy Scene entity appears exactly once`, `wall-first
  LayoutObject appears exactly once under Layout Objects`, `wall-first Scene entity
  appears exactly once under Scene Content`.

Key requirements:

- `UnifiedWallFirstRoom` stops being read-only-only: it gains stable row identity
  usable by `isUnifiedTreeRowSelected` (its `roomId`), and Rooms become interactive
  in Layout mode.
- Wall rows never derive from `wallFirstRooms[].wallIds`; they come from
  `layout.walls`.
- `layoutSelectionAncestorRoomId` **keeps its current legacy-Room meaning and
  export** (pinned by `contracts.test.ts`); canonical reveal is added as a **new
  pure sibling** `layoutSelectionRevealTarget(selection, layout)` (see §Reveal
  target API) rather than by overloading the legacy helper with a misleading
  Room-ancestor type.

## Inspector structure and authority cleanup

Priority order inside the selected-entity panel:

```text
actionable diagnostic (if present)
→ identity
→ editable geometry/properties
→ behavior / semantic role
→ meaningful relations
→ advanced / debug
```

The Inspector is **not** an architecture-wide inventory. The document-wide Junction/
Wall/Room lists move into the disclosed `Topology…` surface as navigation.

### `precisionTarget` retirement (explicit)

1. Delete `precisionTarget`, `precisionTargetKind`, `precisionTargetId`,
   `selectedPrecisionJunction/Wall/Room`,
   `selectedPrecisionWallEndpoints`, `selectedPrecisionRectangle`,
   `precisionRectangleWidthWallOptions`, `selectPrecisionTarget`, and the
   `precisionTarget`-invalidation `$effect`.
2. Repoint every caller of `selectPrecisionTarget` (the `Architecture · exact`

3. The selected-Wall panel reads `selectedWallFirstWall` (canonical) only. Any place
   the old precision Wall editor was reachable without a canonical `physicalWall`

4. `precisionFixedEndpoint` / `precisionRectangleAnchor` /
   `precisionRectangleWidthWall` stay, but a `$effect` resets them from the

### Reveal target API (decided)

Two helpers with different, non-overlapping meanings — do not overload one:

```ts
// unchanged (legacy Room-qualified selections; pinned by contracts.test.ts)
export function layoutSelectionAncestorRoomId(
  selection: LayoutSelection,
  layout: LayoutDocument
): string | null;

// new, pure, wall-first-capable
export function layoutSelectionRevealTarget(
  selection: LayoutSelection,
  layout: LayoutDocument | LayoutDocumentWallFirst
): LayoutTreeRevealTarget | null;
```

`LayoutTreeRevealTarget` is a **presentation projection** (exact naming and shape
are implementation choice), conceptually one of:

- Rooms root + `roomId`;
- Architecture root + `wallId`;
- host Wall + `openingId`;
- Topology disclosure + `junctionId`;
- Layout Objects root + `objectId`.

Rules:

- A reveal target is **not** a second selected-entity authority: it never selects,
  never edits and never persists. It only names the ancestors to expand and the row
  to scroll to.
- `layoutSelectionAncestorRoomId` stays exported and behavior-identical (its
  null-for-canonical behavior is itself a pinned contract).
- The component may use both: the legacy helper for legacy Room-qualified
  selections, the new helper for canonical selections.
- `contracts.test.ts` gains a source contract for the new helper **in the same task
  that adds it**; the existing `layoutSelectionAncestorRoomId` pins stay.

## Canvas ↔ tree reveal

Canonical selection reveals its corresponding **resting** row when one exists:

- Wall selection → expand **Architecture** → reveal Wall row.
- Opening selection → reveal host Wall, expand it, reveal the Opening row.
- Room selection → expand **Rooms** → reveal Room row.
- LayoutObject selection → expand **Layout Objects** → reveal row.
- Junction selection → **do not** explode the Topology inventory; reveal via the
  disclosed selected representation (e.g. `Topology… ⚠` selected state) without
  expanding every Junction.

Filter handling (must not silently erase the user's filter):

- no active filter → expand required ancestors → scroll row into view;
- filter active and the selected row **matches** → reveal normally;
- filter active and the selected row is **excluded** → keep the filter, indicate the
  selection is hidden by the filter, and offer an explicit **Reveal** / **Clear
  filter** action. Do not auto-clear.

Expansion/filter/scroll state is transient UI state, never project state.

### Room rename guard (wall-first must not inherit legacy rename)

`UnifiedProjectTree.svelte` today exposes a Room context-menu rename
(`onRoomRowContextMenu` → `renameRoomViaPrompt` → `runLayoutMutationGuarded(() =>
updateLayoutRoomFields(layoutPreview, roomId, { name }))`, plus
`buildPlanLayoutContextMenuItems({ renameRoom })`). `updateLayoutRoomFields`
(`apps/editor/src/lib/editor/layout/layout-preview-state.svelte.ts`) is **legacy**:
it resolves the Room through `layout.floors`, which no wall-first document has.

Therefore, when wall-first Room rows become interactive:

```text
wall-first Room row → no legacy renameRoom action / context-menu command
legacy Room row     → existing rename behavior may remain
wall-first renaming → deferred until a canonical Room metadata operation is
                      explicitly designed (no such operation exists)
```

Do not add a Room metadata planner to preserve rename, and do not route a
wall-first Room id into `updateLayoutRoomFields`. Required regression test:
`canonical wall-first Room context/menu does not expose or invoke the legacy
updateLayoutRoomFields rename`.

## Test plan

Extend `apps/editor/tests/lib/editor/app/unified-project-tree.test.ts` plus a new
B-focused suite. Named scenarios:

- **Ownership:** a Wall shared by two Rooms appears exactly once; Rooms never list
  boundary Walls as owned children; adding a second Room does not duplicate Wall rows.
- **Openings:** an Opening nests under exactly one host Wall; no Opening row without
  a host.
- **Groups:** LayoutObject rows live under the document-level group, not under Rooms;
  an explicit `roomId` renders as an association.
- **Scene separation:** Scene rows route to the workspace slot, never
  `LayoutSelection`.
- **Junctions:** absent from the resting tree; reachable via the `Topology…`
  disclosure and search.
- **Selection round-trips:** canvas Wall → same tree row highlighted + Wall Inspector;
  tree Wall click → `{kind:'physicalWall'}`; Opening row → `{kind:'wallOpening'}`;
  Room row → `{kind:'room'}`; LayoutObject row → `{kind:'object'}`.
- **Authority:** selecting a Wall/Junction/Opening updates the Inspector with **no**
  `precisionTarget` present; operation parameters (`precisionFixedEndpoint`, rectangle
  anchor/width-wall) remain deterministic and do not become selected-entity state.
- **Capability preservation:** each row of §Capability preservation mapping has a
  reachable control bound to its handler (Length/Angle/Thickness/Height/role/add
  vertex, rectangle dims + duplicate, Opening ops, Junction X/Z, diagnostics).
- **Mode matrix:** structural rows inert in Arrange; object rows active in Arrange;
  Scene rows not co-highlighted with layout rows.
- **Plan/3D continuity:** the same rows persist across view switches; no test asserts
  direct 3D Wall picking.
- **Reveal:** no-filter reveal expands ancestors; a row excluded by an active filter
  offers Reveal/Clear and does not erase the query; Junction reveal does not expand
  the whole inventory.
- **Determinism:** order stable across selection/hover; derived labels stable; dense
  project (≈50 Walls / ≈100 Junctions / 20 Openings / many objects/entities) renders
  without Junction flood or shared-Wall duplication.
- **Numeric formatting:** `formatMeters`/`formatDegrees` bounded output; durable
  precision unchanged.
- **Legacy compatibility projection:** a legacy document populates no canonical
  top-level roots; a legacy Room-associated LayoutObject appears exactly once
  (still Room-nested); a legacy Scene entity appears exactly once. For a wall-first
  document: a LayoutObject appears exactly once under Layout Objects and a Scene
  entity exactly once under Scene Content.
- **Room rename guard:** a wall-first Room row exposes no legacy `renameRoom`
  context-menu command and cannot invoke `updateLayoutRoomFields`; the legacy Room
  rename path is unchanged where it still applies.
- **Reveal helper contract:** `layoutSelectionAncestorRoomId` keeps returning `null`
  for `physicalWall` / `wallOpening` / `junction` (existing test unchanged);
  `layoutSelectionRevealTarget` returns the Architecture/host-Wall/Opening/
  Topology/Layout-Objects target for those selections and never selects.
- **Source contracts:** `apps/editor/tests/lib/editor/app/contracts.test.ts` stays
  green with the added reveal-helper contract.
- **Regression:** existing shell collapse/focus tests stay green; `cameraTour`
  consumers unaffected.

## Deferred: 3D wall-first picking / highlighting

Direct 3D Wall/Opening **picking and highlight** is a separate responsibility from
hierarchy continuity. The tree may keep the same rows and remembered selection
across Plan/3D, but B does **not** implement canonical 3D Wall picking/highlighting.

Current state: `apps/editor/src/lib/editor/layout/layout-3d-picking.ts` resolves
layout 3D hits but the P23.6 list-3d-picking deferral
(`isLayoutDirectPickDeferred`) still governs direct structural picks. This plan
**defers** direct 3D wall-first Wall/Opening picking/highlighting out of B; it must be
assigned a dedicated owner or remain a documented deferral at P23.7. No test may
assert it works.
