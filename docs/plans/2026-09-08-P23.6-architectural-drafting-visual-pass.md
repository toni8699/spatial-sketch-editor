# P23.6 — Architectural drafting visual pass

**Parent:** [P23 — Layout Depth umbrella](2026-09-07-P23-layout-depth-minimum-build.md)  
**Status:** `implementation-ready` — runs after semantic slices stabilize.  
**Evidence:** P23-H2 complete; wall-first reconciliation ratified 2026-09-09.

## Outcome

Plan visually communicates first-class Junctions, Walls, Rooms, Openings, dimensions, snapping and topology diagnostics clearly without creating a second geometry or selection authority. Room-bounding and non-room-bounding behavior is presented as one Wall concept.

## Selection ownership

P23.6 owns the **single primary Wall authoring presentation** and the
**existing single canonical selection authority** (`LayoutSelection` + the Plan
interaction/hit projection) extended to first-class Wall/Junction selection,
hover and editing affordances — the cutover P23.3 deliberately leaves open.

There is one primary Wall concept in the polished P23 UX, not separate Wall and
Partition product concepts. The separate Partition primary tool is removed from
authoring presentation. The internal `role: 'boundary' | 'partition'` Wall
semantic remains authoritative, but `partition` is an internal Wall semantic
rather than a separate user-facing object family.

P23.3 ships only the minimal canonical Opening target its create/edit/drag/
resize gestures require (`{ kind: 'wallOpening'; wallId; openingId }` on the
same authority). It adds no Wall/Junction selection slot, and the full legacy
`(roomId, segmentId)` → canonical `wallId`/`junctionId` architectural
selection cutover stays deferred to this slice and is accepted in P23.7.

Never create a second selection store, a parallel hit-test path or a
renderer-local selection model: extend the one authority and its projection.

## Hard authority boundary

P23.6 may extend the existing canonical selection/hit/interaction projection
for Wall/Junction targets. It does not introduce new authored geometry,
topology, mutation authority, history authority, or renderer-local state.
Durable edits continue through the existing Layout domain operations.

```text
LayoutDocument
→ compileLayoutGeometry()
→ compiled query/render data
→ PlanRenderModel / interaction projection
→ PlanSvg.svelte + existing Plan chrome
```

No durable fields are added solely for visual treatment. No SVG-specific topology, Room extraction, opening placement or snap coordinates become authored truth.

## Wall-first visual hierarchy

There is one primary Wall concept in the polished P23 UX. The visual distinction
between room-bounding and non-room-bounding Walls is a subtle truthful
presentation of a single Wall's current behavior, not a separate object system.

### Room-bounding Walls (role: 'boundary')

- strongest primary architectural stroke hierarchy;
- selected/hovered state unmistakable;
- join/cap treatment derives from canonical compiled geometry;
- no decorative centerline presented as an independent editable representation.

### Non-room-bounding Walls (role: 'partition')

- physically wall-like and visually present as real physical Walls;
- do **not** look temporary, invalid, or provisional — they remain physical Walls;
- subtle visual distinction enough to communicate that they do not divide semantic Rooms;
- use the same selection/highlight language as room-bounding Walls rather than a separate object system;
- the distinction is the truth of current behavior, not a different object family.

### Junctions

- normally quiet;
- visible/interactive when tool/selection context requires them;
- selected/hovered/snap-target Junction states distinct;
- do not render every Junction as permanent clutter at distant zoom.

### Rooms

- restrained derived region fill/label treatment;
- persistent Room name shown where legible;
- selected Room emphasis remains subordinate to active Wall/Opening editing when those are the tool target;
- Room labels are presentation of persisted Room metadata, not separately persisted drawing annotations.

### Openings

- doors/windows read as intentional Wall openings/gaps;
- selected-only body/width handles match P23.3;
- shared-Wall opening renders once from one physical authored Opening.

Do **not** imply hinge side, handedness or swing direction unless those semantics are actually authored. H2 found the current SVG deriving a directional door leaf/swing from insufficient state; the reconciled visual pass should suppress that invented directional semantics and use a neutral door treatment.

### Layout objects

- editable Layout object footprints retain authored/selected/hover hierarchy;
- passive Scene footprints remain quieter and keep no Layout hit authority;
- document-level object placement is not visually forced into Room ownership.

## Dimensions

Use one architectural dimension grammar for selected/active precision contexts:

- straight Wall length (selected Wall in Inspector; live passive readout during candidate preview is presentation only — see [Wall-drawing UX](#wall-drawing-ux-segment-first));
- supported rectangle width/depth;
- optional Junction coordinate readout where useful;
- opening clearances/width where P23.3 exposes them.

Presentation may use extension lines/ticks/concise meter labels.

No persistent general annotation/dimension document is created. Lower-priority labels may hide on collision; the underlying authored values never change.

## Snap / guide vocabulary

Show the **winning semantic snap**, not all possible candidates.

Distinct transient marker/guide treatments for relevant families such as:

- Junction/endpoint;
- midpoint;
- intersection;
- nearest Wall span;
- orthogonal/extension relation;
- Opening edge;
- grid.

Snap feedback must be visually distinct from:

- committed selection;
- hover;
- invalid candidate;
- draft geometry.

One blue/selection language stays canonical; do not make snap feedback look like another selection slot.

## Wall-drawing UX (segment-first)

P23.6 owns the Plan-side presentation of continuous Wall drawing per the ratified P23.9 segment-first amendment. Normal Layout authoring presents one **Wall** concept; newly drawn Walls default to participating in Room topology (`role: 'boundary'`). The separate Partition primary tool is removed from the polished P23 UX. The internal `role: 'boundary' | 'partition'` Wall semantic remains authoritative, but `partition` is an internal Wall semantic rather than a separate user-facing object family.

- committed Walls versus transient candidate preview;
- continuation start / current start point;
- snap winner/guide;
- **live passive candidate length readout** for the current `start → cursor` segment (presentation only, not authored state, not a second geometry path — see ownership below);
- run-closure cue (snapped onto the run's starting Junction);
- invalid topology preview.

Candidate visuals never enter document/history.

### Live candidate length readout

While previewing `start → cursor`, show a **live, passive Wall length readout** that updates continuously as the candidate changes. This readout is presentation only: it does **not** become authored state, does **not** expose an editable exact-length input during the normal drawing gesture, and does **not** constitute a second geometry path. Exact precision belongs to post-selection editing (see [Selected Wall precision](#selected-wall-precision)).

### Removed / deferred Wall-drawing chrome

The following are explicitly **not** part of the normal Wall drawing flow and are removed or deferred:

- **No separate Commit segment button.** A normal straight Wall is committed by the second click. There is no pending chain waiting for Finish.
- **No large bottom-right Wall-drawing action bar** whose only purpose is Length / Commit / Cancel.
- **No editable exact-length input** during the normal Wall drawing gesture. Exact length editing is a post-selection Inspector operation (see [Selected Wall precision](#selected-wall-precision)).
- **Cancel draft is keyboard-first via Escape.** A large persistent cancel button that blocks the Plan canvas / XZ axis overlay is not required. Escape cancels only the active transient candidate/run; committed Walls remain.
- **No verbose success/status messages** such as `Committed wall`, `Committed 4 walls + 1 room`, or similar implementation-oriented commit counts. Successful authoring is communicated primarily by the resulting geometry/Room appearing in Plan. Keep explicit status messaging for rejection, invalid geometry, conflicts, or other cases where the user needs explanation.

### Selected Wall precision

When a canonical Wall is selected, the Inspector exposes exact editing operations:

- **Length** — exact straight-Wall length editing;
- **Angle** — exact angle editing;
- **Thickness**, **Height** — alongside the above.

These exact edits reuse the existing canonical P23.1 precision operations. They do **not** add a stored `wall.length` field or bypass Junction/topology reconciliation. Every exact edit runs normal validation, topology/Room reconciliation, Opening-fit checks, compiler validation, and one deterministic history transaction.

Length/Angle editing is owned here (P23.6) for presentation; acceptance that the canonical precision/topology/history paths are reused is owned by P23.7.

### Selected Wall: Defines room boundary

Once canonical Wall selection exists, the Inspector exposes a **Defines room
boundary** control for the selected Wall:

- **checked** → `role: 'boundary'` — the Wall participates in Room face extraction;
- **unchecked** → `role: 'partition'` — the Wall remains a physical Wall but does not divide semantic Rooms.

Do not require the user to understand the term `partition`. The property is
presented as a single Wall affordance, not as a separate object family.

Changing this control is **not** a direct UI field assignment (`wall.role =
'partition'`). The semantic role change must use one canonical Layout operation:

```text
candidate Wall role change
→ structural validation
→ P23.8 topology / face extraction
→ persistent Room reconciliation
→ Opening / portal validation and remap
→ canonical compiler validation
→ one deterministic Layout history transaction
```

P23.8 remains authoritative for topology and Room identity/reconciliation. P23.6 owns only:

- the user-facing **Defines room boundary** property;
- the Inspector interaction;
- the thin operation adapter/planner needed to invoke existing canonical topology/reconciliation machinery.

Do not add another topology engine, Room allocator, compiler, selection store, or history path.

Typical behavior:

- drawing enclosing Walls → enclosed topology → Room appears through existing P23.8 reconciliation;
- drawing another room-bounding Wall across an existing Room → supported face split → Room reconciles into two persistent Rooms;
- if that Wall is later changed to **Defines room boundary = off** → physical Wall remains, Wall stops participating in Room face extraction, affected Room topology reconciles canonically;
- a non-room-bounding Wall → enable **Defines room boundary** → if supported topology is formed → Room creation/split occurs through canonical reconciliation.

This supports decorative, exhibition, freestanding, display, or other physical
Walls that should not create separate semantic Rooms.

## Topology diagnostics

P23.8 diagnostics need useful presentation without auto-repair implications.

Examples:

- collinear overlap;
- non-noded crossing;
- dangle/cut edge relevant to failed enclosure;
- invalid ring;
- unsupported nested/hole case;
- ambiguous Room correspondence;
- metadata/portal conflict.

Show the affected source Wall/Junction/Room where possible and concise reason. Do not “fix” geometry by merely moving SVG paths.

## Grid

Preserve P23.2 configured metric step and current major/minor LOD concept.

Improve hierarchy/readability only. Zoom treatment must not change snap coordinates or authored values.

## Invalid / preview states

Visually distinguish:

- committed geometry;
- valid transient preview;
- invalid candidate;
- read-only legacy compatibility geometry where user action would otherwise imply editability.

Legacy compatibility state may display a clear read-only/migration diagnostic without changing physical appearance merely to look like new wall-first data.

## Theme/accessibility constraints

- reuse existing P21 Plan/theme token system;
- no separate CAD theme;
- no hard-coded per-theme palette branches in SVG;
- keyboard focus visible;
- sufficient contrast across all shipped themes;
- reduced-motion preference respected for any animated transient feedback;
- no decorative gradients/shadows that obscure drafting semantics.

## Label density

Use bounded deterministic collision/priority logic only.

Priority should generally favor:

1. active edit/selection;
2. invalid diagnostic;
3. active dimension/snap feedback;
4. Room/other contextual labels.

If density cannot be resolved cheaply, hide lower-priority presentation. Do not build a general annotation-layout solver.

## Tests / visual acceptance

- one primary Wall concept is presented; room-bounding and non-room-bounding Walls are the same object family with truthful behavioral distinction;
- Room / Opening hierarchy readable at representative zooms;
- one shared Opening renders once;
- Junctions appear appropriately in edit contexts without global clutter;
- selection/hover/snap/draft/invalid states are distinguishable;
- current invented directional door swing/leaf is absent unless durable semantics are added separately;
- selected Wall/rectangle/opening dimensions are legible;
- the **Defines room boundary** control is present on selected Walls;
- disabling **Defines room boundary** keeps the physical Wall while reconciling affected Rooms correctly;
- enabling **Defines room boundary** on a non-room-bounding Wall can create/split Rooms where topology supports it;
- passive Scene footprints remain subordinate and non-authoritative;
- read-only legacy compatibility state does not expose active mutation affordances;
- changing visual density/zoom does not change compiled geometry, snap result, document JSON or history;
- keyboard focus/contrast checks across shipped themes;
- render-model/component tests assert semantic output/classes/attributes; pixel snapshots are not the only gate.

## Non-goals

- authored persistent annotation system;
- door handedness/swing design;
- second Canvas/SVG overlay authority;
- renderer-local topology;
- second or replacement selection authority;
- general label-layout solver;
- CAD-specific theme.
