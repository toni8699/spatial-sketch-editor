# P23.6I — Wall-defined enclosure: proposal / review request

**Type:** proposal / decision-support memo. **Not** a registered increment — no
P-number is frozen by this document; per the tracker rule, numbers go on
implementation plans after ratification. On acceptance this memo is archived and
replaced by the two numbered child plans it proposes.

**Status:** **open for review — assume this is not final.** Three semantic calls
were ratified by the owner on 2026-09-12 (§4); everything else below is the
reviewer's to accept, correct, narrow or reject. The memo is revised in place
until it is ratified; nothing here is implemented, and no existing plan document
has been amended by it.

**Date:** 2026-09-12. **Basis:** `main` `f1d13c4` + branch `P23.6-H`
(P23.6H implementation, PR #25 — open, unmerged).

**Trigger.** Reviewing the shipped P23.6H behaviour surfaced two connected
problems:

1. `LayoutWall.height` is capped by `floor.height` (default 3 m), so a Wall
   cannot be authored taller than the storey — and because the only Floor-height
   input in the app lives on the **legacy Room-owned** Inspector branch, the cap
   cannot be raised at all for a wall-first document.
2. That cap, the birth default, and the Room ceiling all read `floor.height` —
   a **Room-first** concept P23 has otherwise spent ten slices retiring. The
   owner's direction: the enclosure should be defined **by** its Walls, not the
   other way around; `floor.height` should go, or at least stop being an
   authority, so future architectures can have inconsistent heights.

**Reviewer ask — please review and revise.** Confirm the direction, the semantics
in §5, the scheduling in §1, and the two I.1/I.2 boundaries in §8 — or correct
them. Treat every section as revisable: the decisions requested in §0, the open
questions in §10, and the scheduling are all first drafts, and feedback against
the evidence in §3 is the most useful form of review. The full
implementation-ready plan documents are written only after this memo is settled,
so no work is wasted by revising it now.

## 2. Problem statement

`floor.height` currently carries four unrelated jobs on the wall-first path:

| Job | Why it is wrong long-term |
|---|---|
| Hard cap on `LayoutWall.height` | A partition or stairwell wall can never exceed the storey; the cap is architecturally arbitrary |
| Wall birth default | Ties creation to a Room-first quantity; H itself had to delete a fixed `3` literal to get here — the replacement is no better conceptually |
| Room ceiling elevation | Makes the *enclosure* declare the Wall, when the Walls make the enclosure |
| Legacy storey carrier | A real legacy need (Room-owned documents keep `floors[].height` forever) that has leaked into the canonical schema |

The owner's goal — *"future we might want inconsistent floor height to allow
different architectures"* — is unreachable while a single document-wide number
bounds every Wall. What is actually wanted is that each enclosure's vertical
extent follows its own Walls, so double-height voids, low display bays and full
storey walls coexist without a global storey value.

## 3. Current-state evidence (verified 2026-09-12)

### 3.1 Where Floor height is set today

- `EditorInspector.svelte:1944` and `:1967` render `<label>Floor height (m)` in
  the **legacy** "Selected layout wall" / "Selected layout room" panels, both
  gated by `{#if selectedLayoutFloor}`.
- `selectedLayoutFloor` (`:393`) resolves through **`project.layout.floors`** —
  the legacy Room-owned array. A wall-first document has no `floors`, so the
  input never renders.
- Its handler `updateRoomNumber` (`:912`) early-returns without that derived
  value and delegates to `updateLayoutRoomFields` →
  `layout-preview-state.svelte.ts:592` `if (patch.floorHeight !== undefined)
  floor.height = patch.floorHeight;` — a `floors[…].height` write.
- **Conclusion:** for wall-first documents there is no Floor-height editor
  anywhere (Inspector, hierarchy, Plan, 3D). `floor.height` is only produced by
  the new-project boot (`createEmptyWallFirstLayoutDocument()`, 3 m), legacy
  migration (`layout-migration.ts:943`) and import/compat decode.

### 3.2 Every wall-first reader of `floor.height`

### 3.4 Facts that make the change cheaper than it looks

- **The chain planner already resolves draft points to existing Junctions by
  coordinate** (`layout-wall-chain.ts`, draft normalization: "Resolve each draft
  point to an existing junction when its coordinate matches … explicit junction
  reuse is the commit semantic"). Neighbour inheritance is therefore
  implementable at plan time without new gesture or snapping work. The editor
  passes no `height` today (`layout-preview-state.svelte.ts:911,950`).
- **Every candidate is recompiled before commit**
  (`layout-wall-first-precision.ts:538`), so a derived envelope re-derives
  automatically on any Wall edit — no separate "recompute ceilings" operation.
- **The legacy compiler source carries no per-room override**
  (`layout-geometry.ts:111-124`), so an optional `CompilerRoomSource` field
  keeps legacy output byte-identical — the same pattern H used for
  `openingHeightLimitBySegmentId`.
- **Opening fit is already host-Wall based** (H, D6), so removing the cap does
  not disturb it; the legacy default limit is untouched.
- **The stored field is already inert data for Walls**: since H, `wall.height` is
  authoritative and no stored format-5 document can contain a Wall above its
  Floor, so nothing has to be rewritten to free the height.

## 5. Proposed semantics

### 5.1 D1 — Wall height is the only vertical authority

```text
wall.height: finite, strictly positive, no upper bound
bottomY = floor.elevation
topY    = floor.elevation + wall.height
```

The shared epsilon stays, but only for equality/derivation comparisons, not as a
cap tolerance. The `wall_height_exceeds_floor` rule and rejection code are
removed; `wall_height_invalid` (non-finite / non-positive) remains.

### 5.2 D2 — Birth rule (Wall creation)

```text
explicit override (authoring UI / API)                → use it
leg → both endpoints new                              → WALL_AUTHORING_DEFAULT_HEIGHT
leg → one endpoint is a reused existing Junction      → that incident Wall's height
leg → both endpoints reused, same incident height     → that height
leg → both endpoints reused, differing heights        → WALL_AUTHORING_DEFAULT_HEIGHT (transition)
```

- `WALL_AUTHORING_DEFAULT_HEIGHT` is a **named creation default** (proposed: 3 m,
  the historical seat) — explicitly not an authority, and the only place a height
  literal may live. It replaces H's `canonicalWallBirthHeight(floor)`.
- Resolution is **per leg** (a chain can continue a 4 m Wall and then turn into a
  new default-height leg). This is a small extension of the current single
  `height` per chain.
- Unusable-floor rejection (`invalid_floor_height`) disappears with its cause.
- Migration keeps using the legacy storey height as the birth height for the
  Walls it creates — that is what those Walls rendered as before the cutover.

### 5.3 D3 — The enclosure is derived from Walls

```text
Room envelope   = max(boundary Wall heights)      // evaluated at compile time
Room ceiling Y  = floor.elevation + Room envelope
Floor envelope  = max over its Rooms' envelopes
```

- `CompilerRoomSource` gains an optional `ceilingEnvelope`; `compileRoom` uses it
  when present and `floor.elevation + floor.height` when absent — so **legacy
  compilation stays byte-identical**.
- `CompiledFloor.height` becomes derived (wall/room-derived) rather than read
  from the document.
- Defensive fallbacks (recorded, not designed around): a Room with no boundary
  Walls falls back to the document's max Wall height, then to
  `WALL_AUTHORING_DEFAULT_HEIGHT`. No current operation can produce that shape.
- Rooms may therefore differ in height from one another and from any storey
  value — which is the point of the slice.

### 5.4 D4 — `floor.height` demotion and the version ladder

`floor.height` survives **only** as a legacy/compatibility input. The ladder
becomes:

| Declared | Rule set | On decode | Writer |
|---|---|---|---|
| `4` (pre-H) | positive-finite Wall height; no Wall-height authority | normalize: `wall.height := floor.height` | — |
| `5` (H) | Wall height `0 < h ≤ floor.height`; Floor-derived envelope | advance to current, no field rewrite | — |
| `6` (I.1) | Wall height `0 < h`; floor envelope ignored; **`floor.height` still present but inert** | advance to current | — |
| `7` (I.2) | as 6, `floor.height` **not allowed** in the document | drop the key (the value has no successor) | current writes `7` |

- The codec's existing single version check
  (`formatVersion === LAYOUT_WALL_FIRST_FORMAT_VERSION ? … : undefined`) is
  replaced by one **version-keyed rule table** — the seam that keeps four known
  versions from scattering `if (version === …)` branches.
- A bump is required even though freeing the height is *read*-compatible: a
  document declaring `5` must keep meaning exactly what H ratified, otherwise a
  stored payload's meaning silently changes.
- The Floor keeps `id`, `name`, `elevation` (authoritative for `bottomY`, portals,
  shells). Only `height` leaves.

## 6. Consequences, blast radius, risks

### 6.1 Mechanical blast radius

| Area | I.1 | I.2 |
|---|---|---|
| `layout-wall-heights.ts` | drop the cap, replace the birth helper | — |
| `layout-wall-chain.ts` | per-leg birth resolution | — |
| `layout-geometry.ts` / `-types.ts` | optional `ceilingEnvelope`; derived `CompiledFloor.height` | remove `CompiledFloor.height` |
| `layout-wall-first-codec.ts` | version-keyed rule table; v6 | v7, version-aware `FLOOR_KEYS` |
| `layout-compat.ts` | v6 decode | v7 decode |
| `layout-migration.ts` | Wall birth heights unchanged in value | floor record loses `height` |
| shells / mesh factory | ceilings already read `CompiledRoom.ceilingElevation` (no change) | floor frames lose `{height}`; the `?? { elevation: 0, height: 3 }` literals go |
| Inspector | no control added; H's `Height (m)` becomes unbounded | remove the now-meaningless legacy coupling comment |
| tests | invert the H envelope assertions; add birth-resolution + envelope cases | fixture/version updates |

### 6.2 Visible consequence (decision 4)

A Room whose boundary Walls are **all shorter than the old storey height** gets a
lower ceiling than it renders today: the enclosure closes at its tallest Wall
(3 m storey with 1.2 m display walls → 1.2 m ceiling). This directly inverts H's
recorded behaviour ("a partial-height boundary Wall does not lower the room
ceiling") and the H regression that pins it —
`p23-6h-wall-height.test.ts` → *"does not lower the Room ceiling, the Floor
envelope or the Room bounds"* (asserts `shortRoom.ceilingElevation ===
fullRoom.ceilingElevation === 4`), plus the suite's header claim that "Room/Floor
envelopes stay Floor-derived".

- This is the necessary meaning of the direction: the cap and the ceiling come
  from the same number.
- Only affected documents are those where an author deliberately lowered
  boundary Walls below the storey (or imported such a document); full-height
  enclosures are unchanged.
- A creator who wants a taller enclosure than its Walls can raise the Walls —
  which is now possible for the first time. A genuinely *taller-than-its-walls*
  ceiling needs authored vertical room semantics, registered below as deferred.

### 6.3 Risks

- **Semantic churn under P23.6a/b** if the scheduling in §1 is not followed.
- **Four known format versions** is more compatibility surface; mitigated by one
  rule table and one decode ladder, plus the ladder being monotone (each version
  is valid under the next version's rules).
- **Test inversion is intentional, not a regression**: the H suites that assert
  the floor-derived envelope must be rewritten with the reason recorded, and the
  golden/parity suites prove legacy output is untouched.
- **Forward compatibility:** a v6/v7 document containing a Wall above its Floor
  height is rejected loudly by an older reader (declared-version rule), never
  silently misread.

## 8. Proposed slice breakdown

### P23.6I.1 — Free Wall heights + Wall-derived enclosure (format 5 → 6)

Scope: §5.1, §5.2, §5.3 plus the v6 rung of §5.4. Acceptance sketch:

1. A Wall can be authored above the storey height, canonically and through the
   Inspector, with one history entry each way.
2. A new chain inherits the height of the Wall it continues, per leg; a new
   isolated Wall births at `WALL_AUTHORING_DEFAULT_HEIGHT`; no other literal
   exists on a Wall-birth path.
3. A Room's compiled ceiling equals `floor.elevation + max(boundary Wall
   heights)`; two Rooms with different boundary heights compile to different
   ceilings.
4. Legacy (`floors[]`) compilation is byte-identical on the golden/parity
   suites; wall-first single-storey enclosures are unchanged.
5. Format-4 and format-5 payloads still load, under their own rule sets, and
   advance to 6; immutable publications are untouched in bytes.
6. Opening fit, topology purity, Room identity and the P23.6H mesh parity
   guarantees still hold.

### P23.6I.2 — Remove `floor.height` from the canonical schema (format 6 → 7)

Scope: §5.4's v7 rung — version-aware floor keys, `CompiledFloor.height` removal,
floor-frame simplification in the shells, migration writes the floor record
without `height`, fixtures/benches updated. Acceptance sketch:

1. A format-7 document cannot declare `floor.height` (`unknown_key` by name).
2. Format 4/5/6 payloads still load and normalize forward; the pre-H
   normalization keeps using the legacy storey value at that boundary.
3. No compiled or rendered output changes from I.1 (it is a schema/plumbing
   slice, proven by unchanged geometry goldens).
4. `rg floor.height` in canonical wall-first code returns only compatibility-path
   hits.

## 9. Alternatives considered and rejected

| Alternative | Why not |
|---|---|
| **Cap removal only** (keep the persisted envelope, demote the field) | Smallest change and it unblocks taller Walls, but the Room ceiling stays a declared quantity — the Room-first residue the owner wants gone — and it leaves the field's meaning half-authoritative. |
| **One atomic slice / one format bump** (free heights + delete the field together) | Fewer versions, but one large diff that mixes a semantic change with schema plumbing, and no reviewable window where the rule change can be validated before the field disappears. Rejected in favour of staged; the reviewer may prefer it (§10). |
| **Stop compiling Room ceilings for wall-first documents** (true "no central ceiling") | The most permissive and arguably the most architecturally honest, but it removes visible geometry (both museum shells' `LayoutCeiling`) and is a presentation change needing its own visual pass. Registered as deferred. |
| **Per-Room authored ceiling height now** | Preserves today's appearance and gives creators explicit control, but adds a persisted Room field plus a new operation before the Wall-defined model has even landed. Deferred, and it is the natural follow-up if §6.2's lowering proves objectionable. |
| **Keep `floor.height` as a `max` floor on ceilings** (`max(walls, floor.height)`) | Preserves appearance in I.1 and then changes it in I.2 anyway; two behaviours for one model is worse than one deliberate change. |
| **A wall-first Floor-height editor** (the previously deferred D5 operation) | Editing a value that stops being authoritative is work in the wrong direction; cancelled by this proposal. |

## 10. Open questions for the reviewer

1. **Transition legs.** A chain connecting two existing Walls of different
   heights currently resolves to the named default (§5.2). Prefer the *lower*,
   the *higher*, or reject the leg? (Recommendation: default — a deliberate
   transition, never a silent guess.)
2. **Per-leg vs chain-level inheritance.** Per-leg is more truthful but means one
   gesture can birth Walls of two heights. Acceptable?
3. **Two bumps or one.** Accept the `5 → 6 → 7` ladder (§5.4), or collapse to a
   single bump with the field removed in the same slice?
4. **Envelope scope.** `max` per Room (ratified) vs the document-wide max Wall
   height. Per-Room enables inconsistent architecture; document-wide would
   preserve appearance for mixed documents. Confirm per-Room.
5. **Default value** for `WALL_AUTHORING_DEFAULT_HEIGHT` (proposed 3 m) and
   whether it should ever be project-configurable (proposed: no, this slice).
6. **Scheduling sign-off** on I.1/I.2 landing before P23.6a (§1), and on the
   PR #25 handling — merge H as-is plus a follow-up supersession note, or add the
   note into #25.
