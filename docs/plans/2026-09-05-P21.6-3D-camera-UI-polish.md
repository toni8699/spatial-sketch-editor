# P21.6 Plan: 3D Camera Visualization & 2D–3D Spatial Unification

**Status:** Approved for implementation (owner 2026-09-07; Interaction & Projection Standards addendum with corrected FOV solver, 24px pick clamp, observer-relative aspect, and drag-deferral contract applied). Prior: Changes Requested (source-level review 2026-09-07, Three.js `0.175.0`); rendering artifacts and frame-time impact still need browser validation via the §5 gate.
**Authority:** `docs/plans/2026-09-04-P21-unified-project-shell-spatial-reconciliation.md` + `docs/Design-specs/Design-specs.md` §10/§28 + `theme.md` (Spatial Invariants).  
**Objective:** Eliminate 3D camera visual noise, unify 3D camera nodes and paths with the 2D Plan standard across all themes, retire the yellow wireframe "object box" body proxy, and implement the ratified translucent cinematic frustum.

---

## 1. Fieldwork Reconciliation & Root Causes

Based on the verified codebase audit, 3D camera visualization currently suffers from four structural flaws:

1. **Theme Contamination & Hardcoded Hexes:** Zero 3D camera components read from `SCENE_PALETTE` or CSS variables. All helpers use hardcoded golds (`0xd6b35f`, `0xffcf67`, `0xffe29a`), light blue (`0x5bc8ff`), and pink (`0xff9ed2`). Because they are hardcoded, they clash with light mode (`porcelain-atelier`), clash with the 2D Plan standard, and drift between themes.
2. **The "Selection Outline Box" Unmasked:** The box appearing around selected cameras is **not** an object selection outline (`SelectionOutline` / `BoxHelper`). It is the virtual-camera body proxy in `lib/editor/camera/EditorCameraFramingHelpers.svelte:32-42`:
   ```ts
   const bodyGeometry = new BoxGeometry(0.28, 0.2, 0.38);
   const bodyMaterial = new MeshBasicMaterial({ color: 0xffcf67, wireframe: true, ... });
   ```
   A wireframe yellow crate appearing at the camera eye looks like a raw debug bounding box.
3. **The "Circus of Floating Spheres":** Up to 5 independent sets of spheres populate the 3D viewport simultaneously:
   * Gold octahedrons at nodes (`EditorCameraHelpers:36`)
   * Light-blue target spheres (`EditorCameraHelpers:37`)
   * Pale-gold path anchors (`EditorCameraPathHelpers:128`)
   * Gold FOV handles floating on the frustum edges (`EditorCameraFramingHelpers:57`)
   * Pink/blue view keyframe spheres (`EditorCameraViewHelpers:86,125`)
4. **Hollow Wireframe Frustum:** The frustum in `EditorCameraFramingHelpers.svelte` is 1px monochrome gold lines with **zero face fill**. It fails to communicate the camera’s spatial volume or field of view as an intersecting light cone.

## 2. Core Architectural Invariant: 2D–3D Spatial Parity

> **Sacred Rule:** Camera nodes and routes represent **authored spatial truth**, not UI chrome.  
> Just as the 2D Plan canvas is invariant `#F5F3EE` across all themes, **3D camera visualization must be identical across all themes.**

* **Sequenced Nodes:** Solid brand blue (`#2F8CFF` / `0x2f8cff`), white sequence number, crisp white keyline.
* **Unsequenced Nodes:** Emerald ring (`#10B981` / `0x10b981`), transparent center.
* **Camera Paths:** Solid brand blue (`#2F8CFF` / `0x2f8cff`), selected path highlighted (`#55A1FF` / `0x55a1ff`); retained/inactive paths keep today's gray dashed line (`0x8a8a8a`) — no second retained language.
* **Frustum Volume:** Translucent electric-blue face fill (9% opacity, bounded per §3.1 — overlapping layers accumulate) with crisp blue silhouette edges (1px `LineBasicMaterial` unless fat-line `Line2` is adopted per §3.2).

#### 2.2 Clean Camera Apex Fixture

  // ConeGeometry is centered on origin with tip at local +Y (+0.08 m).
  // The selected-body helper orients via mesh.lookAt(target), which points

  // derives orientation from eye/target + world-up with an abrupt fallback
  // near vertical. Nub, rectangle, handles, and preview MUST use that same
  // eye/target/up pose convention — no arbitrary authored roll.
  const apexMaterial = new MeshBasicMaterial({ color: 0x1e293b, toneMapped: false }); // dark graphite, zero lighting risk

* The nub is anchored to the camera node position and oriented along the camera forward axis, tip exactly at the eye, meeting the apex of the frustum rays.
* Preview-rig nub is parented to the virtual camera (`EditorCameraRig.svelte:312` carries a `position.z = 0.12` offset): account for that offset separately when applying the same tip-at-eye convention — do not reuse the selected-body translation blindly.

      │ \          / │
      │   \      /   │   (Hollow, no depth cues, monochrome gold 0xffcf67)

      │       \

#### 3.1 Translucent Frustum Volume Mesh
In `lib/editor/camera/editor-camera-framing.ts` and `EditorCameraFramingHelpers.svelte`:
* Construct a capped 4-sided pyramid mesh connecting the eye $(0, 0, 0)$ to the 4 far-plane corners — **6 triangles with consistent winding** (the old "4 triangles" file-map note was wrong: 4 side faces + 2 for the quad cap):
  * Left Face: `[Eye, TopLeft, BottomLeft]`
  * Right Face: `[Eye, BottomRight, TopRight]`
  * Top Face: `[Eye, TopRight, TopLeft]`
  * Bottom Face: `[Eye, BottomLeft, BottomRight]`
  * Far Plane Cap: `[TopLeft, TopRight, BottomRight]` + `[TopLeft, BottomRight, BottomLeft]` (winding consistent with side faces)
* Fixed vertex/index layout: allocate once at component init, update positions in place only when pose/FOV/aspect change, then recompute bounds. Never rebuild per tick.
* **Material Configuration:**
  ```ts
  const frustumFillMaterial = new MeshBasicMaterial({
    color: SCENE_PALETTE.cameraFrustumFill,
    transparent: true,
    opacity: 0.09,
    depthWrite: false,
    depthTest: true,
    side: THREE.DoubleSide, // default two-pass transparent DoubleSide; keep initially, no speculative optimization
    toneMapped: false
  });
  ```
* **Bounded transparency contract (replaces "without sorting artifacts" — that guarantee was incorrect):**
  * `depthWrite: false` prevents the fill from depth-occluding its own subsequent faces. It does NOT sort triangles or solve intersections with other transparent objects (Three.js sorts transparent *objects*, not triangles).
  * Opaque walls correctly obscure the fill via `depthTest: true`; abrupt truncation where the frustum intersects a wall is expected occlusion, not a bug.
  * Does not prevent near-plane clipping or coplanar depth artifacts.
  * Convex + uniformly colored pyramid is forgiving (identical overlapping color/opacity has low ordering sensitivity), but intersections with glass, transparent artwork, or other translucent helpers remain order-dependent.
  * Overlapping visible surfaces accumulate: two 9% layers ≈ **17.2%** effective opacity, not 9%. Do not make the fill carry essential information — perimeter/handle silhouette are the primary affordances (fill is near-invisible on white, subtle on black, can vanish on blue artwork).
  * No order-independent transparency for one selected helper.
* **Occlusion policy (explicit):** fill stays scene-occluded (`depthTest: true`); node discoverability through walls is preserved by markers/badges (§4.1/§4.3), which MUST visually distinguish hidden helpers. Do not mix depth-tested fill with non-depth-tested perimeter without documenting it (§3.2).

#### 3.2 Crisp Silhouette Edge Lines
* Restyle the boundary rays and far-plane rectangle to canonical blue. NOTE: WebGL `LineBasicMaterial` renders at **1px** regardless of any "2px" promise — do not spec 2px here. If 2 CSS px are required, use the already-installed fat-line (`Line2`/`LineMaterial`) implementation:
  ```ts
  const frustumLineMaterial = new LineBasicMaterial({
    color: SCENE_PALETTE.cameraFrustumLine,
    transparent: true,
    opacity: 0.75,
    depthTest: false,
    depthWrite: false,
    toneMapped: false
  });
  ```
* Documented split: fill is depth-tested (§3.1), perimeter/markers/badges are intentionally non-depth-tested for discoverability. A camera behind a wall therefore shows badge + outline while fill/connector disappear — intentional DCC behavior per the §3.1 occlusion policy, not a bug.
* All helper `MeshBasicMaterial`/`LineBasicMaterial` colors in this plan set `toneMapped: false` (retain normal color-space conversion) so helper blue reads identically under the AgX renderer. Revisit only if whole-frame postprocessing lands.

#### 3.3 Dashed Look-At Ray & Target Reticle

Preserve the current in-place position updates and refresh bounds when necessary.
  * World-unit dashes assume unscaled line geometry (`computeLineDistances` measures *local* positions; a later parent scale changes visible spacing) and become subpixel at distance / under foreshortening: fade the ray or switch to a quiet solid line below a projected-size threshold. Never rescale dash phase continuously during orbit.

#### 3.4 FOV Handles Stay Mounted (progressive disclosure rejected for P21.6)
* Owner ruling: keep the FOV handles mounted on the selected frustum — dragging them is the primary (and only) direct-manipulation FOV gesture in 3D (`EditorSelection.svelte:358` resolves drags from `camera-fov-handle` userData); there is no standalone Frame tool mode to gate them behind, so hiding them removes the affordance.
* Streamline instead: shrink `SphereGeometry(0.13)` → `0.09`, recolor to palette blue `#2F8CFF` with `toneMapped: false`. The frustum mounts only for the single selected camera, so two compact handles add no clutter.
* **Smaller visuals MUST NOT mean smaller controls — 24px minimum screen-space pick diameter (mouse baseline; touch/overlap still need inspector editing):** path anchors, FOV handles, and camera target reticles each provide an effective hit area of at least **24px diameter (12px radius)** at all observer distances/zooms via the invisible pick shell (`colorWrite: false`, `depthWrite: false`, `opacity: 1`). Per-frame clamp on the shell (perspective observer only; orthographic needs a different formula):
  ```text
  z         = positive observer-camera-space depth of handle center
            (guard: zero viewport height, centers behind / inside near plane)
  rWorld    = max(rBase, z × tan(effectiveVerticalFOV / 2) × 24 / viewportHeightCSS)
  shellScale = rWorld / shellGeometryRadius
  ```
  Inputs: **camera-space depth** (not Euclidean distance), **CSS pixels** (not drawing-buffer px), observer **effective vertical FOV** via `PerspectiveCamera.getEffectiveFOV()` (includes zoom). This is perspective sizing for small shells, not an exact projected-circle guarantee — validate off-axis and close-up cases. Overlap: larger shells overlap, so after existing semantic priority (nodes > view-keyframes > anchors > connections), arbitrate same-class overlaps deterministically by **closest projected center** (never incidental sphere-entry distance / traversal order). A fixed world-size shell without this clamp shrinks to 1–2px at range — verify at long range.
* **FOV-drag solver — evaluated-once with screen-space fallback (required — current `EditorSelection.svelte:471-504` + `editor-camera-framing.ts:125-137` have singularities that smaller handles make harder to recover from):**
  * Freeze the full drag basis at pointer-down (eye, forward, frozen `up`, `depth` from the authored pose); do NOT recompute the framing basis per move (world-up fallback flips abruptly near vertical).
  * Conditioning check at pointer-down (normalized vectors; heuristic, not a stability guarantee): `alignment = |v_ray · n_plane|`; threshold `0.15` ≈ 8.6° from grazing. **Lock the branch for the whole gesture — never switch solvers mid-gesture.**
  * Well-conditioned (`alignment ≥ 0.15`) — ray-plane with TRUE grab-offset preservation (recording `p₀` alone is insufficient; the update must use it) and signed handle identity (`sign = +1` top, `−1` bottom; replaces the `abs()` bug so crossing the center never inverts). All trig in radians; bounds reference `CAMERA_FOV.min/max` (10/120):
    ```text
    h₀ = depth × tan(FOV₀ / 2)
    h  = h₀ + sign × dot(pCurrent − p₀, frozenUp)
    h  = clamp(h, depth × tan(FOVmin / 2), depth × tan(FOVmax / 2))
    FOV = 2 × atan2(h, depth)
    ```
  * Ill-conditioned (`alignment < 0.15`) — virtual-slider fallback (Blender/Maya standard), immune to camera angle:
    ```text
    FOV = clamp(FOV₀ − (clientY − startClientY) × 0.2, FOVmin, FOVmax)
    ```
    Up-drag increases FOV for BOTH handles (acceptable slider behavior, differs from pulling the bottom handle outward) — show a vertical-slider cursor or brief hint when this mode engages.
  * Ongoing guards even on the locked branch: re-check intersection validity per move — if alignment becomes unsafe, the intersection lies behind the ray, or coordinates are nonfinite, **hold the last valid FOV without switching solvers**.
  * Preserve existing pointer capture, Escape-cancellation, orbit restoration, and single-undo-transaction behavior. One drag = one undoable gesture; no snap, reversal, NaN, or sudden clamp (see §5 gate).
* **Helper scheduling:** the framing helper currently allocates vectors/point arrays and calls `invalidate()` every task tick — do NOT extend that pattern to the fill/nub/ring/reticle. Skip unchanged updates; fixed layout + in-place attribute writes only.

### Slice 6: Viewport focus mode (collapsible side panels + fullscreen 3D)

Give the author room to work: independently collapsible left/right panels plus a combined fullscreen-3D mode. Shell chrome behavior, not camera visualization — folded here as the P21 closeout tail so it lands before the acceptance gate.

* **State:** session view store beside `gridVisible` (session-only, never `ProjectDocument`; a localStorage preference later is optional, not this slice). Independent left/right booleans plus a derived/combined focus flag.
* **Layout:** `EditorApp.svelte:2036-2058` grid — a shell layout mode collapsing `grid-template-columns` toward `0 1fr 0`. Toggles live in Row 2 Zone C (view utilities, per the P21+ chrome contract) with a keyboard shortcut and a status-bar hint. Sidebar (`EditorSidebar`) and `EditorInspector` keep selection/session state throughout.
* **Hard constraint:** hide via CSS grid only — **never unmount the 3D canvas**. Unmounting kills the Threlte context, texture caches, and the paused camera-preview session; collapsing is layout-only, same discipline as the existing `inert` Plan-cell pattern. (Threlte supports parent-driven canvas resize; the renderer updates size + active non-manual camera before main render — no remount needed.)
* **Focus-mode hardening (required):**
  * Preserve a nonzero center viewport with `minmax(0, 1fr)`; clip collapsed panel contents and mark them `inert` (zero-width tracks alone do not remove keyboard focus); restore focus sensibly when a panel holding the active input collapses.
  * No animated grid resizing in this slice — it repeatedly reallocates the drawing buffer and multiplies pixel work.
  * On resize, synchronize Line2 `resolution`, label-projector coordinates, and pointer/NDC coordinates with the resized viewport. Expected defects on miss are stale aspect / temporary stretch / one blank frame — not WebGL tearing. (`invalidate()` requests a frame; it does not itself re-sync every dependent projection.)
  * **Drag discipline: deferral (not lock/ignore, not rebase).** While any pointer-down gesture is active (node move, anchor drag, FOV pull, timeline scrub), focus-mode / sidebar-collapse requests are **deferred**: store ONE pending desired panel configuration (coalesce repeats) and apply it only after the gesture commits or cancels, pointer capture is released, and orbit controls are restored. Terminal coverage: `pointerup`, `pointercancel`, unexpected capture loss, and workspace exit — not just `pointerup`. `Escape` cancels the gesture first (rollback uncommitted transaction, restore prior state); the pending layout change may then apply under the same rule. Pointer capture alone does not prevent a viewport-move jump, which is why deferral (not mid-drag rebasing) is specified. Exception: browser-driven resizes cannot be deferred — cancel the active gesture cleanly if viewport geometry changes externally. Viewport resizes stay out of project history (session view store only).
  * **Framing-aspect rule (ruled): observer-relative.** Vertical FOV is the authored invariant (`camera.fov`); horizontal FOV derives per-frame as `FOVh = 2·atan(tan(FOVv/2)·aspect)` from the **actual 3D viewport dimensions**. Focus mode widens the far-plane rectangle while preserving vertical FOV — this shows the framing for a visitor viewport **with the same aspect ratio** (not "exactly what a visitor sees": observer viewpoint ≠ authored camera viewpoint). A future authored "Crop / Output Aspect Gate" may override this; for P21 the responsive viewport aspect is canonical.
  * Restore the previous independent left/right configuration when exiting combined focus mode.
  * Clarify "fullscreen 3D": the specified column collapse leaves ribbon, status, and potentially Timeline visible. The §5 criterion below matches that intent — do not promise chrome-free fullscreen.
* **Acceptance:** per-side collapse + combined focus mode; canvas resizes cleanly (`invalidate()`, no context loss); Line2 widths, labels, and picking stay aligned at different DPRs incl. paused preview; gizmo drag, preview pause/resume, and selection survive a collapse cycle; shortcut discoverable from the View menu. ### P21.6 Addendum: Interaction & Projection Standards (owner rulings + review corrections)

1. Frustum aspect ratio: follows the active observer viewport aspect ratio; vertical FOV is the authored invariant (`FOVh = 2·atan(tan(FOVv/2)·aspect)`).
2. Drag discipline: focus-mode / sidebar collapses are **deferred** while a pointer-down gesture is active (one coalesced pending config; applied after commit/cancel + capture release + controls restore; covers `pointercancel`/capture-loss/workspace-exit; `Escape` cancels first; external browser resizes cancel the gesture).
3. FOV drag solver:
   - Evaluated once at pointer-down: if `|ray·normal| < 0.15`, lock to screen-space dY slider (`FOV = clamp(FOV₀ − ΔclientY×0.2, CAMERA_FOV.min, CAMERA_FOV.max)`).
   - If `≥ 0.15`, use frozen-basis ray-plane with `h = h₀ + sign·dot(pCurrent − p₀, frozenUp)` + clamp + `FOV = 2·atan2(h, depth)` (signed top/bottom identity, no `abs()`).
   - Hold last valid FOV on mid-gesture invalid intersections; never switch solvers mid-gesture.
4. Screen-space pick clamping: invisible pick shells maintain a minimum **24px projected diameter** via `rWorld = max(rBase, z·tan(effectiveFOV/2)·24/viewportHeightCSS)` (camera-space depth, CSS px, `getEffectiveFOV()`); same-class overlaps arbitrate by closest projected center.
