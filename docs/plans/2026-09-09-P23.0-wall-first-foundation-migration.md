# P23.0 — Wall-first foundation, compatibility and spatial migration

**Parent:** [P23 — Layout Depth umbrella](2026-09-07-P23-layout-depth-minimum-build.md)  
**Status:** `implementation-ready` — coupled Foundation Gate F0; cannot ship independently of P23.8.  
**Evidence:** H1/H2/H3/H5 complete; owner reconciliation ratified 2026-09-09.  
**Current behavior note:** product code remains Room-owned / Room-local until F0 ships.

P23.0 owns the schema/compatibility/migration/cutover halves of the P23 Foundation Gate. P23.8 owns the topology/Room-reconciliation middle. New-schema writes remain disabled until the complete gate passes.

## Foundation sequencing

```text
P23.0a — schema + compatibility scaffolding
NO new writes
        ↓
P23.8 — topology + Room regions
        ↓
P23.0b — migration + compiler/runtime/editor cutover
        ↓
F0 acceptance
        ↓
enable wall-first writes
```

## Outcome

Museum can recognize both legacy and new Layout/Scene data, preserve old saved/published meaning, migrate lossless projects to one wall-first Layout + world-local Scene/Camera model, and run the editor/visitor through one canonical compile/runtime path.

## P23.0a — target schema and identification

Introduce wall-first authored identities conceptually equivalent to:

```ts
type LayoutJunction = {
  id: string;
  point: LayoutVec2;
};

type LayoutWall = {
  id: string;
  startJunctionId: string;
  endJunctionId: string;
  role: 'boundary' | 'partition';
  thickness: number;
  height: number;
};

type LayoutOpening = {
  id: string;
  wallId: string;
  kind: 'door' | 'window';
  offset: number;
  width: number;
  height: number;
  sillHeight: number;
  profile: 'rectangular' | 'rounded' | 'pointed';
  connectsRoomIds?: [string, string];
};

type LayoutRoom = {
  id: string;
  name: string;
  boundary: OrientedWallRef[];
  floorThickness: number;
  ceilingThickness: number;
};
```

The exact numeric format version is chosen only after implementation rechecks historical format usage. Required policy:

- new Layout shape has an explicit format discriminator;
- new Scene shape has an explicit format discriminator;
- missing version is accepted only through an explicit recognized legacy decoder;
- package format and nested Scene/Layout document versions are separate concepts;
- new saves serialize only the new canonical formats after F0 writer enable.

`LayoutObject[]` remains document-level and project/world-local; do not move objects under Floors as part of this schema change.

## Identity rules

- Junction ID is the only normal-authoring connectivity authority.
- Wall IDs are document-global and survive deformation.
- Wall start/end orientation is stable and identity-bearing because opening offsets are measured from start.
- Opening IDs are document-global in the new schema.
- Room IDs remain product identities, not face-extractor IDs.
- IDs never derive from coordinates, traversal order, timestamps or random allocation.

## Compatible decode result

Do not hide migration state inside ordinary validation. Use an explicit compatibility result shape, conceptually:

```ts
type CoordinateSpace = 'legacy-room-local' | 'project-world';

type CompatibleProjectDecode =
  | { kind: 'wall-first'; project: ProjectDocument; sceneSpace: 'project-world' }
  | { kind: 'migrated'; project: ProjectDocument; report: MigrationReport; sceneSpace: 'project-world' }
  | {
      kind: 'legacy-compatible';
      project: LegacyProjectDocument;
      report: MigrationReport;
      sceneSpace: 'legacy-room-local';
    };
```

Exact names may follow existing codec conventions. The invariant is explicit state: downstream runtime preparation must know whether Scene values still require Room-frame resolution.

## Trustworthy Room-frame context

Legacy Scene conversion requires the exact Room frames that gave the stored local values meaning.

Acceptable provenance includes:

1. Scene + Layout decoded from the same recognized legacy Project snapshot/version;
2. a future package that explicitly carries/binds the required legacy frame context;
3. an explicit user-supplied Room-ID → legacy-frame mapping from an import UI designed for that purpose.

Not acceptable:

- Room IDs merely happen to match the currently open Project;
- proximity/containment suggests a likely Room;
- current Room frame differs from the source but IDs match;
- missing frames are replaced with identity transforms.

Missing/untrusted frame context rejects conversion with a dedicated diagnostic before document install.

## Full Project migration

For lossless/deterministically adaptable legacy Projects:

```text
strict legacy Project/Layout/Scene decode
→ capture trusted legacy Room registry
→ resolve Scene/Camera room-local values to project/world space
→ migrate Layout segment/opening records to canonical Junctions/Walls/Openings
→ P23.8 candidate faces + Room reconciliation
→ validate canonical new Project
→ install as one editable baseline
```

Scene conversion happens **before** Room frames stop being authoritative.

### Scene entity transforms

Preserve world transforms using the actual old Room frame composition. Arbitrary entity rotations must be tested; do not implement migration as only `yaw += roomYaw` unless existing rotation conventions prove that mathematically sufficient.

Conceptually:

```ts
worldMatrix = legacyRoomFrameMatrix * localEntityMatrix;
worldTransform = decompose(worldMatrix);
```

Preserve entity IDs, asset IDs, materials, light semantics and other non-spatial data.

### Clusters

Current clusters have Room ownership but no independent transform.

Migration:

- convert member entity transforms to world/project space;
- preserve cluster ID/name/member order;
- remove Room as a spatial grouping constraint;
- do not create a new cluster transform frame;
- adapt creation/membership validation so same-Room membership is no longer required after cutover.

### Camera

Resolve through the legacy Room frame before removing ownership:

- node eye position;
- node `cameraTarget`;
- room-owned position-path anchors;
- room-owned target waypoints;
- room-owned directional view-key targets.

Camera records already stored without `roomId` remain byte-equivalent in spatial meaning.

Connection endpoint positions remain derived from migrated node positions. Do not add a second persisted endpoint representation.

## Standalone `scene.json` / `.scenepack`

Current `.scenepack.zip` contains Scene state without Layout Room frames. That means a legacy Room-local Scene package is not independently convertible unless trustworthy frame context is supplied.

Required import behavior:

```text
new world-local Scene
→ parse directly

legacy Room-local Scene + trusted source/user frame mapping
→ convert once to world-local

legacy Room-local Scene + missing/untrusted frame context
→ reject: missing/untrusted legacy Room-frame context
```

Do not guess from the currently open project merely because Room IDs match.

New package export after F0 writes the explicitly identified world-local Scene format. Package manifest version remains separate from Scene schema version.

## Read-only legacy compatibility path

Lossless migration is not guaranteed for every current valid legacy Project.

Examples requiring compatibility instead of silent normalization:

- coincident Room-owned walls disagree on thickness/openings/curve semantics;
- legacy curves cannot yet be represented exactly by the new authored Wall shape;
- legacy portal relation is valid under old rules but violates the stricter new adjacency contract.

Required shared path:

```text
raw legacy data
→ compatible decoder
→ prepare canonical runtime/compile source
→ compileLayoutGeometry()
→ Plan / 3D / visitor
```

There may be separate decode/preparation adapters, but one geometry compiler/output model remains authoritative.

### Conflicting coincident walls

Compatibility preparation keeps both physical records where that is required to preserve old authored appearance/meaning. It must not pretend they are one canonical new Wall.

Such a Project:

- remains readable/renderable;
- is read-only with migration diagnostics;
- cannot be saved as new-schema until conflicts are explicitly resolved;
- must remain visitor-readable if already published.

### Curved legacy geometry

Never flatten a legacy `auto-bezier` boundary to straight segments as a lossless migration.

Implementation may use either:

- a fidelity-preserving compatibility geometry variant accepted by the canonical compiler; or
- an explicit read-only legacy compatibility source converted at compile preparation.

Either way, Plan/3D/visitor share the same final compiler/output pipeline.

## Runtime coordinate-space preparation

A read-only legacy Project may retain Room-local Scene data. A migrated/new Project stores project/world-local Scene data.

Runtime preparation must branch once, before rendering/navigation:

```ts
if (decode.sceneSpace === 'legacy-room-local') {
  resolvedScene = resolveLegacySceneThroughRoomFrames(...);
} else {
  resolvedScene = decode.project.scene;
}
```

After this boundary, consumers operate on one runtime/world representation. No Plan, renderer, camera evaluator or visitor component may apply Room transforms again to already world-local content.

Acceptance must include a regression specifically catching double-transform.

## Portal compatibility

Old `connectsRoomIds` accepted relations without proving physical adjacency. Compatibility mode must preserve that legacy interpretation so old Projects/publications remain readable.

- do not silently clear an old nonadjacent relation on read;
- do not reject an old immutable published release only because it violates new-schema adjacency rules;
- expose a migration diagnostic;
- block new-schema Save until the relation is explicitly resolved/removed.

P23.8/P23.3 define the stricter new-schema relation contract.

## Compiler/query cutover

Evolve the existing `compileLayoutGeometry()` boundary rather than introducing another compiler.

Target consequences:

- physical Wall geometry compiles once per `wallId`;
- Junction joins/caps are canonical compiler output;
- Room floors/ceilings compile from accepted persistent Room regions;
- Opening cuts derive from Wall-hosted openings;
- query/selection identities use `junctionId`, `wallId`, `openingId` for physical architecture;
- Room-derived semantic/floor query records retain `roomId`;
- Plan/SVG and 3D renderers never rebuild topology from authored records independently.

Legacy-compatible compile preparation may preserve legacy records but must normalize them into the same compiler source/output contracts.

## Editor-adapter cutover before writer enable

F0 is not done merely because codecs/compiler work.

Audit every editor path that can mutate legacy Room-owned/Room-local state. Before new writes enable, each path must be one of:

- **adapted** to write the new canonical model;
- **read-only** over compatibility state;
- **explicitly disabled** with a reason until its later child slice deepens it.

Minimum audit list:

- Layout selection/hit identity;
- Layout/Room/Wall/Opening Inspector controls;
- whole-Room drag/rotate behavior;
- vertex editing / Add Vertex;
- Layout 3D gizmo candidates;
- opening creation/editing;
- object placement fields that expose Room ownership;
- Scene placement creation;
- Camera node creation;
- Camera path/key editors with optional Room ownership;
- cluster creation/member insertion;
- unified project tree nesting;
- Room delete blockers/cleanup;
- project semantic validation;
- Preview preparation;
- visitor cold runtime.

Unsupported old mutation paths must never remain active against a new document.

## Room transform semantics after cutover

`LayoutRoom.frame` is legacy migration machinery, not a target authoring parent for Scene/Camera.

After migration:

- editing/moving Walls/Junctions does not move Scene/Camera content;
- Room identity follows the derived face independently of content coordinates;
- a future explicit grouped operation may move architecture plus chosen content, but that is outside P23 minimum.

## History

Schema migration occurs before the normal editor-session history baseline and creates no user-visible command stack.

Normal new topology edits rely on current exact snapshot semantics:

- committed allocated IDs are part of the document snapshot;
- Undo restores exact previous state;
- Redo restores exact new state;
- correspondence/ID allocation is never rerun on Redo.

No CRDT/event-sourcing/command-log rewrite is part of P23.

## F0 acceptance checklist

P23.0 may complete only when P23.8 is also complete and all of these pass:

- explicit Layout format identification;
- explicit Scene format identification;
- legacy Project migration with trusted source Room frames;
- arbitrary Scene rotation world-transform preservation;
- Camera eye+target/anchor/waypoint/view-key preservation;
- standalone legacy Scene with trustworthy mapping migrates;
- standalone legacy Scene without trustworthy mapping rejects specifically;
- legacy-compatible Scene resolves through Room frames once;
- new/migrated world Scene receives no second Room transform;
- compatible shared legacy walls/openings migrate losslessly;
- conflicting coincident walls/openings remain read-only/renderable;
- legacy curves remain readable without flattening;
- legacy nonadjacent portal relation remains compatibility-readable but blocks new Save;
- old active published Project cold-loads without rewriting stored bytes;
- new wall-first Project compiles identically for editor Preview and visitor;
- selection/Inspector/gizmo/creation adapter audit has no legacy mutator capable of writing stale data;
- all unsupported adapters are explicitly disabled;
- only after all above: enable new-schema Save/write paths.

## Non-goals

- P23.1 precision UX;
- P23.2 snap depth;
- P23.9 continuous Wall sketch UX;
- migration conflict-resolution UI beyond clear diagnostics/read-only blocking;
- general curve topology;
- automatic proximity repair;
- new composite history architecture;
- Room-based replacement ownership field such as transitional `SpatialOwner` unless direct migration proves impossible in implementation and returns for owner review.
