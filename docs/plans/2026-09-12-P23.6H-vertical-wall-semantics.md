## Why this slice exists

P23.6 shipped selected-Wall exact Length / Angle / Thickness editing and explicitly
**deferred** per-Wall Height editing, for a correct reason: the canonical compiler,
bounds, mesh construction and Opening fit all derive vertical geometry from
`floor.height`, so an editable `LayoutWall.height` would be a durable
authored-state field with no authoritative rendering effect
([P23.6 plan §Selected Wall precision](2026-09-08-P23.6-architectural-drafting-visual-pass.md)).

P23.6H closes that seam. The goal is not "restore a Height input"; it is to give
per-Wall height one complete semantic path:

```text
LayoutWall.height
→ canonical validation (range + Opening fit)
→ compileLayoutGeometry()
→ compiled Wall physical sections + vertical bounds
→ shared editor + visitor Wall mesh
→ Inspector exact edit
→ one deterministic Layout history entry
```

One Layout authority, one compiler path. No UI-only, editor-only or visitor-only
interpretation of Wall height may remain.

## Product outcome

A creator selects a canonical Wall and sets its physical height. A Wall may be
shorter than the Floor height while remaining the same authored Wall and keeping
the same X/Z Room topology.

Examples: full-height room boundary; 1.2 m exhibition partition; 2.0 m
freestanding/display Wall; a partial-height Wall that still defines a Room
boundary.

Changing Wall height changes its 3D physical geometry. It does **not** by itself
change X/Z topology or Room identity. Plan stays X/Z authoring: Height is entered
in the Inspector and appears in 3D; Plan gains no Y drag affordance.

## Approved semantic decisions

### D1 — Authoritative physical extent

`bottomY = floor.elevation`, `topY = floor.elevation + wall.height`.
`LayoutWall.height` is the authoritative physical height of that Wall, measured
upward from the Floor elevation. It is finite, strictly positive, per physical
Wall, shared by both sides of the Wall, and consumed by the compiler, bounds,
mesh inputs and Opening fit. No Room, Scene entity or renderer owns Wall height.

### D2 — Height range (P23 minimum)

```text
0 < wall.height <= floor.height
```

P23.6H is **partial-height** Wall semantics, not taller-than-Floor or multi-floor
Wall semantics. `floor.height` is therefore simultaneously (a) the birth default
and (b) the Floor-level vertical envelope / maximum supported Wall height.

Do not expand H into multi-floor Walls, per-end heights or arbitrary profiles.

### D3 — Birth rule

For every semantic Wall creation after H:

```ts
wall.height = floor.height   // the baseline document's own floor.height
```

`floor.height` stops being a *live* authority after birth: changing Floor height
must not silently rewrite authored Wall heights (see D5). No Wall-birth default
literal may remain anywhere.

### D4 — Topology purity

Wall height is **not** part of Plan face extraction. Room topology continues to
derive from Junction connectivity + Wall X/Z geometry + `role`. Changing only
`wall.height` must not create, retire, split or merge Rooms, and must not change
Wall ID, Junction ID, Opening ID or `role`. Never infer Room topology from
whether a Wall reaches the ceiling.

### D5 — Floor-height interaction

Wall-first Floor height is **currently immutable in the editor** (see Evidence
E6): the only Floor-height input lives in the legacy room Inspector branch and
never reaches a wall-first document. H does not add a Floor-height editor.

The invariant `wall.height <= floor.height` is nevertheless pinned canonically so
that any future Floor-height operation must obey it: such an operation must
**reject** when it would push an existing authored `wall.height` above the new
Floor height. Silently clamping/truncating Walls is forbidden. H records this as
a canonical gate (`validateWallFirstWallHeights`, §Implementation seams S3) with
no new user-facing Floor-height operation.

### D6 — Openings fit the hosting Wall

Wall-first Opening vertical fit becomes host-Wall based:

```text
opening.sillHeight + opening.height <= wall.height + epsilon
```

At every wall-first validation/compiler gate. Legacy (Room-owned) documents keep
their existing `floor.height`-based rule byte-for-byte.

If a Wall-height edit would invalidate a hosted Opening: reject atomically,
preserve the previous Wall height, preserve the Opening, write zero history.
Never clamp, resize, move or delete the Opening.

### D7 — Historical compatibility (the pre-H decision)

**The problem.** Every wall-first document written before H stores a
`wall.height` that was **not** authoritative for rendered geometry. Confirmed
current behavior:

- `planWallChain()` / `planWallSegment()` birth Walls with
  `WALL_CHAIN_DEFAULTS.height = 3`
  (`packages/layout-core/src/layout-wall-chain.ts`), i.e. a **fixed** default,
  not the Floor height;
- `layout-migration.ts` initializes `height: floor.height`;
- Wall split (`layout-wall-noding.ts`) and isolated-Room duplicate
  (`layout-duplicate.ts`) preserve the source Wall height;
- nothing in `apps/**` reads `wall.height` at all (probe: zero matches);
- the compiler renders every Wall from `floor.elevation` to
  `floor.elevation + floor.height`.

So a valid pre-H document can carry `height: 3` on a 4 m Floor and still render
4 m tall (probe-verified), and the codec accepts `height` above `floor.height`
(probe-verified). Simply trusting stored values would visibly change old
projects, and a numeric mismatch cannot establish author intent (there was no
Wall-height authoring UI before H).

**Decision.** Pre-H wall-first documents are migrated at the compatibility
boundary to the *previously visible* floor-derived extent, then read as the new
authoritative model:

```text
formatVersion 4 payload (pre-H)
→ existing explicit version dispatch (KNOWN_LAYOUT_FORMAT_VERSIONS)
→ validate with the pre-H rule set
→ normalize: every wall.height := document.floor.height
→ canonicalize to formatVersion 5 (authoritative Wall height)
→ one decode result kind, unchanged consumers
```

Concretely:

- `LAYOUT_WALL_FIRST_FORMAT_VERSION` becomes `5`;
  `KNOWN_LAYOUT_FORMAT_VERSIONS` becomes `[4, 5]` (keep 4 known — do **not**
  invent a new format system; this is the existing versioned compatibility path
  that `layout-compat.ts` already owns).
- Version `4` is the pre-H format: no `wall.height <= floor.height` rule, and its
  decode path normalizes `wall.height := floor.height` before returning. Walls
  that already equal the Floor height (the migration and default-3-on-3 cases)
  are unchanged; a `3`-on-`2.5`-Floor Wall normalizes to `2.5` and keeps its old
  visible extent.
- Version `5` is the authoritative format: the range rule (D2) is a canonical
  codec rule.
- `decodeLayoutValueCompatible()` keeps returning `kind: 'wall-first'` (with an
  additive `migratedFromVersion?: 4` field) so
  `classifyLayoutFormat` / `LAYOUT_MUTATION_POLICY` / `prepareCompatibleRuntime`
  / `decodeProjectCompatible` need no new branch and mutation policy stays
  `adapted`. Additive result fields only; no consumer fork.
- Mutable project migration: loading a `4` project yields the normalized `5`
  document in memory; the next Save writes `5`. One-way, no user-visible
  migration command (P23.7 owns end-to-end Save/Load acceptance).
- Immutable publications: stored release bytes are never rewritten. A published
  pre-H snapshot decodes through the same boundary, so a `4` snapshot keeps
  rendering exactly its old floor-derived Wall extent. Reproducibility is
  preserved through the versioned compatibility path, not by mutating stored
  JSON.

**Regression fixtures for historical documents are mandatory** (see Tests).

## Authority boundaries

Preserved / not introduced:

- `LayoutDocument` and `SceneDocument` remain separately owned; H touches Layout
  only.
- One canonical geometry path
  (`LayoutDocument → compileLayoutGeometry() → compiled/query data →
  Plan/3D/visitor`). No second editor-only or visitor-only compile path.
- One canonical Layout selection authority. H adds no selection slot, no
  Inspector-local entity, no hierarchy-local truth.
- One history/mutation path: the existing guarded Layout transaction
  (`layout-mutation-runner.ts` + `EditorStore.begin/commit/cancelLayoutTransaction`).
- Plan stays X/Z authoring; Arrange stays owner-aware; visitor/editor isolation
  stays intact.

H owns: historical Wall-height compatibility; the Wall birth rule; Wall-height
validation; compiler/bounds vertical semantics; host-Wall Opening fit;
editor/visitor physical parity; the Height exact mutation + history.

## Exact in-scope behavior

1. `LayoutWall.height` is authoritative for physical Wall vertical extent.
2. New Walls birth at the document Floor height.
3. Height is editable per selected canonical Wall through one planner, one
   history entry.
4. Range rule enforced canonically; violating values reject with a clear reason.
5. Compiler emits authoritative Wall vertical sections and bounds; Room/Floor
   envelopes stay Floor-derived.
6. Opening vertical fit is host-Wall based for wall-first documents; legacy
   documents are unchanged.
7. Lowering a Wall below a hosted Opening's top rejects atomically.
8. Editor and visitor render the same compiled Wall extent for the same
   document.
9. Pre-H documents keep their previously visible Wall extent through the
   version-4 normalization boundary.
10. Plan X/Z geometry, snap candidates, hit geometry, Room polygons and
    selection identity are unaffected by a height-only change.

## Explicit non-goals

- sloped Wall tops; per-end heights; arbitrary/curved vertical profiles;
- multi-floor Walls; Floor elevation editing expansion;
- automatic ceiling generation; ceiling attachment; Room volume semantics;
- wall-height constraints/relations; bulk or multi-Wall height editing;
- Plan Y-axis manipulation; vertical drag handles;
- Scene-object vertical solving; automatic Opening resize/move/delete;
- Room topology derived from Wall height;
- a wall-first Floor-height editor;
- a second compiler, second mesh builder, or a visitor-specific geometry fork;
- canonical 3D Wall picking/highlight (explicitly deferred — see §Deferred).

- `decodeLayoutValueCompatible()`: when the payload declares `formatVersion: 4`,

  before the wall array (`readFormatVersion`), so thread it into
  `parseDocument` → `parseWall` (one parameter; no second codec).

### S1b — The single compatibility-normalization boundary

Two different things must not be confused, or H will quietly grow a second
migration path:

**Compatible read/decode — owns the v4 → v5 normalization, exactly once.**

```text
format-4 payload
→ validate under format-4 semantics
→ normalize: every wall.height := document.floor.height
→ return a canonical format-5 in-memory document
```

**Canonical Save validation — receives canonical current-format state only.**

`validateWallFirstProject()` / `serializeWallFirstProject()`
(`packages/project-model/src/wall-first-project.ts`) and
`serializeWallFirstLayoutDocument()` (`packages/layout-core/src/layout-wall-first-codec.ts`)
validate/serialize what the editor already holds. Their input contract is
canonical current-format state; they are **not** a migration boundary and must not
silently normalize historical payloads. A raw format-4 payload that bypassed the
compatible decode is therefore **rejected fail-closed** by the v5 range rule
rather than quietly rewritten. The implementation task must not describe these
writers as running the compatibility migration unless the task explicitly changes
their upstream input contract (it does not in H).

Invariant to state in code comments and tests:

```text
compatibility normalization happens once, at the compatible read/decode boundary;
canonical validators and writers operate on canonical current-format state and
never silently normalize historical payloads.
```

Enforcement point (as implemented): the two canonical *writers* named above —
`serializeWallFirstLayoutDocument()` throws and `validateWallFirstProject()`
reports `unsupported_format_version` via the shared
`wallFirstCanonicalFormatVersionIssue()` rule. The **tolerant** validators
(`validateWallFirstLayoutDocument`, the shared `validateProject`) keep accepting a
pre-H payload on purpose: the compatible decode must validate before it
normalizes, and the API publication read path loads already-stored v4 releases
through `validateProject`. Adding the writer gate there instead would break
stored publications — do not "fix" that later without a compatibility plan.

Required regression assertion: **after a compatible load of a format-4 payload,
the document handed to the canonical Save path is already format 5** (i.e. Save
validation sees a v5 document and never needs a normalization branch).

## Mutation / history behavior

- One successful Height edit → exactly one Layout history entry through the
  existing guarded transaction (`layoutMutationRunnerFor` + `EditorStore`).
- Undo restores the exact previous `wall.height` and the resulting compiled
  vertical geometry; Redo restores the edited value and geometry.
- Rejected (unknown Wall, non-finite, non-positive, above Floor envelope,
  Opening-invalidating), blank, and no-op edits → zero history entries, no
  durable mutation.
- Blank input rejects before the planner runs (presentation) and the planner
  independently rejects non-finite values (authority).

## Failure / rejection behavior

| Condition | Result |
|---|---|
| Unknown Wall | reject `unknown_wall`, message names the ID |
| Non-finite / ≤ 0 / blank | reject (presentation for blank, planner for non-finite) |
| `height > floor.height` | reject `invalid_value`, message names the Floor envelope; never clamp |
| No change | reject `no_op`; zero history |
| Hosted Opening no longer fits | reject atomically; Wall height, Opening and history unchanged |
| Candidate fails codec/topology/compile | reject; no mutation, no history |

## Compatibility / migration consequences

- **Format:** `LAYOUT_WALL_FIRST_FORMAT_VERSION` 4 → 5. Version 4 stays loadable
  and normalizes deterministically (D7). No new format system.
- **Mutable projects:** a loaded version-4 project becomes a version-5 document in
  memory; the next Save writes version 5 with `wall.height = floor.height` on
  Walls that differed. Users see no visible change (the old render was
  floor-derived).
- **Save/Load:** `serializeWallFirstLayoutDocument` writes version 5;
  `validateWallFirstProject` (`packages/project-model/src/wall-first-project.ts`)
  validates through the version-aware codec; `layoutCanonicalJson` in
  `layout-preview-state.svelte.ts` follows automatically.
- **Immutable publication/runtime:** stored release JSON is never rewritten. The
  visitor cold path (`visitor-cold-runtime.ts` → `prepareCompatibleRuntime()` →
  `decodeProjectCompatible()` → `decodeLayoutValueCompatible()`) normalizes a
  version-4 snapshot in memory, so old publications keep their old appearance and
  `decodeKind: 'wall-first'` (no runtime fork).
- **Migration:** `migrateLegacyLayoutDocument()` output is version 5 and already
  sets `height = floor.height`; no migration change beyond the version constant.
- **One normalization boundary:** the v4 → v5 rewrite happens only in the
  compatible read/decode path (S1b). Canonical Save validation
  (`validateWallFirstProject`, `serializeWallFirstLayoutDocument`) receives
  format-5 state and never normalizes; a stray format-4 payload fails closed there
  instead of being silently rewritten.
- **API publication validation:** `apps/api/src/publication-persistence.ts`
  currently validates with the legacy `validateProject` and compiles through the
  legacy `compileLayoutGeometry` entry. H does not change that file; P23.7 owns
  the end-to-end new-schema publish path. H only requires that the canonical
  wall-first decode/compile path used by editor, Preview and visitor is
  height-correct.

## Deterministic identity requirements

- Wall/Junction/Opening/Room IDs are never affected by a height edit.
- No allocation of any kind occurs during a height edit.
- Normalization for version-4 documents is a pure, order-preserving field rewrite
  (no ID or ordering change) so Save-diff and history baselines stay comparable.
- `WALL_CHAIN_DEFAULTS` no longer contributes a runtime height, so the same
  authoring input on the same Floor document produces the same Wall heights.
