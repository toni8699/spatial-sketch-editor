# P23.9 — Wall / Partition sketching

**Parent:** [P23 — Layout Depth umbrella](2026-09-07-P23-layout-depth-minimum-build.md)  
**Status:** `implementation-ready` — blocked by Foundation Gate F0, P23.1 precision and P23.2 snap infrastructure.  
**Evidence:** H1/H2/H3 complete; owner reconciliation ratified 2026-09-09.

## Outcome

A creator can sketch architecture directly as continuous Walls/Partitions in Plan. Rectangle and Polygon remain convenience tools, but they produce the same canonical Junction/Wall records rather than a parallel Room-polygon system.

## Primary workflow

```text
Choose Wall
→ click first point
→ preview segment
→ snap / type exact length where supported
→ click next point
→ continue chain
→ Finish open chain or Close loop
```

Partition uses the same interaction with `role: 'partition'`.

## Draft versus authored state

The in-progress chain is transient editor/session state.

- clicks extend the draft only;
- Backspace removes the latest draft segment/point;
- Escape cancels the entire draft with no document/history change;
- Finish/Close plans the complete topology mutation;
- successful Finish/Close commits **one** Layout history entry;
- invalid complete candidate commits nothing.

Do not persist half-finished draft state into `LayoutDocument`.

## Open chains are valid architecture

A valid open Wall/Partition chain may be committed without producing a Room.

Room creation is not a modal confirmation step. After a boundary-Wall commit, P23.8 derives candidate enclosed faces and reconciles persistent Rooms automatically where supported.

## Wall versus Partition

### Wall

Creates `role: 'boundary'` Walls. They participate in Room face extraction.

### Partition

Creates `role: 'partition'` Walls. They are real physical Walls and use the same:

- Junction topology;
- thickness/height fields;
- compiler/mesh machinery;
- opening hosting where semantically valid;
- selection/query IDs;
- precision/snap tools.

But they do not divide semantic Rooms.

No generic `LayoutObject.kind = box` is presented as a Partition.

## Junction/connectivity semantics

Snapping is a suggestion; committed topology is explicit.

### New endpoint near existing Junction

If the snap winner is accepted, reuse that Junction ID.

### New endpoint on Wall interior

Acceptance invokes P23.8 canonical Wall subdivision and connects to the resulting Junction.

### Proper Wall crossing

If the chosen operation permits an X crossing, plan all required Wall subdivisions/Junction creation before commit. Installed new-schema data must not contain an un-noded visual crossing.

### Collinear overlap

Reject. Do not auto-merge/trim/choose one Wall.

## Rectangle convenience tool

Rectangle is a bounded multi-Wall creation frontend.

It creates:

- four Junctions, subject to explicit reuse/snap where valid;
- four straight Walls using the chosen role;
- one complete candidate operation;
- Room reconciliation through P23.8 if boundary Walls form a supported enclosure.

Rectangle is not a distinct persisted Room geometry kind.

Initial interaction may be two-corner drag/click with exact width/depth entry integrated from P23.1. Rotated rectangle authoring may be added only if the existing Plan interaction model can keep the gesture deterministic without creating an unrelated transform mode.

## Polygon convenience tool

Polygon is simply a multi-click closed boundary/partition chain.

- same Junction/Wall records;
- same Close/Escape/Backspace semantics;
- same P23.8 topology gate;
- no standalone polygon truth.

## Precision integration

P23.1 provides exact straight-Wall semantics. During a draft, where supported, the current segment may accept:

- exact length;
- horizontal/vertical or explicit angle constraints already defined by P23.1/P23.2;
- typed meter values that bypass gesture grid snapping.

Do not build a persistent constraint solver. Exact draft input resolves into final endpoint coordinates/Junction topology for the committed candidate.

## Snap integration

Consume P23.2's one snap pipeline:

```text
tool/context validity
→ semantic feature priority
→ screen distance
→ stable ID/key
```

Draft candidates may include:

- Junction/endpoints;
- Wall midpoint;
- Wall interior projection;
- valid intersection;
- orthogonal guide;
- bounded extension;
- grid fallback;
- parallel/perpendicular/angle aids only where P23.2 explicitly supports them.

Reference acquisition remains screen-space. Model topology tolerances remain H3-owned.

## Visual draft feedback

P23.6 owns the final visual polish, but P23.9 requires a functional transient presentation:

- committed Walls visually distinct from draft;
- current segment preview;
- active snap winner/guide;
- invalid candidate state;
- clear first/current point;
- explicit role indication Wall versus Partition.

Presentation never becomes geometry truth.

## Selection behavior after commit

Use existing deterministic selection authority adapted by F0.

Recommended minimum:

- successful one-segment chain selects the created/retained top-level Wall as appropriate;
- successful multi-segment chain selects a deterministic primary created Wall or resulting Room according to existing selection UX conventions finalized during implementation recheck;
- no multi-selection is invented solely for chain creation;
- failed/cancelled draft restores prior selection.

The exact post-commit selection choice is UI behavior, not identity allocation authority.

## Room effects

Every boundary-chain commit invokes P23.8 on all affected correspondence components.

Examples:

```text
closed outer loop
→ 0 old Rooms → one new candidate Room
```

Initial P23.8 correspondence rules primarily cover existing-Room edits; first enclosure creation may allocate one new Room deterministically from the canonical candidate face key because no predecessor exists.

```text
existing Room + complete divider
→ simple 1→2 Room split
```

```text
same geometry drawn as Partition
→ existing Room remains 1→1
```

A chain that causes unsupported many↔many correspondence in any affected component rejects atomically.

## Initial Room creation

When a boundary operation creates an enclosed candidate face with **no predecessor Room**, Museum may create a new persistent Room as an explicit result of that authoring command.

P23.8's **Initial Room creation — foundation responsibility** contract owns allocation, naming, floor/ceiling defaults, validation and exact replay. P23.9 invokes that same operation; it adds no separate creation/reconciliation implementation.

This does not weaken the hard boundary: topology derives faces; the authoring operation/product reconciliation allocates Rooms.

## Finish/Close validation

Before commit:

1. resolve all accepted snap intents to explicit Junction IDs/coordinates;
2. plan every required subdivision/noding operation;
3. reject zero/tiny/overlapping Walls;
4. build the complete candidate graph;
5. run P23.8 candidate faces/Room reconciliation;
6. remap/validate openings and portal semantics;
7. compile/validate canonical geometry;
8. commit once.

No click-by-click partial document commits.

## Keyboard/pointer cancellation

Required lifecycle:

- `Escape` → cancel entire chain;
- `Backspace` → remove latest draft leg while at least one prior point remains;
- pointer loss / workspace/domain change → cancel according to existing editor interaction teardown conventions, never leave a hidden active draft;
- Finish/Close disabled or returns explicit reason when candidate is invalid.

Respect existing keyboard focus/input guards; typing into numeric controls must not trigger draft Backspace/Escape behavior incorrectly.

## Tests

- simple open Wall chain commits once and creates no Room;
- closed outer loop creates deterministic Room identity;
- complete divider creates simple split identities per P23.8;
- Partition inside Room does not split Room;
- endpoint snap reuses Junction ID;
- endpoint-on-interior performs canonical subdivision;
- X crossing nodes explicitly when supported;
- collinear overlap rejects;
- Backspace removes only latest draft leg;
- Escape cancels whole draft/no history;
- invalid final candidate leaves document/selection unchanged;
- Rectangle creates same canonical graph as equivalent four-wall chain;
- Polygon close creates same canonical graph as equivalent chain;
- exact numeric draft length equals P23.1 semantic Wall length result;
- snap winner stable across Plan zoom;
- one finished chain affecting several independent valid correspondence components commits once;
- one chain with one unsupported component rejects all.

## Non-goals

- freehand/sketch recognition;
- persistent constraints;
- automatic topology repair;
- arbitrary trim/extend commands;
- general curve creation/editing;
- Room confirmation modal after every enclosure;
- multi-floor drafting in one gesture;
- BIM wall assemblies;
- separate Polygon/Rectangle persisted geometry systems.
