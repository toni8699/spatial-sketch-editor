## Ratified amendment (2026-09-11) — segment-first continuous drawing

Core semantic rule:

> One completed straight segment = one Wall authoring command and one Layout transaction. In the ordinary case it produces one Wall record; canonical subdivision/noding may materialize multiple Wall records inside that same transaction.

The whole run is no longer one transient chain. Only the currently previewed next segment is transient. Undo means "revert the last segment transaction and all fragments/effects it created," not literally "remove exactly one Wall record" — if `AB` crossed another Wall, canonical noding may have committed it as `A→X` + `X→B` fragments, and Undo reverts all of them together.

Initial interaction:

```text
Choose Wall

click A
→ establish current transient start

move toward B
→ preview A→cursor

click B
→ validate + commit Wall AB immediately
→ B becomes the continuation start

move toward C
→ preview B→cursor

click C
→ validate + commit Wall BC immediately
→ C becomes the continuation start
```

Each click after the first therefore does two things:

```text
1. completes the current Wall
2. establishes the start of the next candidate Wall
```

The Wall tool remains active. Do not require tool re-entry between connected Walls.

### Architecture unchanged

This amendment changes the **interaction and transaction boundary**, not the persisted geometry model:

```text
LayoutDocument
→ explicit Junctions / Walls
→ topology / noding
→ P23.8 face extraction + Room reconciliation
→ canonical geometry compiler/query
→ Plan + 3D
```

Do not introduce chain geometry as project truth, another Wall representation, a second topology engine, a renderer-local Wall path, another history mechanism, or a second selection authority.

### Transaction boundary

Each successfully completed Wall segment is one logical Layout transaction/history entry through the existing runner (`runLayoutMutation` / `commitLayoutTransaction` on the shared chronological stack — no special Wall history):

```text
click A, click B → Wall AB → history entry 1
click C         → Wall BC → history entry 2
Undo            → BC transaction reverted (Wall, fragments, Room effects), AB remains
```

All effects caused by one Wall belong to that Wall's transaction: Junction creation/reuse, endpoint-on-Wall subdivision, crossing noding, noding-caused fragmentation, opening/portal remapping, candidate-face extraction, Room birth/split/merge reconciliation, canonical validation. A rejected segment mutates nothing, creates no history entry, preserves authored prior Walls, and leaves the current start available for correction.

Rooms are never directly created by the drawing interaction. After every committed `boundary` Wall, the existing P23.8 reconciliation path runs as required; a commit that closes an enclosure (e.g. `DA` completing `AB+BC+CD`) commits `DA` **plus** its Room effects atomically, and Undo of that entry reverts both while leaving `AB`, `BC`, `CD` intact. No Create Room command, no Room confirmation step.

### Continuous-run closure

For `boundary` drawing, the active run remembers the canonical starting Junction ID once the first Wall commits. When a final endpoint resolves to that same Junction ID, the Wall commits normally; after topology/Room reconciliation completes, the run clears its continuation state while the Wall tool stays selected — the next click starts a new run. Closure is explicit Junction identity (`resolvedEndJunctionId === runStartJunctionId`), never coordinate proximity alone and never "a Room appeared". Snapping may suggest the start Junction, but committed topology identity is authoritative. For Partition, keep the same segment lifecycle but end runs via Escape (no Room-completion inference) unless existing code already supports a better small deterministic convention.

### Transient state

The old model (`[A, B, C, D]` = one transient chain) is replaced by: `AB`, `BC`, `CD` are authored Walls; only `D→cursor` is transient. The active interaction retains only the next-candidate state (follow existing code conventions for exact shape):

```ts
currentStartPoint
currentStartJunctionId   // null until the first Wall commits
runStartJunctionId       // set once the first Wall commits
cursorPreview
role
```

After each commit, continuation state derives from the **canonical committed result**, not stale pointer coordinates. Never duplicate authored Wall/Junction topology in transient state.

### Segment result contract

The per-segment commit must return the canonical resolved Junctions of the committed candidate:

```ts
startJunctionId  // canonical start (establishes runStartJunctionId after the first commit)
endJunctionId    // canonical end (becomes the next continuation start)
```

Both are required: after the first `A→B`, the UI needs canonical `A` as much as canonical `B`. The planner already resolves both internally but does not expose them (`commitWallChain()` returns only Wall IDs and Room IDs today). Do not derive continuation from `createdWallIds` — crossing/noding can turn one candidate into several Wall fragments, so Wall IDs do not identify the run endpoints. Status text must not claim `Committed wall <id>` unless the transaction really produced exactly one Wall record.

### Finish / Close / Escape / Backspace (new semantics)

- **Finish is removed** from normal Wall/Partition authoring. A completed segment commits immediately; there is no pending authored chain waiting for Finish.
- **Escape** cancels only the active continuation preview (`C→cursor`), clears the run, creates no history entry, and leaves committed `AB`/`BC` intact. The Wall tool remains selected unless existing editor convention strongly requires otherwise. Escape must never remove committed Walls.
- **Backspace** must not act as undo for committed legs; committed Walls use normal Undo/Redo. Keep Backspace only for genuinely transient compound tools where already appropriate (e.g. an uncommitted Polygon gesture).
- **Close is not required** for minimum P23.9. Normal closure is click/snap onto `runStartJunction`. If the UI keeps Close as a convenience, it means exactly: current committed endpoint → run starting Junction → commit **one** final Wall transaction. It must never commit/recommit the preceding run as one chain.

### Undo / Redo and teardown

History operates only on committed transactions. If Undo/Redo fires while a next-segment preview is active, clear the transient continuation state first, then perform the history operation; never reconstruct the run from history. Also clear continuation state on real teardown only: project/document replacement, import/reset, workspace/domain transition, view unmount, or genuine pointer cancellation. `pointerleave` must **not** cancel the run — click-click UX requires leaving the SVG to focus the Length control and coming back; it clears only the cursor/snap preview (current viewport behavior already does exactly this). No stale start Junction may survive document/history replacement. (Note: the viewport's existing `previewVersion` watch already clears draft state on any document bump — reuse it.)

### Snapping, precision, exact entry

P23.1 and P23.2 are preserved unchanged per candidate segment: `start → cursor → snap/constraint resolution → resolved endpoint → canonical Wall operation`. Junction reuse, Wall midpoint/interior snap, endpoint-on-Wall subdivision, valid intersections, orthogonal/angle guides, grid fallback, exact length, angle constraints, deterministic snap ordering, screen-space acquisition, and model-space tolerances all stay. The pointer path has no geometric meaning; the Wall stays straight between resolved endpoints; no freehand geometry.

Typed exact length resolves the endpoint of the **current candidate segment**: on confirmation, resolve endpoint → validate → commit current Wall → the committed endpoint becomes the next continuation start. Do not append another transient chain point and wait for Finish.

## Outcome

A creator can sketch architecture directly as continuous Walls/Partitions in Plan. Rectangle and Polygon remain convenience tools, but they produce the same canonical Junction/Wall records rather than a parallel Room-polygon system.

## Primary workflow

```text
Choose Wall
→ click A (transient start)
→ preview A→cursor (snap / type exact length where supported)
→ click B → Wall AB commits immediately (one history entry)
→ B becomes the continuation start, preview B→cursor
→ click C → Wall BC commits immediately (one history entry)
→ … run continues without tool re-entry …
→ click/snap final endpoint onto the run's starting Junction → final Wall commits, run ends, tool stays selected
→ Escape at any time cancels only the active preview; committed Walls remain
```

Partition uses the same interaction with `role: 'partition'` (Escape ends the run; no Room-completion inference).

## Segment versus transient state

Only the currently previewed next segment is transient editor/session state.

- the second click commits one Wall immediately (one history entry);
- the committed endpoint becomes the next continuation start;
- Undo removes the previous **committed** Wall transaction (never a transient leg);
- Escape cancels only the active continuation preview/run with no document/history change;
- an invalid candidate commits nothing and preserves the current start for correction.

Do not persist half-finished candidate state into `LayoutDocument`.

## Open Walls are valid architecture

A valid open Wall/Partition may be committed without producing a Room.

Room creation is not a modal confirmation step. After a boundary-Wall commit, P23.8 derives candidate enclosed faces and reconciles persistent Rooms automatically where supported.

## Wall versus Partition

### Wall

Creates `role: 'boundary'` Walls. They participate in Room face extraction.

### Partition

Creates `role: 'partition'` Walls. They are real physical Walls and use the same:

- Junction topology;
- thickness/height fields;
- compiler/mesh machinery;
- opening hosting where semantically valid;
- selection/query IDs;
- precision/snap tools.

But they do not divide semantic Rooms.

No generic `LayoutObject.kind = box` is presented as a Partition.

## Junction/connectivity semantics

Snapping is a suggestion; committed topology is explicit.

### New endpoint near existing Junction

If the snap winner is accepted, reuse that Junction ID.

### New endpoint on Wall interior

Acceptance invokes P23.8 canonical Wall subdivision and connects to the resulting Junction.

### Proper Wall crossing

If the chosen operation permits an X crossing, plan all required Wall subdivisions/Junction creation before commit. Installed new-schema data must not contain an un-noded visual crossing.

### Collinear overlap

Reject. Do not auto-merge/trim/choose one Wall.

## Rectangle convenience tool

Rectangle is a bounded multi-Wall creation frontend.

It creates:

- four Junctions, subject to explicit reuse/snap where valid;
- four straight Walls using the chosen role;
- one complete candidate operation;
- Room reconciliation through P23.8 if boundary Walls form a supported enclosure.

Rectangle is not a distinct persisted Room geometry kind.

Initial interaction may be two-corner drag/click with exact width/depth entry integrated from P23.1. Rotated rectangle authoring may be added only if the existing Plan interaction model can keep the gesture deterministic without creating an unrelated transform mode.

## Polygon convenience tool

Polygon is simply a multi-click closed boundary/partition run.

- same Junction/Wall records;
- same P23.8 topology gate;
- no standalone polygon truth.

Lifecycle distinction (segment-first era): Polygon **may remain a bounded compound transient tool** (transient vertices, Backspace/Escape operating on still-uncommitted vertices, one atomic commit) if that is the safest reuse of current code. Its lifecycle must not redefine normal Wall tool semantics — the Wall tool commits per segment; only the Polygon tool may hold a multi-vertex transient.

## Planner reuse (segment-first)

Prefer the smallest change to current implementation. If the existing `planWallChain` safely plans one segment:

```ts
planWallChain({
  baseline,
  points: [start, end],
  close: false,
  role
})
```

Reuse `planWallChain` as the canonical engine **after** the P23.9 adapter-correctness fixes below (true correspondence components, canonical Room allocator, authored-segment provenance). A thin `planWallSegment(...)` wrapper may delegate to it. Do not fork the topology or reconciliation algorithms. Existing multi-segment planner support remains for the bounded compound convenience tools (Rectangle/Polygon) above.

## Precision integration

P23.1 provides exact straight-Wall semantics. During a candidate segment, where supported, the current segment may accept:

- exact length (typed value resolves the **current** endpoint; on confirmation the Wall commits and the endpoint becomes the next start — never another transient point waiting for Finish);
- horizontal/vertical or explicit angle constraints already defined by P23.1/P23.2;
- typed meter values that bypass gesture grid snapping.

Do not build a persistent constraint solver. Exact draft input resolves into final endpoint coordinates/Junction topology for the committed candidate.

## Snap integration

Consume P23.2's one snap pipeline:

```text
tool/context validity
→ semantic feature priority
→ screen distance
→ stable ID/key
```

Draft candidates may include:

- Junction/endpoints;
- Wall midpoint;
- Wall interior projection;
- valid intersection;
- orthogonal guide;
- bounded extension;
- grid fallback;
- parallel/perpendicular/angle aids only where P23.2 explicitly supports them.

Reference acquisition remains screen-space. Model topology tolerances remain H3-owned.

## Visual candidate feedback

P23.6 owns the final visual polish, but P23.9 requires a functional transient presentation:

- committed Walls visually distinct from the candidate preview;
- current segment preview (from the canonical committed endpoint);
- active snap winner/guide;
- invalid candidate state;
- clear first/current point;
- explicit role indication Wall versus Partition.

Presentation never becomes geometry truth.

## Selection behavior after commit

Use existing deterministic selection authority adapted by F0.

Recommended minimum (segment-first era):

- preserve selection throughout continuous Wall drawing; never select newborn Rooms mid-run (the current branch behavior of selecting the born Room would interrupt the run and must be removed from the Wall/Partition path);
- roomless commits preserve current selection — no `wallId` authority is invented here (see below);
- continuous drawing must never depend on selection;
- failed/cancelled candidates leave selection unchanged.

The exact post-commit selection choice is UI behavior, not identity allocation authority.

## Room effects

Every boundary segment transaction invokes P23.8 on all affected correspondence components.

Examples:

```text
closed outer loop
→ 0 old Rooms → one new candidate Room
```

Initial P23.8 correspondence rules primarily cover existing-Room edits; first enclosure creation may allocate one new Room deterministically from the canonical candidate face key because no predecessor exists.

```text
existing Room + complete divider
→ simple 1→2 Room split
```

```text
same geometry drawn as Partition
→ existing Room remains 1→1
```

An authoring operation that causes unsupported many↔many correspondence in any affected component rejects atomically.

## Initial Room creation

When a boundary operation creates an enclosed candidate face with **no predecessor Room**, Museum may create a new persistent Room as an explicit result of that authoring command.

P23.8's **Initial Room creation — foundation responsibility** contract owns allocation, naming, floor/ceiling defaults, validation and exact replay. P23.9 invokes that same operation; it adds no separate creation/reconciliation implementation.

This does not weaken the hard boundary: topology derives faces; the authoring operation/product reconciliation allocates Rooms.

## Per-segment validation

Before each segment commit:

1. resolve the accepted snap intent to an explicit Junction ID/coordinate;
2. plan required subdivision/noding for this one segment;
3. reject zero/tiny/overlapping Walls;
4. run P23.8 candidate faces/Room reconciliation for the one-segment candidate;
5. remap/validate openings and portal semantics;
6. compile/validate canonical geometry;
7. commit once (one history entry).

No click-by-click partial document commits beyond the segment itself; no waiting for Finish.

## Compiler prerequisite (acceptance-blocking)

Segment-first authoring requires roomless Walls to exist in canonical compiled/query geometry immediately after commit:

```text
commit open Wall AB
→ no Room required
→ AB present in canonical compiled/query output
→ available to normal downstream Plan/3D consumers
```

Confirmed gap on the branch: `compileWallFirstLayoutGeometry` builds segments only from `room.boundary` (`packages/layout-core/src/layout-geometry.ts:144-165`), `CompilerSource` carries only `floors[].rooms[]` (`:82-100`), `CompiledLayoutGeometry` has no top-level physical-Wall collection (`layout-geometry-types.ts:214-220` — `floors`, `rooms`, `objects`, `queries`; `CompiledWall[]` exists only under `CompiledRoom`), `compileRoom()` is where Walls are actually compiled (`:314-339`), and `plan-render-model.ts:437-447` emits wall primitives by iterating `room.walls` — so an authored Wall no Room references never reaches compiled geometry, snap/align queries, Plan, or 3D.

This is therefore a **bounded compiled-geometry contract change**, not a render-model patch. Preferred direction: canonical wall-first compilation exposes physical Walls independently of Room ownership, keyed by document-global Wall ID, emitting each physical Wall once; Room floor/ceiling semantics remain Room-derived. Since current compiled query records are Room-oriented, the new physical-Wall path must **not invent fake Room ownership for a roomless Wall**:

```text
roomless physical Wall
→ document-global Wall identity
→ canonical physical-Wall/query output
→ no fabricated roomId/Room ownership merely to satisfy the old compiler shape
```

Whether that means optional Room fields, separate physical-wall records, or another bounded representation inside the same compiler is the implementer's choice. Plan/3D/query then consume that canonical physical-Wall output without double rendering. That is still **one compiler**, not a second geometry system. P23.6 may style/polish compiled Walls but must not invent omitted authored Walls. If the gap is fixed before implementation, record the actual behavior here instead.

## Selection (no new authority)

No new selection authority is invented. The live authority is still legacy room-anchored (`{kind:'wall', roomId, segmentId}`, `layout-interaction.ts:121-124`) with no `wallId` target; the `(roomId, segmentId)` → canonical `wallId`/`junctionId` cutover belongs to P23.6/P23.7 per P23.8:371-381. Until then: roomless commits preserve current selection, continuous drawing never depends on selection, and legacy `roomId/segmentId` ownership is never faked. Richer Wall selection defers to its proper owner.

## Keyboard/pointer cancellation

Required lifecycle:

- `Escape` → cancel only the active continuation preview/run (committed Walls remain; no history entry; tool stays selected unless editor convention strongly requires otherwise);
- `Backspace` → must not remove committed legs (they use normal Undo/Redo); kept only for genuinely transient compound tools (e.g. uncommitted Polygon vertices);
- Undo/Redo during an active preview → clear transient continuation first, then run history;
- genuine pointer cancellation/capture teardown, workspace/domain change, document replacement → cancel per existing teardown conventions (reuse the `previewVersion` watch), never leave a hidden active run; ordinary `pointerleave` is explicitly excluded (it clears only cursor/snap preview);
- invalid candidates return an explicit reason on the plan surface and preserve the current start.

Respect existing keyboard focus/input guards; typing into numeric controls must not trigger Backspace/Escape behavior incorrectly.

## Tests (segment-first boundary)

At minimum (rewrite/add; old whole-chain tests that assert Finish-to-commit, Backspace-pops-leg, or one-chain-one-entry are superseded and must be rewritten, not extended):

- **basic segment history:** click A, click B → one authored Wall AB + one history entry; click C → Wall BC + second entry; Undo → BC transaction reverted (Wall, fragments, effects), AB remains;
- **room closure:** AB + BC + CD committed; commit DA by resolving onto starting Junction A → DA + Room effects = one transaction; Undo → DA removed, Room effects reverted, AB + BC + CD remain;
- **continuous drawing:** commit AB → B automatically becomes next start; preview begins from canonical B; no tool re-entry;
- **rejection:** invalid candidate (overlap + other existing invalid cases) → no mutation, no history entry, prior Walls remain, current start available for retry;
- **Escape:** AB + BC committed, C→cursor active → Escape clears preview/run, AB + BC remain, no history entry;
- **Undo during continuation:** AB + BC committed, C→cursor active → Undo clears the run, reverts BC, no stale continuation from C;
- **junction reuse:** endpoint snaps to existing Junction → same canonical Junction ID, no duplicate;
- **endpoint-on-Wall:** canonical subdivision + segment effects commit atomically; Undo restores exact prior topology;
- **crossing:** explicitly noded where supported; all noding effects in the segment transaction; Undo restores exact prior topology;
- **closure identity:** ending on the run's canonical starting Junction commits the final Wall and ends the run; near-coordinates without explicit Junction reuse do not count as closure;
- **Partition:** segments commit individually with normal per-segment history; no semantic Room split;
- **precision:** typed exact length resolves the current endpoint, commits exactly one segment transaction, and makes the canonical end Junction the next continuation start; canonical noding may materialize multiple Wall records inside that transaction;
- **determinism:** equivalent replay → same committed Junction/Wall IDs per allocator contract, same Room reconciliation identities, same history snapshots, no transient state persisted;
- **roomless Wall compiler/query:** commit open Wall AB with no Room → Wall present in canonical compiled/query output for Plan/3D consumers;
- **Rectangle:** canonical four-Wall result, one bounded atomic history entry;
- **Polygon:** canonical Walls/Junctions, no persisted polygon geometry type;
- retained planner coverage (reuse as-is where still valid): open/closed/partition, junction reuse incl. near-miss, T/X noding, overlap/collinear rejection, multi-crossing, multi-component atomicity, rect≡chain exact-document equality, Proxy-baseline clone test; divider tests rewritten against true `1→2` lineage + metadata preservation (see above).

## Implementation delta from PR #18 (branch `p23.9`)

Derived from actual inspection of the branch (`ea09667`; planner `packages/layout-core/src/layout-wall-chain.ts`, facade `apps/editor/src/lib/layout/layout-wall-chain.ts`, interaction `apps/editor/src/lib/editor/layout/layout-interaction.ts`, preview `apps/editor/src/lib/editor/layout/layout-preview-state.svelte.ts:659-691`, viewport `apps/editor/src/lib/editor/layout/LayoutPlanViewport.svelte`, workspace `apps/editor/src/lib/editor/app/PlanWorkspace.svelte:57-111`, history `layout-mutation-runner.ts` + `history-controller.svelte.ts` + `editor-store.svelte.ts:2858`, compiler `packages/layout-core/src/layout-geometry.ts:82-165`, render `apps/editor/src/lib/layout/plan-render-model.ts:437-447`, tests `p23-9-wall-chain.test.ts` (25) + `p23-9-wall-chain-commit.test.ts` (5) + `layout-interaction.test.ts` draft/length/cursor blocks).

**Reuse (no change):**

- `planWallChain` noding machinery (junction reuse by coordinate, T/X noding loop, collinear-overlap rejection, JSON-round-trip clone, wall/junction allocator contract), P23.8 entry points (`planWallSplitAtPoint`, `planWallCrossing`, `reconcileRooms`, `extractBoundaryCandidateFaces`), P23.1 exact-length semantics, P23.2 `resolveLayoutSnap` pipeline and viewport `applyLayoutSnap` call sites, shared history runner (`runLayoutMutation` → `commitLayoutTransaction`), format gating in `LayoutDraftToolbar`, `previewVersion`-watch teardown seam, Rectangle→closed-chain and wall-first Polygon frontends in `PlanWorkspace`, rect≡chain equivalence test, Proxy-baseline test.

**Change (includes two correctness items previously misfiled as reuse):**

- **Planner adapter correctness — true P23.8 correspondence components.** `layout-wall-chain.ts:352-360` builds one component per candidate face (`candidateFaceKeys: [face.key]`), so a divider is interpreted as `1→1 + 0→1` instead of a true `1→2`: deterministic split-survivor choice and child inheritance (`reconcileRooms` `1→1 + 1→2` path, `layout-room-reconciliation.ts:236-283`) never engage, and the born child gets creation defaults instead of predecessor metadata. Rework the adapter to build true P23.8 correspondence components as connected components of the bipartite predecessor-Room ↔ candidate-face correspondence graph. Candidate faces with no predecessor form independent `0→1` birth components. Do not approximate this by one component per face or by grouping only identical predecessor sets. This naturally yields the supported `1→1`, `1→2`, `2→1` cases and lets P23.8 reject unsupported many↔many cases correctly, matching the canonical P23.8 contract. Regression must prove a divider is a genuine `1→2` (lineage `split-survivor` + `created` under one component) and preserves non-default predecessor metadata (name, floor/ceiling thickness) on the survivor/children. Segment-first does not fix this by itself.
- **Planner adapter correctness — canonical Room allocator.** `roomAllocatorAdapter` (`layout-wall-chain.ts:633-648`) ignores `faceKey`, seeds `room.chain.N`, and routes Room IDs through `nextJunctionId`. Replace with the canonical `createAuthoringRoomAllocator()` (`layout-wall-topology-ops.ts:53`), which seeds deterministic `room.<faceKey>` IDs. Regression: equivalent replay allocates identical Room IDs per the allocator contract.
- **Planner provenance — authored segment versus noding fragments.** `planWallChain` grows `createdWallIds` with every newly created noding fragment — including fragments of pre-existing intersected host Walls — and feeds that set back into `nextNodingFix` as `chainDerivedWallIds`, so the name/contract is misleading and host fragments participate as if they came from the authored candidate. Distinguish provenance explicitly, e.g. `authoredWallIds` (candidate segment lineage/fragments) versus `createdWallIds` (every new Wall record the transaction caused, if still needed) versus `splitWallIds` (pre-existing Walls affected); exact shape is the implementer's choice. Invariant: do not infer authored-segment provenance merely from "Wall record did not exist before this noding pass." If an authored-derived Wall is subdivided, its child fragments inherit authored provenance. ## Implementer handoff

- **State machine:** `idle (tool armed, no start)` → `first click = transient start` → `preview start→cursor` → `click = validate + commit one Wall + seed next start from canonical endJunctionId (set runStart from canonical startJunctionId on first commit)` → `preview …` → `resolve end == runStartJunctionId = final commit + clear run (tool stays armed)`; `Escape = clear preview/run only`; `Undo/Redo = clear preview/run first, then history`; `pointerleave = clear cursor/snap preview only, never the run`; selection preserved throughout the run.
- **Transaction boundary:** one completed segment = one authoring command and one `runLayoutMutation`/`commitLayoutTransaction` entry carrying Junction/noding-fragment/Room/opening/compile effects; rejections commit nothing. Undo reverts the whole segment transaction including fragments.
- **Canonical planner path:** `planWallChain({ baseline, points: [start, end], close: false, role })` (or thin `planWallSegment` wrapper) **after** the adapter correctness fixes (true components + `createAuthoringRoomAllocator` + authored-segment provenance); Rectangle/Polygon keep multi-point chain calls.
- **Segment result contract:** `startJunctionId` + `endJunctionId` from the committed candidate — never derived from `createdWallIds`.
- **Transient state that remains:** `currentStartPoint`, `currentStartJunctionId`, `runStartJunctionId`, cursor preview, role — nothing else.
- **Old chain behavior to delete:** `wallChainPoints` array model, Finish/Close commit, Backspace-pops-leg, Escape-cancels-all, click-start within 14px to close (replaced by Junction-identity closure), chain-length leg appending, mid-run newborn-Room selection, `Committed N-wall chain` status strings.
- **Tests to rewrite/add:** the segment-first list in [Tests](#tests-segment-first-boundary) plus the genuine-`1→2` divider regression; planner reuse tests stay.
- **Compiler/query prerequisite:** bounded physical-Wall contract change first (else committed segments are invisible and several acceptance tests cannot pass).
- **Explicitly deferred:** `wallId` selection authority (P23.6/P23.7), wall-first boot/migration (P23.0/P23.7), all prior non-goals.
